<objective>
Gap closure for 14-VERIFICATION.md's Key Link warning and 14-REVIEW.md **WR-01**.

`niche-score.test.ts:323-331` is the SOLE enforcement of the locked structural-separation invariant
(`niche-score.ts` / `flags.ts` must never import the vision / value-gap / area-comps / Phase-14
analysis modules). Phase 14 explicitly leaned on it: three new specifiers
(`discovery/holistic-schema`, `discovery/confounder-guard`, `discovery/brf-lookup`) were registered
BEFORE the modules existed, because the guard is silently inert for an unlisted specifier.

But the matcher filters `source.split("\n")` down to lines matching `/^\s*import\b/`. A multi-line
named import puts the module specifier on the closing `} from "..."` line, which never matches — so
the guard is blind to the exact import style Prettier produces for more than one named import, and
the exact style `candidate.ts:6-13` and `confounder-guard.ts:24-31` already use for these very
modules. A future edit adding a multi-line `import { normalizeForConfounders, buildHolisticBrief }
from "@/lib/discovery/confounder-guard";` to `niche-score.ts` would pass the guard silently.

Purpose: this invariant is what keeps a hedged, image/data-derived analysis signal from silently
becoming a deterministic ranking input without the visible "från bildtolkning" marker (UI-SPEC §4,
D-14-06/D-14-07). An inert guard is worse than no guard — it reads as proof.

Output: a fixture-testable `sourceImportsVisionModule(source)` matcher plus regression tests that
FAIL against the old line-anchored implementation.
</objective>

  <action>
    In `src/lib/discovery/niche-score.test.ts`, inside the existing structural-separation describe
    block (do NOT create a new test file — this invariant lives in exactly one place by design):

    1. Add two module-specifier-aware regexes above the matcher:
    `const IMPORT_FROM_STATEMENT_RE = /^[ \t]*(?:import|export)\s+[\w*\s{},$]*?from\s*["'][^"']+["']/gm;`
    and
    `const SIDE_EFFECT_IMPORT_RE = /^[ \t]*import\s*["'][^"']+["']/gm;`

    The `[\w*\s{},$]*?` clause is deliberately NARROW and must be commented as such: it admits only
    the characters that can legally appear in an import clause (identifiers, `type`, `as`, `*`,
    braces, commas, `$`, and whitespace INCLUDING newlines), so a multi-line named import is matched
    whole, while the match can never run past a `(`, `;`, `/` or `=` into unrelated code or into a
    comment. A greedy `[\s\S]*?` would swallow prose between statements and produce false positives
    from a doc comment that merely names a module — the reason `niche-score.ts`'s own comments
    mention these paths.

    2. Replace the line-filtering matcher with a PURE source-text function:
    `function sourceImportsVisionModule(source: string): boolean` that collects
    `source.match(IMPORT_FROM_STATEMENT_RE) ?? []` and `source.match(SIDE_EFFECT_IMPORT_RE) ?? []`
    and returns whether any collected STATEMENT contains any entry of `VISION_MODULE_SPECIFIERS`.
    Because the whole statement (quotes included) is the haystack, the existing quote-suffixed
    entries keep working unchanged.

    3. Keep `importsVisionModule(sourcePath: string): boolean` as a thin wrapper:
    `readFileSync(join(process.cwd(), sourcePath), "utf-8")` → `sourceImportsVisionModule(...)`. The
    two existing `it(...)` assertions for `niche-score.ts` and `flags.ts` must remain untouched and
    still pass.

    4. Update the describe block's rationale comment with a WR-01 note: the matcher inspects whole
    (possibly multi-line) import/export-from statements because a line-anchored `/^\s*import\b/`
    filter is blind to the specifier on a closing `} from "..."` line — the shape Prettier produces
    for >1 named import and the shape `candidate.ts` / `confounder-guard.ts` use for these exact
    modules.

    Do NOT add, remove or reword any entry in `VISION_MODULE_SPECIFIERS`, and do not touch any
    production file.
