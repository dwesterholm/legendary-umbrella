## User Constraints (from CONTEXT.md)

### Locked Decisions

**Score definition**
- **D-01** The ranking score is **estimated flip profit in kr**: `resale − purchase − renoCost`. Not a 0–100 taste model.
- **D-02** `resale` = expected sold price of the flat in RENOVATED condition, from a hedonic kr/m² model fitted on Booli slutpriser (sold prices): micro-area, floor, balcony, build year, size band, distance to nearest hub. The fitted coefficients ARE the weights — floor and balcony are worth what the market paid for them.
- **D-03** `purchase` = asking price × district bid premium derived from the same slutpris data (study 2026-10-12: Söder final ≈ +7–10 % over asking, Kungsholmen +3–4 %). Expected final, not asking, is what is compared to the 4 M ceiling in the output (flag when expected final > 4.0 M; do not hide the listing).
- **D-04** `renoCost` = tier from the existing `RENO_COST_MATRIX` / `flip-economics.ts`, selected by the VISION condition verdict (kitchen/bathroom/surfaces freshness). "Nyrenoverat" → low tier; original condition → high tier. Unknown (no images / vision skipped) → mid tier, flagged.
- **D-05** **No tax** in the model: Daniel defers vinstskatt via uppskov by buying the same year (interest-free since 2021). **No broker fee / holding cost**: near-identical across flats, does not change order. Keep the code shape so they can be added later, but zero by default.
- **D-06** **Taste bonus ≤ ~5 % of resale**, additive on top of profit, for: stated morning-leaning facade (E/SE/S from `extractOrientationFromDescription`), and proximity to Daniel's loved hubs (SoFo/Folkungagatan, Medborgarplatsen, Mariatorget, Slussen, Katarina Bangata, central Kungsholmen = Fridhemsplan/St Eriksgatan/Hantverkargatan core). Phrases like "sol hela dagen", "genomgående" count toward the sun part. Unknown orientation → no bonus, no penalty.
- **D-07** Balcony is a plus, never a must. A great reno object without a balcony must be able to outrank a 3rd-floor balcony flat with poor sun. This falls out of D-02/D-04 (balcony premium single-digit %, reno discount 10–20 %); add a regression test asserting it on fixtures.

**Filters (taste that is a filter, not a score)**
- **D-08** Hard filters: lägenhet, ≥35 kvm, asking ≤4.0 M kr, within innerstan (Södermalm, Kungsholmen, Vasastan, Östermalm as today's `innerstan` umbrella). **Floor is NOT a filter** (Daniel: score only); the hedonic model prices it.
- **D-09** Net = all of innerstan. Loved hubs get the bonus (D-06), never exclude anything.

**Vision re-ordering (lifts a v1.1 guard)**
- **D-10** Deterministic pre-rank over ALL candidates (cap 60) using the existing niche score + hedonic resale; then vision on the top **~20** (`VISION_ENRICH_LIMIT` 8 → 20, `CAP_VISION_SEK_MAX` raised proportionally, ~25 SEK; Anthropic/Apify spend pre-approved); then the profit estimate re-sorts the list. Candidates outside the vision window keep mid-tier reno cost, flagged "ej bildtolkad".
- **D-11** `niche-score.ts` and `flags.ts` stay PURE and keep their import ban. A NEW module (e.g. `src/lib/discovery/fit-score.ts` or `flip-profit.ts`) composes niche + vision + comps + hedonic. The static-grep separation test is AMENDED to allow the new module to import vision, not deleted.

**Delivery**
- **D-12** Headless first. Output = ranked table (script under `scripts/`, reusing `scripts/find-reno.ts`'s pipeline reuse pattern) with: address, kvm, floor, asking, expected final, resale estimate, reno tier, profit, taste bonus, flags, Booli link. No UI work in this phase — Daniel will not use the UI until the model is tuned. The 14.2 email consumes the same function.
- **D-13** The in-app discovery job keeps working unchanged for other niches; if the fit score is exposed in the job at all, it is behind the existing niche selection as a 4th `NicheId` ("daniel-profile" / "flip-profit") with no UI changes required.

## Summary

The pipeline pieces are all there and the seam is small. A headless script can reuse `find-reno.ts` (scrape, filter), call the existing `enrichCandidateImages` and `runVisionPass` on a pre-ranked subset, and hand the result to one new pure module that computes profit. `niche-score.ts` and `flags.ts` do not need to change. The separation test only inspects those two files, so a new composing module is not blocked by it; "amending" it means registering the new module specifiers so the two pure files can never import the composer, plus a positive control and updated comments. [VERIFIED: src/lib/discovery/niche-score.test.ts:366-372, quote: `expect(importsVisionModule("src/lib/discovery/niche-score.ts")).toBe(false);`]

The hard part is not plumbing, it is whether a hedonic-gap ranking finds anything real. I prototyped it this afternoon on a 350-sale / 147-listing Booli pull that a previous session left in `/private/tmp` (see Prototype Evidence). Three results matter for planning: (1) card-only features explain little (R² 0.35; floor is not statistically different from zero; a kernel-smoothed "price level of neighbouring sales" feature lifts R² to 0.50); (2) the candidate set (asking ≤4.0 M, ≥35 m²) is the cheap tail of the sold distribution, so every candidate sits 7–35 % below the model and a raw profit ranking simply sorts by "most below model", which is also where the defective flats live; (3) in that raw ranking Folkungagatan 61 lands 21st–28th of 35 Södermalm candidates, the opposite of D-14. With the repo's own discount-attribution cap (credit at most 15–20 % of value, `MAX_CONDITION_EXPLAINED_PCT`) and a "fresh kitchen" vision verdict it moves to 6th–13th. So D-14 is reachable but only if the vision window actually contains it and the credit cap exists; the plan must treat the live rank as a measured outcome, not a tuned target.

Two environment facts change cost and reliability assumptions. Real Apify spend per successful 2048 MB render is about $0.036 (about 0.40 SEK), roughly 6x the `USD_PER_RENDER = 0.0055` the code budgets with, and 18 of the 30 page renders I could inspect from a 40-way parallel burst timed out at 180 s (each timeout costs about $0.059). Also, Booli's sold-vs-asking label uses an en dash for below-asking sales, which `page-functions.ts` parses as a positive number, so every existing "sold vs list" value is sign-flipped for negative cases. That must be fixed before any bid premium is derived.

**Primary recommendation:** Build in this order: (1) fix the sold-card parser and add a bounded-concurrency slutpris puller that writes a gitignored cache; (2) fit a ridge OLS with a leave-one-out neighbour-price feature in a pure TypeScript module (about 60 lines, no new dependency); (3) a pure `fit-score.ts` that wraps `valueGap()` with a credit cap, vision-driven reno bundles and a ≤5 % taste bonus; (4) a headless `scripts/fit-score.ts` doing pre-rank, enrich+vision on the top 20, re-sort; (5) fixtures, offline replay, then one live run. Keep the in-app job untouched (D-13).

        │                                                        │ top ~20 by pre-rank profit (ties: asking/pred closer to 1 first)
        │                                                        ▼
        │                                  enrichCandidateImages(top20, 20, {deadlineMs: 15 min, concurrency ~4})

Decision points: pre-rank uses a constant reno cost, so its order is the hedonic gap order after the credit cap; vision only demotes dated flats (higher reno) or promotes fresh ones; the 4.0 M flag looks at expected final, not asking.

### Pattern 1: Ridge OLS on ln(kr/m²) with a neighbour-level feature
**What:** Standardise continuous features, add `λ·I` (not on the intercept) to `XᵀX`, solve by Cholesky, report SEs from the inverse, back-transform with the Duan smearing factor `mean(exp(residual))`. Features, in the order they should be tried (keep a feature only if 5-fold CV RMSE improves):
1. `nbLevel`: Gaussian-kernel (bandwidth about 300 m, cut-off 1 km) average of ln(kr/m²) over other sales, **leave-one-out for training rows**; fall back to district mean when kernel weight <0.5.
2. `floor` (numeric, clipped to 0–6, "BV" = 0) and `basement` indicator (floor ≤ 0).
3. `ln(m²)` (replaces "size band" dummies; fewer parameters, same information).
4. `monthsAgo` (centre at 0 = today) so the prediction is for today's market.
5. Optional second stage on residuals using only the detail-enriched subsample: `balcony`, build-year buckets (≤1930, 1931–1960, 1961–1990, ≥1991), each capped at ±8 %.
6. `centralityKm`: km to a **market** centrality list (Stureplan, T-Centralen, Medborgarplatsen, Hornstull, Odenplan, Fridhemsplan), not Daniel's loved hubs; drop it if `nbLevel` already absorbs it.
**When to use:** always for the resale term. The planner should not add district dummies if `nbLevel` is present (keep them only as the fallback path).

## Common Pitfalls

### Pitfall 1: Below-asking sales are parsed as above-asking (en dash)
**What goes wrong:** Booli renders a below-asking sale as `"–1,5%"` with an en dash (U+2013, TrendDown icon). `toNumber` uses `/-?\d[\d ]*(?:[.,]\d+)?/` which does not match an en dash, so it returns `1.5`. The existing `soldPricePercentageDiff` (and `SoldComp.soldVsListPct`) is positive for negative cases. In the 350-card pull the minimum parsed value is exactly 0. [VERIFIED: src/lib/booli/page-functions.ts:54-59 and 168; live probe label shapes `"–#,#%"` + TrendDown]
**Why it happens:** the only fixture/test uses `"+15,1%"` (page-functions.test.ts:72).
**How to avoid:** in the new `slutpriser.ts` parser (and fix `page-functions.ts`), treat U+2013, U+2212 and `-` as minus, and use the icon key (`TrendDown`) as a cross-check. Add tests for `"–1,5%"`, `"−0,4%"`, `"+0%"`, and `null`. Re-derive every premium number after the fix; the study figures in CONTEXT (+7–10 % Söder, +3–4 % Kungsholmen) may carry the same bias if they came from this parser (unknown).
**Warning signs:** minimum premium is 0; median premium looks too high; premium never negative.

### Pitfall 2: Selection on the outcome makes cheap flats look like bargains
**What goes wrong:** candidates are filtered to ≤4.0 M and ≥35 m², which is the low tail of the sold distribution for that size band. Every candidate is below the model (median asking/pred 0.79), and the profit ranking just sorts by depth below the model.
**How to avoid:** (a) credit cap at `MAX_CREDIT_PCT = 0.20` of resale (reuse `MAX_CONDITION_EXPLAINED_PCT`), (b) `hiddenDefectRisk` flag at asking <75 % of prediction (reuse `DISCOUNT_ATTRIBUTION_TRIGGER_PCT = 0.25`), (c) exclude rows with asking/pred <0.5 as "ej jämförbar" and print them in a separate list (Norra Hammarbyhamnen 1.75 M / 45 m² is the example), (d) report the median asking×(1+bid)/pred of the candidate set as a model-health line; if it is outside 0.85–1.15 apply a segment offset rather than silently trusting levels, (e) never tune cap or premium to a single listing.
**Warning signs:** top 10 are all ground-floor or under 80 k kr/m²; median profit above 500 000 kr.

### Pitfall 3: Cost model understates Apify spend about 6x and failures cost more than successes
**What goes wrong:** `USD_PER_RENDER = 0.0055` (cost.ts:8) versus observed $0.0358 per successful 2048 MB run and $0.0586 per timed-out run. A budget built on `renderSek` will be wrong by 6x; `CAP_SEK_MAX = 5` for the in-app scrape would not pass if the constant were corrected (4 districts x 5 pages x about 0.40 SEK = 8 SEK).
**How to avoid:** in the new scripts, report **actual** spend by listing runs started after the script's t0 through `apify-client` (`runs().list` then `usageTotalUsd`), as done in this research. Do not change `USD_PER_RENDER` in this phase (it would flip in-app caps); log it as a follow-up.
**Estimated cost of the pull (all `[ASSUMED]` volumes):** about 100–200 pages (35 sold cards per page; the Södermalm 33–47 m² slice produced 175 cards for about 7 weeks of peak season). At a 50–80 % success rate: about $0.05–0.095 per fetched page = about $5–19 (55–210 SEK) for the pull, plus about $0.04 each for any detail enrichment of sold flats. ### Pitfall 4: Parallelism and `waitSecs` cause half of the renders to time out
