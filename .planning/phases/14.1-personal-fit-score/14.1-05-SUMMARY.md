# Phase 14.1 Plan 05: Model-fitting maths Summary

**Ridge regression by hand-written Cholesky, plus the full fit around it: neighbour level that never sees its own price, a sign guard that falls back to the study's numbers and says so, deterministic cross-validation, smearing, district fallbacks, a flat-versus-slope bid premium and a Swedish plain-language readout, all proven on data generated from known coefficients.**

## What this plan does, in plain terms

14.1-03 built the half of `hedonic-model.ts` that prices a flat from a finished model file. This plan builds the other half: it turns the 7 431 sold flats from 14.1-04 into that model file. The model says "a flat like this sold for about X kr per m²" and every ranking in the phase rests on it. If the fitting maths is wrong, every resale estimate is off in the same direction and nothing downstream can notice. So the work here is mostly about proving it right on data where the answer is known.

How the fit works, in the order it happens:

1. Each sale becomes one number to explain: the log of its price per m².
2. For each sale, a "neighbour level" is the distance-weighted average price of other sales within about 1 km. The sale itself is left out of its own average. Without that, the model would partly be told the answer it is asked to predict.
3. The model weighs six things: neighbour level, floor, ground floor, size, months since the sale, and distance to the nearest big hub. A small penalty (the "ridge") stops two features that move together from taking huge opposite values.
4. One cleaning pass drops sales that sit far outside the scatter (3 robust standard deviations).
5. A guard checks each weight. If it points the wrong way (a higher floor making the flat cheaper) or is too uncertain to tell from noise, it is replaced. The replacement is the research study's number where one exists (floor +1 % per floor, ground floor -10 %) and zero otherwise. Every replacement is written into the model file and printed in Swedish.
6. Five-fold cross-validation (fit on four fifths, test on the held-back fifth, five times) gives an honest error on sales the model has not seen.

## Accomplishments

- **Solver:** `choleskySolve` and `fitRidge`, no dependency. Recovers a noiseless line to 1e-6, stays finite when two columns are identical or one column is all zeros.
- **Fit:** `fitHedonicModel` returns a model that `hedonicModelSchema` accepts, from synthetic data with floor +1 %/floor, ground floor -10 %, size -0.08. The recovered floor coefficient lands within 0.004 of the truth.
- **Honest fallbacks:** wrong-signed floor becomes exactly ln(1.01) with source "prior"; a wrong-signed size effect (no study value exists) becomes 0 with source "zeroed"; an uncertain-but-right-signed floor is labelled "unstable". All three are recorded.
- **No self-leakage:** a sale never sees its own price in its neighbour level, and a held-out sale never sees its own fold. The cross-validation test uses pairs of twin sales that always land in the same fold; if the held-back twin were visible the error would collapse to near zero, and it stays above 0.15.
- **Bid premium:** fitted flat and as a slope on how far the asking price sits from the model price. The lower cross-validation error wins. Sales with no label are left out and their share is reported (27.3 % on the real cache).
- **Size range (R-12):** `minLivingArea` and `maxLivingArea` are taken from the kept rows, so 14.1-07 can flag candidates outside it. A test plants a 300 m² outlier and checks it does not widen the range.
- **Plain language:** `describeModel` produces 17 to 20 Swedish lines on a real fit, e.g. "En våning upp ≈ +1,6 % (SE 0,1 %), källa: data".
- **Tests:** 99 in `hedonic-model.test.ts` (was 30), 70 more across the repo. Five deliberate one-line breakages of the code (own-price leakage, CV leakage, guard disabled, size range from all rows, wrong sign in a description) were each caught by a failing test.

## What the real cache said (smoke run, not a deliverable)

I ran the finished code once on the real 7 431 rows to see that it survives them. It took 7.9 s, produced a schema-valid model, and nothing was written to the repo. The real fit and the committed model file belong to 14.1-08. Treat these as a first look:

| Item | Result |
|---|---|
| Rows kept / dropped as outliers | 7 381 / 50 |
| R² (same data) / typical error on unseen sales | 61 % / about ±12 % (CV-RMSE 0.116 in log scale) |
| One floor up | +1.6 % (SE 0.1 %) |
| Ground floor or below | -6.4 % (SE 0.8 %) |
| Market trend | +0.9 % per month, about +11 % per year |
| Size | zeroed, see below |
| Distance to hub | -0.7 % per km (SE 0.4 %), small |
| Bid premium form | slope, b = -0.19 (the research prototype found -0.21); flat CV 0.076, slope 0.073 |
| Premium when asking equals the model price | Södermalm +11.0 %, Kungsholmen +5.7 %, Vasastan +6.1 %, Östermalm +3.9 % |
| Sales without a premium label | 27.3 %, left out |
| Smearing / renovated-value cap | 1.007 / at most +8.3 % over the model price |

Three things in that table are for you to look at, not for me to decide:

1. **The size coefficient came out positive (+0.046 on ln of area, about +3 % in price per m² for a doubling of the area, t = 8.4), so the guard zeroed it.** Bigger flats costing more per m² goes against the expected direction, and no study value exists for it, so the rule from the plan applied. My guess at why, which I did not test: 14.1-04 could only pull the 60 to 120 m² flats from the latest 2.5 to 6 months, so size and recency are tangled together, and the +0.9 %/month trend has to untangle them. With size at zero the model gives no discount for big flats. If the trend is overstated, that is where it would show. Options for 14.1-08: accept it and say so, or pull more months for the upper bands before the final fit.
2. **+11 % per year market growth** over April 2025 to October 2026 deserves a sanity check against what you know of the market.
3. **The premium figures are not comparable with the raw medians in 14.1-04** (Södermalm +13.9 %). Under the slope form the district figure is the premium for a flat asked exactly at the model price; a flat asked below it draws a bigger bid, one asked above it a smaller one.

Also expect this on the real fit: **distance to hub is mostly redundant.** The neighbour level already contains it, because neighbours within 300 m are about as close to the hubs as the flat is. In my synthetic city it was replaced by zero in nearly every seed. On the real cache it survived with a small value. Either outcome is fine for pricing; if it gets zeroed, the printout says why. This is the situation RESEARCH Pattern 1 describes ("drop it if nbLevel already absorbs it").

## Decisions Made

- **Worst-first guard with refit.** The plan says a bad coefficient "is replaced". I replace one at a time, worst first, and refit the others against the value actually used. If "floor" is overruled, "ground floor" moves with it and would otherwise be estimated against a number the model no longer uses.
- **Slope intercepts are medians.** The plan asks for the lower cross-validation error to win. Comparing a median-based flat against a mean-based slope is unfair (squared error rewards the mean), so a slope model with no real slope kept winning in my test. With median intercepts, flat is exactly slope with b = 0.
- **Stage-2 buckets are relative to an average flat.** The schema (from 14.1-03) says a known balcony multiplies by 1 + pct and an unknown one leaves the price alone. Expressing build-year effects at the average balcony mix keeps unknown-balcony candidates unbiased; a known balcony then adds its percent on top, which over-shoots by roughly half the balcony effect for a flat that has one. The schema has no "no balcony" deduction, so this cannot be fixed here.
- **Out-of-fold predictions for the premium** include ln(smearing), matching what `expectedOverbid` receives at prediction time.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug, test wording] "Intercept equals mean(y)" only holds for centred columns**
- **Found during:** Task 1
- **Issue:** The plan's own formula is `intercept = mean(y) - Σ beta_j·mean_j`, so with a huge penalty the intercept equals mean(y) only if the columns are centred. My first test used raw columns and failed by 9e-5.
- **Fix:** The test checks the property that does hold (the line passes through the point of means within 1e-9) and the plan's literal statement on centred columns. Code unchanged.
- **Commit:** 2e69f10

**2. [Rule 1 - Bug] Description printed a rising market as falling**
- **Found during:** Task 2, real-cache smoke run
- **Issue:** `monthsAgo` counts backwards, so a coefficient of -0.0085 means prices rise 0.85 % a month. `describeModel` printed "Marknaden per månad ≈ -0,9 %". Daniel would have read that the market is falling.
- **Fix:** Sign flipped for that line, label renamed "Prisutveckling per månad", regression test added.
- **Commit:** 4db4ed1

**3. [Rule 2 - Missing critical] Fair comparison between flat and slope premium**
- **Found during:** Task 2 (a constant-premium test kept picking the slope form)
- **Issue:** Median intercepts for flat against mean intercepts for slope, scored on squared error, favours slope for the wrong reason.
- **Fix:** Slope intercepts are medians of z - b·u. See Decisions.
- **Commit:** 4db4ed1

### Test premises that did not survive contact, and what I did

- **"Centrality wrong-sign at +5 %/km → zeroed" could not be built on distance to hub.** In a small test city the neighbour level absorbs smooth location effects (see above). The wrong-sign-without-prior test uses the size coefficient instead; centrality is covered by the exact-number `guardVerdict` tests and a test that predictions stay right when it is zeroed.
- **"Closeness of the neighbour-level coefficient to 1" was dropped.** Four tight clusters make that coefficient poorly pinned down (1.26 ± 0.11 in one run). The test checks sign, strength and, in the train/serve test, that prices come out within 5 %.
- **The "unstable" integration test is pinned to seed 3.** It is deterministic (same seed, same rows). The decision itself is covered by exact numbers in the `guardVerdict` tests, so the pin only demonstrates the wiring.
