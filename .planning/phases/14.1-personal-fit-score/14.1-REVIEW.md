**Reviewed:** 2026-10-13

## Summary

The phase's core machinery holds up under adversarial reading. I traced these and found them correct:

- Cholesky solve and ridge (indexing, centring, un-scaling of beta/SE, zero-variance columns, the 1e-8 lambda floor, NaN rejection).
- Duan smearing and the back-transform (residual mean is exactly zero by construction, so smearing is at least 1).
- Sign handling of the sold-vs-asking label: the character classes contain the real U+2013 and U+2212 code points (verified by code point, not by eye), and the icon override and the node/page-function cross-check work.
- The page function's `toSignedPct` escaping inside the template literal.
- Bounded concurrency in the puller: the render-allowed check and the counter increment have no await between them, so the render cap holds.
- The Apify headroom check runs before the first paid call in all four scripts, and `--dry-run` exits ahead of any spend.
- Secrets are never printed: only `satt`/`saknas`. apify-client sends the token in an `Authorization` header, so the `console.error(error)` in the transport does not leak it.
- `git diff a432c2f..HEAD` shows `niche-score.ts` and `report/flags.ts` untouched. Neither imports any of the five new modules.

There are no blockers. The six warnings are heuristic and data-completeness defects that change money numbers or silently shorten paid data. The reno classifier and the sun-phrase matcher have confirmed false positives (reproduced by running the regexes). The puller can record a transient failure as end-of-results and never retry it.

## Warnings

### WR-01: Negation window in `NEGATED_RENOVATION` turns "renovated" into "dated" across clause boundaries

**File:** `src/lib/discovery/reno-tier.ts:161-162` (used at 182)
**Issue:** The second branch allows up to three arbitrary words between `ej|inte|icke|aldrig` and `renoverat`, and it only stops at punctuation. A claim joined with `och`/`utan`, or a negation about something else, is read as "renovation negated", which classifies as `dated` and prices a full reno. I reproduced these by running the shipped regexes:

| Text | Result | Should be |
|---|---|---|
| `Ej synliga skador och nyrenoverat kök` | dated | fresh |
| `Inte bara fräscht utan helrenoverat kök` | dated | fresh |
| `Köket är inte gammalt, nyrenoverat 2023` | dated | fresh |

For a kitchen, dated versus fresh swings the reno bundle from 0 to 200 000 kr (`kitchen-full` mid), and for all three attributes from 10 000 to 427 500 kr. That is the whole profit margin of a typical row, and it reorders the ranking. The phase's own revisit threshold is 20 % misclassified claims, and nothing measures the rate.
**Fix:** Tighten the window so the negation must directly govern the verb. The sketch below allows only auxiliaries or adverbs between negation and verb (untested, check it against the table above). Alternatively keep the window but forbid conjunctions and other clause openers inside it.
```ts
export const NEGATED_RENOVATION =
  /\borenover(?:at|ad|ade)|\b(?:ej|inte|icke|aldrig)\s+(?:(?:alls|längre|nyligen|helt|nyss|ut\s+att\s+vara|verkar\s+vara|vara|varit|blivit|har|är)\s+){0,3}\S*?renover(?:at|ad|ade|ats)/i;
// and add a negative lookahead for clause joiners, e.g. (?!(?:och|utan|men|samt)\b) on each skipped word
```
Add table-driven tests for the three strings above plus "Ej renoverat badrum" and "Köket har inte renoverats sedan 1990".

### WR-02: "No renovation need" short-circuits dated words, and negated dated words are still dated

**File:** `src/lib/discovery/reno-tier.ts:169-170, 180-186`
**Issue:** There are two related gaps in `classifyClaimText`.
1. `NO_RENOVATION_NEED` is tested first and returns `ok` for the whole text. A claim that also contains dated vocabulary is understated: `Gammalt kök, inget uppenbart renoveringsbehov` and `Daterat badrum men inget renoveringsbehov` both classify as `ok` (verified). That breaks the module's own rule that the worst state wins so that a cost is never understated.
2. The shared `DATED` regex has no negation handling, so `Köket är inte gammalt` and `Köket är ej daterat` classify as `dated` (verified). The negation-first logic only covers the word "renoverat".

Related: `ursprunglig` and `ursprungliga` mark any "original details" claim as dated, which includes well-kept pre-war parquet or stucco under `overall`. That adds the paint-plus-floors bundle (about 60 000 kr) to well-kept pre-war flats.
**Fix:** Test dated vocabulary first and let "no need" only downgrade a bare `renoveringsbehov` hit. Strip negated dated words before testing. The sketch is untested; check it against the strings above.
```ts
const NEGATED_DATED = /\b(?:inte|ej|icke|aldrig)\s+(?:\S+\s+){0,1}(?:gammal\w*|daterad\w*|daterat|slit\w+|sliten|omodern\w*)/i;
export function classifyClaimText(text: string): Exclude<RenoState, "unknown"> {
  const cleaned = text.replace(NO_RENOVATION_NEED, " ").replace(NEGATED_DATED, " ");
  if (NEGATED_RENOVATION.test(cleaned)) return "dated";
  if (DATED.test(cleaned) || DATED_EXTRA.test(cleaned)) return "dated";
  if (RENOVATED.test(cleaned)) return "fresh";
  return "ok";
}
```

### WR-03: `genomgående` is read as a through-flat layout, but brokers also write "genomgående renoverad"

**File:** `src/lib/discovery/sun-path.ts:317, 331`
**Issue:** `THROUGH_FLAT_RE = /\bgenomgående\b/iu` matches "Lägenheten är genomgående renoverad med hög standard" (verified `true`). In Swedish listings "genomgående" is at least as common as an intensifier ("genomgående renoverad", "genomgående hög standard") as it is for "genomgående planlösning". Every such flat gets `throughFlat: true`, so `sunScore` adds 0.3, which adds 0.9 % of resale (about 35 000 kr on a 3.8 Mkr flat) to its profit. That is unearned, and it favours freshly renovated flats, the opposite of what the reno ranking wants.
**Fix:** Require the layout nouns, and keep a negative lookahead for condition words.
```ts
const THROUGH_FLAT_RE =
  /\bgenomgående\s+(?:planlösning|lägenhet|våning|bostad|rum|ljus)\b|\bgenomgående\b(?!\s+(?:renover|fräsch|hög|god|bra|modern|nyrenover|ny|ytskikt|standard|skick))/iu;
```
The simplest safe form is the first alternative only (a missed phrase costs nothing; a false hit costs money).

### WR-04: A page that is empty once and then errors is recorded as a final, empty page

**File:** `src/lib/booli/slutpriser.ts:512-536`
**Issue:** The attempt loop sets `sawEmpty = true` on any empty response and never clears it. If attempt 1 comes back empty (the half-loaded page the comment describes) and attempts 2 and 3 throw (proxy 403, timeout), the loop exits with `parsed === null && sawEmpty === true`. The `parsed === null && !sawEmpty` branch is skipped, so the page is written as `status: "ok", rowCount: 0, attempts: 3`. `isFinalPage` returns true, `runSlice` treats `rowCount === 0` as the end of the results and returns, and a resume never renders that page again. Result: a district-and-size slice is silently cut short, and the paid cache is permanently missing the older sales for it. This is the data-loss mode the file header promises to avoid ("a gap would skew time coverage").
**Fix:** Only treat the page as an empty end-of-results when every attempt returned empty:
```ts
let emptyCount = 0;
// in the loop, on an empty response:
emptyCount += 1;
// after the loop:
const allEmpty = parsed === null && emptyCount === attempts;
if (parsed === null && !allEmpty) { /* failed state */ } else { /* ok / empty state */ }
```
Add a test with the sequence empty, throw, throw. It should yield `status: "failed"`.

### WR-05: Live run prints the "real" Apify bill immediately, without letting the ledger settle

**File:** `scripts/fit-score.ts:311-331` (called at 428 and 447)
**Issue:** `pull-slutpriser.ts` and `probe-fit-sources.ts` both wait 8-10 s (`LEDGER_SETTLE_MS`) before reading `apifySpendSince`, because `usageTotalUsd` of just-finished runs is not final. `printSpend` in `fit-score.ts` calls it straight after the last render and prints the result as "Kostnad ... (från körnings-API:t)" and a `Totalt` line. It can come out low, and that number is what Daniel uses to decide how much monthly headroom is left. The fallback estimate also leaves out broker-page renders and failed detail fetches (`renders = areas + detailFetched`).
**Fix:** Share the settle delay (move `LEDGER_SETTLE_MS` and the wait into one helper) and call it from `printSpend`. Count the fallback as `areas + 3 * window.size` (the documented worst case per window row) or label it "minst".

### WR-06: The sign guard zeroes a coefficient that the data supports at t = 8.4

**File:** `src/lib/discovery/hedonic-model.ts:637-644, 743-753`; `data/hedonic-model.json` (features, lnArea)
**Issue:** `EXPECTED_SIGNS.lnArea = -1` makes the guard replace the fitted size coefficient (+0.0461, SE 0.0055, t = 8.4) with zero. The model note says "Daniel avgör", so the decision is flagged. The mechanics still matter: `lnArea` has mean 3.896 (about 49 m²), so a zeroed slope over-predicts the 35-40 m² target segment by roughly 0.046 x (ln 37 - 3.896), about 1.3 %. That is about 50 000 kr of resale on a 3.8 Mkr flat. It pushes every small flat's profit up, and the above-cap `creditCapped` logic hides some of it. The guard also cannot tell "sign contradicts a prior" from "estimate is noise", so it overrides the most certain coefficient in the model.
**Fix:** Either keep the locked D-18 behaviour and surface the bias in the printed table (add a line "storlek nollställd, små lägenheter prissätts ca 1-2 % högt"), or change the guard so a wrong-sign estimate with |t| above, say, 3 is kept and flagged instead of replaced. Record the decision in CONTEXT either way.

## Info

### IN-01: `CAP_VISION_SEK_MAX` was raised 10 to 25 for the in-app path to serve a headless script

**File:** `src/lib/discovery/cost.ts:188`
**Issue:** The constant is the shared ceiling for in-app discovery jobs (comps, BRF and vision share one pool). The comment argues practical spend is unchanged because `VISION_ENRICH_LIMIT = 8`. That is a convention, not an enforcement. Anything that widens the enrichment limit in the app now has a 2.5x looser backstop. `runVisionPass` already takes `initialSpentSek`, so a per-call cap parameter would have let the headless run pass 25 and keep the app at 10.
**Fix:** Add `capSek?: number` to `runVisionPass` options, default to the old 10, and have `fit-score.ts` pass 25.

### IN-02: Bid-premium slope `b` has no sanity bound, unlike every other coefficient

**File:** `src/lib/discovery/hedonic-model.ts:424-436, 1049-1077`
**Issue:** Each regression coefficient goes through the sign and stability guard, but the slope of the bid premium does not. It is not capped, and `expectedOverbid` has no clamp. A fitted `b < -1` would mean a higher asking price lowers the expected final price. With the current model (`b = -0.187`) the effect is small (a flat asked at 0.5 x model gets about 26 % overbid), so this is only a latent risk on a refit.
**Fix:** In `fitSlopePremium`, return null (fall back to flat) when `b` is outside `[-1, 0]`, and note it in `fallbacks`.

### IN-03: A resumed pull keeps the old `asOf`

**File:** `scripts/pull-slutpriser.ts:446-453`; `scripts/fit-hedonic.ts:242`
**Issue:** On resume the code prints that the cache's cutoff is kept, but `cache.asOf` stays at the first pull date. `fit-hedonic.ts` defaults the model's price date to `cache.asOf`. A fit run weeks after a late resume predicts the old date. The fitted trend is about 0.85 % per month, so each month of lag understates today's price by that much.
**Fix:** Update `cache.asOf` to the current day when a pull adds rows, or have `fit-hedonic.ts` default `asOf` to the newest sold date in the cache.

### IN-04: `sizeCheck` throws when the last three months hold no sales

**File:** `scripts/fit-hedonic.ts:171-209, 287`
**Issue:** `used` can be empty for a stale cache or an `--as-of` override. `fitRidge` then throws `RangeError`, and the script exits 1 after the model is already fitted but before it is written, so a diagnostic aborts the real output.
**Fix:** Skip the recent check when `points.length < MIN_FIT_ROWS` and print "för få försäljningar".

### IN-05: `apifySpendSince` can undercount without saying so

**File:** `src/lib/booli/transport.ts:176-213`
**Issue:** It stops after 20 pages (2 000 runs) and treats a run with no or invalid `startedAt` as "older", which ends the walk. Both cases return a smaller number with no flag. The budget guard in `pull-slutpriser.ts` takes `max(real, estimate)`, which masks it for now.
**Fix:** Add `truncated: boolean` to `ApifySpend` and print it next to the number.

### IN-06: Table output uses U+2212 for negatives and can print "-0"

**File:** `src/lib/discovery/fit-pipeline.ts:300, 335-336`; `scripts/fit-score.ts:93`
**Issue:** `toLocaleString("sv-SE")` writes negative numbers with MINUS SIGN (U+2212) and a no-break space as thousands separator (verified). A reader that parses the printed table with `Number()` fails on any loss row. `Math.round(-0.3)` gives `-0`, which prints as "-0". Money is correctly rounded once at the table boundary, so this is cosmetic.
**Fix:** If the table is ever machine-read (Phase 14.2 email), add `+ 0` after rounding (`Math.round(n) + 0` normalises `-0`) and document the U+2212 behaviour, or format negatives with an ASCII hyphen.

### IN-07: Floor labels with a typographic minus are dropped

**File:** `src/lib/booli/slutpriser.ts:223`
**Issue:** The label parser handles the typographic minus, but `parseFloorLabel` only accepts ASCII `-`. A basement floor written "vån −1" returns null and is imputed with the mean floor. It is not a wrong-sign error, just lost information, and it matters little (3 % of rows are `groundOrBelow`).
**Fix:** Use `([-–−]?\d+...)` and normalise the sign, as `parsePremiumLabel` does.

### IN-08: One bad Booli id aborts the whole enrichment at the end

**File:** `src/lib/booli/slutpriser.ts:880`
**Issue:** `soldDetailUrl(row.booliId)` sits outside the `try`. A cached id that is not all digits (the id falls back to `String(value.booliId ?? value.id ?? key...)`) makes `one()` reject. `runPool` swallows it until the end, then `enrichSoldRows` throws, so the script reports failure although the rest was fine and persisted.
**Fix:** Move the URL build inside the `try` and count it as `failed`.

### IN-09: Duplicated numbers and a hard-coded local key

**File:** `scripts/pull-slutpriser.ts:284`; `scripts/fit-score.ts:386`; `scripts/fit-hedonic.ts:103-109`
**Issue:** Three small things.
- The enrichment dry run hard-codes 0.036 and 0.059 instead of `OBSERVED_USD_PER_RENDER_2048MB` and `OBSERVED_USD_PER_TIMED_OUT_RENDER`, so a rebase of those constants will not reach it.
- `fit-score.ts` embeds Supabase's well-known local-development publishable key as a fallback. It is not a secret, but secret scanners will flag it, and it would silently point a production-configured shell at localhost.
- `fit-hedonic.ts` re-implements `sv`/`svPct` (decimal-comma helpers) that already exist unexported in `hedonic-model.ts`.

**Fix:** Import the cost constants, require the env vars (or read the local default from the supabase config), and export the formatters from one module.
