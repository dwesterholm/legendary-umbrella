<decisions>

### Score definition
- **D-01:** The ranking score is **estimated flip profit in kr**: `resale − purchase − renoCost`.
  Not a 0–100 taste model.
- **D-02:** `resale` = expected sold price of the flat in RENOVATED condition, from a hedonic kr/m²
  model fitted on Booli slutpriser (sold prices): micro-area, floor, balcony, build year, size
  band, distance to nearest hub. The fitted coefficients ARE the weights — floor and balcony are
  worth what the market paid for them.
- **D-03:** `purchase` = asking price × district bid premium derived from the same slutpris data
  (study 2026-10-12: Söder final ≈ +7–10 % over asking, Kungsholmen +3–4 %). Expected final, not
  asking, is what is compared to the 4 M ceiling in the output (flag when expected final > 4.0 M;
  do not hide the listing).
- **D-04:** `renoCost` = tier from the existing `RENO_COST_MATRIX` / `flip-economics.ts`, selected
  by the VISION condition verdict (kitchen/bathroom/surfaces freshness). "Nyrenoverat" → low
  tier; original condition → high tier. Unknown (no images / vision skipped) → mid tier, flagged.
- **D-05:** **No tax** in the model: Daniel defers vinstskatt via uppskov by buying the same year
  (interest-free since 2021). **No broker fee / holding cost**: near-identical across flats, does
  not change order. Keep the code shape so they can be added later, but zero by default.
- **D-06:** **Taste bonus ≤ ~5 % of resale**, additive on top of profit, for: stated morning-leaning
  facade (E/SE/S from `extractOrientationFromDescription`), and proximity to Daniel's loved hubs
  (SoFo/Folkungagatan, Medborgarplatsen, Mariatorget, Slussen, Katarina Bangata, central
  Kungsholmen = Fridhemsplan/St Eriksgatan/Hantverkargatan core). Phrases like "sol hela dagen",
  "genomgående" count toward the sun part. Unknown orientation → no bonus, no penalty.
- **D-07:** Balcony is a plus, never a must. A great reno object without a balcony must be able
  to outrank a 3rd-floor balcony flat with poor sun. This falls out of D-02/D-04 (balcony premium
  single-digit %, reno discount 10–20 %); add a regression test asserting it on fixtures.

### Filters (taste that is a filter, not a score)
- **D-08:** Hard filters: lägenhet, ≥35 kvm, asking ≤4.0 M kr, within innerstan (Södermalm,
  Kungsholmen, Vasastan, Östermalm as today's `innerstan` umbrella). **Floor is NOT a filter**
  (Daniel: score only); the hedonic model prices it.
- **D-09:** Net = all of innerstan. Loved hubs get the bonus (D-06), never exclude anything.

### Vision re-ordering (lifts a v1.1 guard)
- **D-10:** Deterministic pre-rank over ALL candidates (cap 60) using the existing niche score +
  hedonic resale; then vision on the top **~20** (`VISION_ENRICH_LIMIT` 8 → 20, `CAP_VISION_SEK_MAX`
  raised proportionally, ~25 SEK; Anthropic/Apify spend pre-approved); then the profit estimate
  re-sorts the list. Candidates outside the vision window keep mid-tier reno cost, flagged
  "ej bildtolkad".
- **D-11:** `niche-score.ts` and `flags.ts` stay PURE and keep their import ban. A NEW module
  (e.g. `src/lib/discovery/fit-score.ts` or `flip-profit.ts`) composes niche + vision + comps +
  hedonic. The static-grep separation test is AMENDED to allow the new module to import vision,
  not deleted.

### Data acquisition for the hedonic model
- **D-17:** Slutpris pull via the existing Apify/Booli transport (`page-functions.ts` handles
  slutpriser pages). Scope: four innerstan districts, ≥35 kvm, last 12–18 months, need floor,
  balcony flag, build year (detail enrichment where cards lack it — cards lack build year/BRF),
  coordinates, sold price, asking price, sold date. Cache to a local JSON/parquet-like file under
  `.planning/calibration/` or `data/` (gitignored if large) so fitting is repeatable without
  re-scraping. Respect Apify memory fix (2048 MB renders, limited parallelism).
- **D-18:** Model: ordinary least squares on log(kr/m²) with the features in D-02 is sufficient;
  no ML framework. Report coefficients + R² in the phase SUMMARY in plain language (e.g. "one
  floor ≈ +1.8 %, balcony ≈ +4 %"). If a coefficient has the wrong sign or is unstable, fall back
  to the study's medians and say so.

### Resolved after research (orchestrator calls, 2026-10-12 — Daniel's question budget was spent; report these in the SUMMARY for his confirmation)
- **R-01 (D-04 "tier")** = condition SEVERITY bundles at the MID price band of `RENO_COST_MATRIX`: all fresh ≈ 10 000, unknown ≈ 105 000, all dated ≈ 427 500 kr for a 35 m² flat; `RENO_BAND` configurable; print the reno range in the table. "High price band" was never meant — it would price a 35 m² reno at ~1 M and erase every reno object (breaks D-07).
- **R-02 (D-14 calibration)** is MEASURED, not tuned. Record Folkungagatan 61's rank + per-component decomposition. A fresh-kitchen flat with little margin ranking mid-table under a profit model is a correct result, not a bug. Do not add knobs whose only purpose is to lift one listing. Expose the knobs that exist for principled reasons (credit cap 15–20 % reusing `MAX_CONDITION_EXPLAINED_PCT`, bid-premium model, vision window) as named constants.
- **R-03 (D-10 vision window)** = two constants: in-app `VISION_ENRICH_LIMIT` stays 8 (sequential pass, 120 s deadline would wedge the job); headless `FIT_VISION_WINDOW = 20`. `CAP_VISION_SEK_MAX` → 25.
- **R-04 (bugs found by research, fix in Wave 0 — they corrupt the dataset otherwise):** (a) Booli writes below-asking sales with an en dash "–1,5 %" / minus sign "−0,4 %"; `page-functions.ts` parses them as positive → sign-flip; the study's +7–10 % / +3–4 % premiums may carry this bias and must be recomputed. (b) Search-card `balcony: false` means UNKNOWN; enrichment merge `c.balcony ?? detail.balcony` never lets a detail `true` win → treat card false as null, let detail overwrite. (c) `extractOrientationFromDescription` returns null for "södervända", "sydvänd", "sydöstläge", "genomgående" — extend the keyword set (still reject "Söderort", "Södertälje").
- **R-05 (sold-page fields):** Wave 0 probe, ≤3 renders, whether sold detail pages expose build year + balcony. If yes, enrich a random 150–300 sample (≈6–13 USD, pre-approved). If no, drop those features from the fit and use capped priors; say so in the SUMMARY.
- **R-06 (Apify reality):** renders cost ≈ $0.036 ok / $0.059 timed-out, not the $0.0055 `USD_PER_RENDER` assumes → fix the constant; concurrency ≤ 8, `waitSecs` 240, `maxRequestRetries` 3; report spend from the Apify runs API, not from estimators. Slutpris depth unproven (deep pages timed out) → probe pages 10/30/60 first; if capped, slice by living-area bands per district.
- **R-07 (bid premium):** fit both the flat per-district median and `ln(1+premium) = a_district + b·(ln askingKrPerSqm − ln predKrPerSqm)`; use the second when CV error is lower; fall back to the flat median when n < 30 per district; null labels ≠ zero (exclude, report share).
- **R-08 (data location):** raw dataset + snapshots under `.planning/calibration/data/` (gitignored); the small aggregate model JSON (coefficients, SEs, R², fit date, n) IS committed so the replay test is deterministic in CI.
- **R-10 (supersedes the "fix the constant" clause of R-06, orchestrator 2026-10-12):** the in-app `USD_PER_RENDER` (0.0055) and its cap tests stay UNCHANGED in this phase — changing it would silently re-scale every in-app discovery cost cap. The headless scripts get SEPARATE observed-cost constants (`OBSERVED_USD_PER_RENDER_2048MB ≈ 0.036`, `OBSERVED_USD_PER_TIMED_OUT_RENDER ≈ 0.059`) for their spend ledger and MUST prefer the real bill read from the Apify runs API. Re-basing the in-app constant is a follow-up todo, not this phase.
- **R-11 (plan size):** plans 14.1-01 and 14.1-06 hold 3 tasks each (the iteration-1 checker miscounted 4); the count is ACCEPTED as is — no split.
- **R-12 (slutpris size coverage):** the dataset must cover every size the hard filter admits. Pull bands `[35,40],[40,45],[45,50],[50,60],[60,80],[80,120]` (≥35 with no upper bound in the filter), and the model must flag `utanförModellensStorlek` on any candidate whose kvm lies outside the fitted range instead of extrapolating silently.
- **R-13 (paid steps):** every script branch that spends money (plan 04 pull, plan 08 enrichment, plan 09 live mode, plan 10 live run) is rated `costly` and runs the monthly-Apify-headroom check before the first paid call; rated, never gated (spend pre-approved).
- **R-09 (dependencies):** none new. Ridge via a short Cholesky in TypeScript. No Python (system python3 has no numpy).
