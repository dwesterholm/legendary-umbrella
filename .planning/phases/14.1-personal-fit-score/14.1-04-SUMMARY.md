# Phase 14.1 Plan 04: Slutpris dataset puller Summary

**Resumable Booli sold-price puller (sign-correct parsing, 8 renders at most in flight, per-page cache) plus the real pull: 7 431 sold flats across Södermalm, Kungsholmen, Vasastan and Östermalm, 35-120 m², sold 2025-04-12 to 2026-10-12, for 18.43 USD of Apify spend.**

## Performance

- **Duration:** about 3 h, almost all of it waiting on paid renders (three resumed runs)
- **Completed:** 2026-10-13
- **Tasks:** 2 (library with tests, then script plus the real pull)
- **Files:** 3 tracked created, 1 local gitignored data file

## Accomplishments

- The sold-price dataset the model is fitted on now exists locally: **7 431 rows** (Södermalm 2 371, Kungsholmen 2 218, Vasastan 1 972, Östermalm 870), refit-able offline with no more scraping.
- Below-asking sales are now kept as negatives: 444 of 5 406 labelled rows. Under the old parser every one would have looked like a premium.
- The puller survives what Booli actually does: pages that time out, and pages that load half-empty. A re-run picks up where it stopped and does not pay for finished pages again.
- All five boundaries the plan named are tested before a krona was spent: the cutoff day, exactly 8 in flight, null and signed labels, float kr/m², and the bands being contiguous from 35 to 120.

## Decisions Made

- The library takes `render` and `persist` as arguments and touches no file, clock or environment variable; the script supplies them.
- The upper-band cap stays at 4 pages per district as the plan says. That means the large flats come only from recent months. 14.1-05 should not read a time trend off the 60-120 m² rows alone.
- Rows are stored with a float `krPerSqm = soldPrice / livingArea`; Booli's own rounded "159 500 kr/m²" text is not used.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Half-loaded pages ended slices early and were cached as final**
- **Found during:** Task 2 (live run 1)
- **Issue:** Some renders returned Apollo data with no sold card in it (Östermalm 80-120 page 1, Södermalm 35-40 page 7 at an April 2026 date). The transport only throws when there is no data at all, so these counted as "ok, 0 sold", ended their slice and, worse, would have been skipped on resume. After run 1, Östermalm 80-120 held 3 rows and Södermalm's lower bands reached back only to November 2025.
- **Fix:** An empty page now uses its remaining attempts (up to 3) and counts as the end of results only after 3 empty looks; an `ok` page with 0 entries and fewer than 3 attempts is rendered again on resume. Two tests added, one replaced.
- **Files modified:** src/lib/booli/slutpriser.ts, src/lib/booli/slutpriser.test.ts
- **Verification:** 63/63 tests; run 2 fetched the missing pages (Östermalm 80-120 went from 3 to 140 rows)

## Issues Encountered

- 71 of 353 renders came back empty or timed out at about 245 s even with Apify's retries. Both kinds are billed. The puller retries each page up to 3 times, so 3 pages still failed all three times in run 2; run 3 re-fetched them.
- One page (Vasastan 35-40, page 4) returned 70 sold cards instead of 35, as if two pages arrived together. The duplicates were removed by Booli id, so it did no harm, but it is an unexplained Booli behaviour.
- The tools that print the transport's error add stack-trace lines to the run log for every timeout. Cosmetic.

## Coverage gaps the fit should know about

- **Upper size bands are recent-only** (see above): 60-120 m² flats come from the last 2.5 to 6 months, 1 104 rows in all. The size effect is anchored; the time trend for large flats is not.
- **Östermalm 40-45 m² is thin** (84 rows): page 3 came back empty three times, so it counts as the end of results. Östermalm 45-50 is also small (86 rows, 5 pages) but reaches back to 2024-07.
- **Vasastan 50-60 and Kungsholmen 50-60** ended on an empty page. Vasastan 50-60's oldest sale is 2025-05-23, about six weeks short of the cutoff.
- **Östermalm is the smallest district** (870 rows against 2 000 to 2 400 elsewhere). That looks like a real feature of the market (fewer small flats), but I did not check it.
- **Asking price is approximate** on the 72.7 % of rows that have it, because Booli's label is often a whole percentage ("+13%").
