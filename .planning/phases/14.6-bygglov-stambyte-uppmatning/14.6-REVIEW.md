# Phase 14.6: Code Review Report

**Reviewed:** 2026-10-18
**Depth:** standard (changes since cf106dc, plus small offline probes run with `npx tsx` against the real modules; no network, no paid call, no source modified)
**Files Reviewed:** 30
**Status:** issues_found

## Summary

The overall construction is careful. The client is a fixed-host, one-attempt, no-redirect, size-capped, 3 s-paced door with a 24 h per-host block; the parsers build their results field by field and never carry Handler, Documents or the free ärendemening out of memory; the committed detail fixtures have `Handler: null` and empty `Documents`; the optional `stambyteTerm` really is optional (no change to `HEDONIC_FEATURES` or `version`, a model file without the key predicts as before, a term that is not kept never moves a price); the sold cache is only read (the script even stats it before and after); `areaUpsideSek` is only called from display formatters in `fit-pipeline.ts`, never from `fit-score.ts` profit, taste or flags; the confounder switch is exhaustive; the mail cells are HTML-escaped and the Booli link is last in both `COLUMNS` and `plainCells`.

The defects cluster in four places: (1) one cache rule is broken in a way that wipes a multi-hour result (address map), (2) the text and tag readers have holes in exactly the "relining is never a stambyte" and "negation guard" rules the phase says it enforces, (3) several guards that exist in the spike script were not moved into the shared client, and (4) a few latent footguns that only bite when the stambyte term is grafted or a dry run is started with defaults.

Probes run and confirmed (details in the findings): one bad entry in `address-beteckning.json` turns the whole map into one entry on the next lookup; `Stambyte 2020 ej genomfört.` reads as completed 2020; `Stambyte genom relining` classifies as `["relining","stambyte"]` and yields `lastStambyteYear`; `Södermalm 8:57`, `Södermalm 85:7` and `Södermalm 857` share the file name `sodermalm-857`; Node's `redirect: "error"` surfaces as `TypeError: fetch failed` (cause `unexpected redirect`).

No structural-findings (fallow) block was supplied for this run.

## Critical Issues

### CR-01: One damaged entry wipes the whole address map (violates "never overwrite a damaged file")

**File:** `src/lib/stockholm/beteckning.ts:126-135` (also `scripts/stambyte-join.ts:311-313` and `:460`, `src/lib/stockholm/bygglov-cache.ts:331-340`)
**Issue:** `readMap` turns any unreadable or invalid map file into `{}` and logs "den skrivs om". `remember` then calls `saveAddressMap({ ...map, [key]: entry })`, which replaces the file with that single entry. The schema is `strictObject` with a refined key and a `status` enum, so one hand-edited or future-version entry makes the whole file "fel format". Confirmed by probe: a map with two entries, one with `status: "resolvd"`, held one entry after a single `resolveBeteckning`. The same happens in `scripts/stambyte-join.ts`: a failed `loadAddressMap` gives `map = {}` and the `finally` in `askAddresses` calls `saveAddressMap(map)`. The sold join alone is about 3 300 addresses at 3 s per request (roughly three hours of polite traffic); the file is shared with the candidate lookup. The cache header says a bad file "is never renamed or deleted", but "the next save overwrites it" is the same loss for a file that holds many independent answers.
**Fix:** Never write over a map that failed to load. Either refuse to save (throw a Swedish error telling the user to inspect or move the file), or move the bad file aside once (`address-beteckning.json.bad-<timestamp>`) before the first write. Better, parse entry by entry so one bad entry is dropped and reported while the good ones survive:
```ts
// bygglov-cache.ts
export function loadAddressMap(opts): { ok: true; map: AddressMap; dropped: number } | { ok: false; error: CacheMiss } {
  // read raw; if raw.entries is a record, safeParse each entry on its own and keep the valid ones
}
// beteckning.ts remember(): if the last load was { ok: false, error !== "saknas" }, throw instead of saving
```

## Warnings

### WR-01: Redirect to a login page is not a block (the plan-02 blind spot) in the client that every run shares

**File:** `src/lib/stockholm/bygglov-client.ts:226-229`; `src/lib/stockholm/minkarta.ts:329-332`
**Issue:** `redirect: "error"` makes Node throw `TypeError: fetch failed` with `cause: Error("unexpected redirect")` (confirmed with a local server). The client logs only `error.name` ("TypeError") and throws `CityStop("natverksfel")` with `blocked=false`. A city that starts redirecting to a login or terms page therefore never reaches the 24 h block; the weekly stage, `bygglov-candidates`, `stambyte-join` and `fit-score` simply retry on the next run. Only `scripts/bygglov-spike.ts` (`looksLikeRedirect`) recognises it, and only for the spike verdict. The same applies to Min Karta (`reason: "natverksfel"`, no block).
**Fix:** Move `looksLikeRedirect` into the client and treat it as a refusal:
```ts
} catch (error) {
  if (looksLikeRedirect(error)) { line(`${CITY_HOST}${path} omdirigering (${took()} s)`); return refuse("omdirigering"); }
  line(...); throw new CityStop("natverksfel");
}
```
Add `"omdirigering"` to `SPIKE_STOP_LABELS` and do the same in `minkarta.ts` (`refuse("omdirigering")`).

### WR-02: Stambyte text reader ignores a negation that follows the year ("Stambyte 2020 ej genomfört" reads as done 2020)

**File:** `src/lib/discovery/stambyte-text.ts:211-216` (the `!/(?<!\d)(?:19[5-9]\d|...)/.test(between)` clause in `negatedKeywords`); relining flag at `:303`
**Issue:** After the keyword, a negation is dropped whenever a year sits between keyword and negation. Probe results: `Stambyte 2020 ej genomfört.` gives `lastYear: 2020`; `Stambytet från 1975 är ej genomfört.` gives `1975`; `stambyte 2019 saknas` gives `2019`. The module's own cost-of-being-wrong note says a false hit tells Daniel the pipes were replaced when they were not, and the city/precedence merge treats the text year as a positive finding. The year exception exists for "Stambyte genomfört 2018 ingen avgiftshöjning", which is a different negation target. Separately, `RELINING.test(clause)` sets `relining = true` for "(ej relining)" (`Stambyte genomfört 2018 (ej relining)` gives `relining: true`).
**Fix:** Keep the exception only when the negated word is not followed by a completion participle. For example, treat a negation as binding to the keyword across a year when it is directly followed by `(genomfört|gjort|utfört|klart|slutfört|genomförts|gjorts)` or ends the clause:
```ts
const NEG_COMPLETION = /^\s{0,2}(?:genomför|gjor|utför|klar|slutför)\p{L}{0,4}/iu;
// in the "after" branch: allow a year between when NEG_COMPLETION.test(clause.slice(word.end))
```
and skip `relining = true` when a NEGATION sits within 15 characters before the relining word.

### WR-03: A case tagged both relining and stambyte counts as a stambyte year (breaks "relining is never a stambyte")

**File:** `src/lib/stockholm/bygglov-classify.ts:94-104` (rules), `:411` (`buildingFactsOf`), `src/lib/discovery/stambyte-join.ts:632` (`isStambyteCase`), `src/lib/stockholm/spike-report.ts:189-194`
**Issue:** The tag set is not exclusive. Probe: "Stambyte genom relining", "Stambyte med relining av stammar" and even "Ej stambyte, enbart relining" all classify as `["relining","stambyte"]`, and `buildingFactsOf` then returns `lastStambyteYear` and `lastStambyteBasis: "start"` plus `reliningCase: true`. The text reader has an explicit `RELINING_AS_STAMBYTE` guard for exactly this phrase; the city classifier has none, so the two sources disagree about the same wording. D-06/R-05 and the module headers promise the opposite. On today's data the damage is nil (0 of 2 928 swept cases and 0 of 1 104 cached cases carry both tags), so this is latent, not live.
**Fix:** In `classifyDescription`, drop `stambyte` when the stambyte match sits inside a relining construction (`genom|via|med|som|i form av` + `relin`) or when a negation precedes it, or define `isStambyteCase = kinds.includes("stambyte") && !kinds.includes("relining")` in one shared place and use it in `buildingFactsOf`, `stambyteAtSale`, `stambyteYearsOf` and the join.

### WR-04: Old, never-opened "stambyte" cases give a year even if they were withdrawn or refused; the cell shows only a bare year

**File:** `src/lib/stockholm/bygglov-classify.ts:340-344` (`needsDetail` skips cases older than 5 years), `:417-419` (`startYears`), `src/lib/discovery/fit-pipeline.ts:~566` (`formatStambyteCell`)
**Issue:** Refusal is read from `latest`, which exists only after a detail page was read, and detail pages are only fetched for cases started within five years. So a 2012 stambyte application that was "Avskrivet" or "Avslag" is never opened and still yields `lastStambyteYear = 2012` with basis `"start"`. The Stambyte column prints "2012" and drops the basis, so the reader cannot tell a slutbesked year from an unverified start year. Same effect in `stambyteAtSale` for the training join (`recorded` from start year without detail).
**Fix:** Either read the detail page for the single newest `start`-basis stambyte case per building (one extra request, cached), or show the basis in the cell ("2012 (start, ej kontrollerad)") and keep `start`-basis years out of the "genomfört" status. At minimum, carry `lastStambyteBasis` into `formatStambyteCell`.

### WR-05: `bygglov-sweep --dry-run` writes fixture data into the live sweep cache by default

**File:** `scripts/bygglov-sweep.ts:140` (and `:369` `saveSweep`); `scripts/bygglov-candidates.ts:91-95`
**Issue:** `cacheDir` defaults to `BYGGLOV_CACHE_DIR` even for a dry run. The dry run serves the single Södermalm "stambyte" 1985 fixture for ANY query whose `Description` is `stambyte` (any district, any window) and saves it with `fetchedAt` from a virtual clock that starts at the real current time. A later live sweep then sees fresh files and never asks those queries again, silently using fixture cases. The header example passes `--cache-dir .../bygglov-dry`, but nothing enforces it. `bygglov-candidates.ts` defaults safely to `bygglov-dry` but still accepts the live directory with `--dry-run`. The spike script uses a temp folder and has no such problem.
**Fix:** In a dry run, ignore `--cache-dir` and use `join(workDir, "cache")` (as the spike does), or reject a dry-run `--cache-dir` equal to `BYGGLOV_CACHE_DIR`.

### WR-06: "(redan i värderingen)" suffix over-claims for planned stambyte and for text-sourced "pågår"

**File:** `src/lib/discovery/watch-reasons.ts:282-291`, `:344-355`
**Issue:** `coveredByModel.stambyte` is `stambyteTerm.kept === true`, and the suffix is added to both "stambyte pågår" and "stambyte planerat ...". The term prices only (a) age buckets of a recorded city stambyte, (b) an `ongoing` group that exists only when at least 30 sold rows were ongoing (`term.ongoing !== null`), and (c) a reference. A planned stambyte is not an input at all, `ongoing` is read only from `cityStambyte.ongoing` (`fit-score.ts` `stambyteInputOf`) while the reason line also fires on broker text, and today's scratch fit has `ongoing: null` (22 rows). If the term is ever grafted, the mail would say the valuation already prices something it does not. Latent today (the committed model has no term).
**Fix:** Pass finer flags: `stambyte: { pagar: kept && term.ongoing !== null && source === "bygglov_stockholm", planerat: false }` and add the suffix only for the matching status and source.

### WR-07: One 404 or unparsable detail page ends the stage, or blocks the whole host for 24 h

**File:** `src/lib/stockholm/bygglov-client.ts:236-241` (any non-200 gives `CityStop("http-N")`), `:332-335` (`caseDetail` refuses on a missing model), `src/lib/stockholm/city-stage.ts:350-355`
**Issue:** `caseDetail` uses `dataSource=Archived|Active` taken from a case list that may be 30 days old; closed cases move to the archive. A detail request with the wrong `dataSource` (or a case since removed) gives either a 404 (a `CityStop` that `city-stage` treats as a stage-ending stop for all remaining rows) or a page with no `caseViewModel`, which `refuse("andrad-sida")` turns into a 24 h block of the host for every tool and the weekly job. A page-shape failure on one case is not evidence that the site changed. (The mechanism is verified in code; whether the city actually answers like this for a moved case is not verified.)
**Fix:** In `caseDetail`, treat 404 as "no detail" (return `null` or throw a non-stop error) and, on a missing model for a single case, retry once with the other `dataSource` before refusing; only block when the list page or a second detail page also fails. In `readDetails`, catch the non-block case and continue.

### WR-08: Min Karta never enforces its size cap while reading, and body errors escape the "never throws" contract

**File:** `src/lib/stockholm/minkarta.ts:349-355`; same pattern in `src/lib/stockholm/bygglov-client.ts:247-250`
**Issue:** Min Karta does `await response.text()` and checks the size afterwards (`MINKARTA_LIMITS.maxBytes` is comment-level only; no `content-length` check, no streaming cap), so a large or endless body is fully buffered until the 30 s abort. The abort (or a connection reset) during the body read throws out of `get()` because only the fetch call is inside the inner `try`; `resolveViaMinKarta` is documented as "Never throws on a bad answer". The city client has the same gap: `readCapped` can throw a raw `AbortError`/`TypeError("terminated")`, which is not a `CityStop`, so `city-stage` logs "en rad kunde inte behandlas" and goes on to the next row instead of stopping.
**Fix:** Reuse `readCapped` in `minkarta.ts` (move it to a shared module) and wrap both body reads in `try/catch` that return `{ ok: false, reason: "natverksfel" }` (Min Karta) or throw `CityStop("natverksfel")` (city).

### WR-09: Min Karta accepts a single candidate found at buffer 5 or 10 m without the point-in-parcel test

**File:** `src/lib/stockholm/minkarta.ts:399-401`
**Issue:** The header promises "NO FUZZY FALLBACK", but when the buffer ladder widens to 5 or 10 m and returns exactly one non-Stockholm-filtered registerenhet, it is returned as `resolved` on trust. If the address point sits on street land and the building's own plot is more than the buffer away, the one candidate can be a neighbouring plot (the street-land guard only catches district-named parcels such as `Södermalm 8:57`). The result lands in the 365-day address map as a resolved building and drives every later column for that candidate.
**Fix:** For `buffer > 0` with a single candidate that has an id, run the same `fastighetsinfo` + `pointInParcel` check (the call budget of 5 allows it: search + up to 3 buffer steps + 1 boundary); otherwise return `ambiguous`.

### WR-10: "No candidates" is cached for 30 days even when rung (c) was never tried

**File:** `src/lib/stockholm/beteckning.ts:210-228`
**Issue:** When `deps.minkarta` is null (Min Karta blocked, disabled, dry run, `--no-city`-style paths), the ladder ends at rung (b) and `remember(map, key, { status: "no_candidates" ... })` stores a negative answer for 30 days that is indistinguishable from "all four rungs said no". After Min Karta becomes available again the address is served from cache as unknown. `fetch_failed` from Min Karta is correctly not stored, so the code already knows the distinction.
**Fix:** Do not store a negative (or ambiguous) answer when rung (c) was skipped, or store it with the rungs tried and treat it as stale when (c) is now available.

### WR-11: File-name slug drops ":" so different beteckningar share one cache file and one in-run building entry

**File:** `src/lib/stockholm/bygglov-cache.ts:37-48`; `src/lib/stockholm/city-stage.ts:371-372`
**Issue:** `beteckningSlug` strips every character outside `[a-z0-9-]`. Probe: `Södermalm 8:57`, `Södermalm 85:7` and `Södermalm 857` all give `sodermalm-857`. On disk this only causes alternating refetches (the `sameBeteckning` check returns "annan fastighet"). In `city-stage.building()` the in-run `buildings` Map is keyed by the same slug, so the second building silently receives the first building's cases and stambyte facts. No collision exists among the 2 274 swept beteckningar today (47 contain ":"), so this is latent; Min Karta can return any colon designation.
**Fix:** Keep the colon in the slug (`:` to `_`, or `-k-`), and key `buildings` by the normalised beteckning (`beteckningKey`), not the slug.

### WR-12: A damaged `host-gates.json` fails open, and the rewrite drops other hosts' `disabled` flag

**File:** `src/lib/stockholm/host-gate.ts:54-77` (read), `:109-117` (`blockHost`)
**Issue:** An invalid or truncated file counts as "no block" and only logs. A politeness control that fails open means a corrupted file silently lifts a 24 h refusal; and any single bad entry (`reason` not matching `LABEL`) discards all entries. `blockHost` then rewrites the file from `read.gates` (empty), losing Min Karta's `disabled: true` (set when it refused our User-Agent), so Min Karta is asked again.
**Fix:** On a damaged file, treat the city host as blocked for this run (fail closed) and say so, and make `blockHost` refuse to rewrite a damaged file unless the user moves it (or parse per entry like CR-01).

### WR-13: The graft does not enforce R-08 (CV and t >= 2), and the keep rule passes on a hair

**File:** `src/lib/discovery/hedonic-model.ts:2371` (`keep = cvWith < cvWithout`), `:2497-2509` (`graftStambyteTerm`); `scripts/fit-hedonic.ts` `graftMode`
**Issue:** R-08 says a graft needs both the CV rule and t >= 2. The scratch fit already shows the weakness: kept with a 0.07 % gain and t = 0.9. `graftStambyteTerm` only checks that every other number is equal; it never looks at `kept` or the significance, and the `t` is not stored in the term, so `graftMode` cannot check it either (it prints "behållen" or "ej behållen" and writes the file). The correct outcome today depends on someone remembering the rule. Also, `hedonicModelSchema.parse({...base, stambyteTerm})` would silently strip any key the schema does not know, so "no other number changes" is not guaranteed for unknown keys.
**Fix:** Store `cvGain: { relativeRmseGain, t }` inside `stambyteTerm` (optional), and have `graftStambyteTerm` throw unless `donor.stambyteTerm.kept && (t ?? 0) >= 2` (with an explicit `--force-weak` override that prints the reason). Compare `Object.keys(base)` against the schema keys before parsing.

### WR-14: A single-year window with 500 or more rows is saved as complete

**File:** `src/lib/discovery/stambyte-join.ts:267-269`
**Issue:** `if ((rows >= SPLIT_ROWS || stated >= SPLIT_ROWS) && childrenOf(q).length > 0) return split(...)`; when `childrenOf(q)` is empty (a single year) the code falls through to `deps.save`, and `recordUnsplittable` is not called. The header promises "A single year that is still capped is reported (`unsplittable`)". With `vatten`/`avlopp`/`stam` keywords a single year in a big district could plausibly reach 500, and the report would show it as complete. Today's maximum is 442, so no live damage yet.
**Fix:** In that branch call `deps.recordUnsplittable(q, "antal")`, push to `unsplittable`, log, and still save (or not, but flag it).

### WR-15: `stambyte-join` has no per-address error isolation; one bad address stops a stage permanently

**File:** `scripts/stambyte-join.ts:439-440`, `:455-458`; also `:224-227` (`loadDetails` casts without validation)
**Issue:** `city.addressSearch(asking)` throws a plain `Error` ("Ogiltigt värde för adress") for an address longer than 80 characters or with a control character; `askAddresses` rethrows anything that is not a `CityStop`. Addresses are asked in a fixed order (most rows first, then alphabetical) and the failing key is never recorded, so every re-run stops at the same key and later keys are unreachable. The current sold data has a maximum address length of 28, so this has not triggered. `loadDetails` trusts `raw as { details?: Record<string, JoinDetail> }` with no schema, unlike every other cache file.
**Fix:** Wrap the single call in `try/catch`; on a non-stop error `remember(key, { beteckning: null, rung: null, status: "no_candidates", at })` and continue; validate `details` entries with a zod schema.

### IN-09: A replay of an old snapshot can see decisions made after its date

**File:** `src/lib/stockholm/bygglov-classify.ts:413-419`; `src/lib/stockholm/city-stage.ts:186-188`
**Issue:** `asOf` filters case start dates only. A slutbesked dated after the snapshot makes the stambyte "done" in a replay, with years clamped by `Math.max(0, asOfYear - lastYear)`. The module comment says a replay "must give the same facts a month later"; with a cache that later live runs update, it does not.
**Fix:** Ignore `slutbeskedDate`/`startbeskedDate`/`closedDate` later than `asOf` in `buildingFactsOf`.

### IN-10: Training and scoring define "ongoing" differently (matters only if the term is grafted)

**File:** `src/lib/discovery/stambyte-join.ts:958-969` vs `src/lib/stockholm/bygglov-classify.ts:432-435`; `src/lib/discovery/fit-score.ts` `stambyteInputOf`

### IN-11: The join script loads the address map before it takes the city lock

**File:** `scripts/stambyte-join.ts:311` vs `:359`
**Issue:** `map` is read at start and written back whole (`saveAddressMap(map)`); the lock is taken later, inside `openCity`. A candidate run between the load and the lock loses its entries when the join saves.

### IN-12: "One request at a time" is a start-gap, and the budget check precedes the wait
