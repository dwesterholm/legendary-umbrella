## Summary

The city e-service is far friendlier to parse than the research note assumed. Both the list page and the detail page are server-rendered ASP.NET pages that embed the complete data as JSON inside a `<script>` block: `var CaseSearchResultsViewModel = {...};` on the list page and `const caseViewModel = JSON.parse("...");` on the detail page. There is no table to scrape and no second request for page 2: the "50 per page" is a client-side display setting, and every result (53, 97 and 380 rows seen) arrives in the first response. That cuts the sweep from "a few hundred GETs" (D-05) to roughly 60 to 120 GETs, and it makes cheerio a thin helper rather than the parser. `cheerio` 1.2.0 and `undici` 7.27.2 are installed. The project has no general HTTP wrapper; the pattern to copy is `src/lib/discovery/osm-overpass.ts` (injected `fetch`/`sleep`/`now`/`log`, fixed host list, honest User-Agent constant, `redirect: "error"`, size and shape checks, labels instead of message text in logs) plus `json-store.ts` for atomic writes.

Ten polite GETs (all 200, cookie-less, 0.1 to 9 s each, no login wall, no terms text, no 403/429) produced eight real fixtures plus four Min Karta fixtures from the sibling repo's saved snapshots. Two findings change the plan. (1) **The city record of stambyten is thin after 2011.** The Södermalm sweep for "stambyte" since 1985 returned 380 cases in 347 buildings, but only about 3 per year from 2018 on, against about 20 per year in the peak years 1994 to 1996 and 2001 to 2006. Joined offline by address to the 2 371 Södermalm sold rows, 488 rows (20.6 %) sit in a building with any recorded stambyte, and of those only 3 are 0 to 5 years before the sale and 38 are 5 to 15 years before. D-06's first two buckets are therefore nearly empty; the measurable contrast is "recorded 16 to 40 years ago" against "no record". The likely result of the CV rule is "not kept". The phase should be planned so that this is a valid, clearly reported outcome. (2) **The model schema is closed to new features.** `hedonicModelSchema` demands each name in `HEDONIC_FEATURES` exactly once and `version` is the literal 2, so adding names there would make every existing model file unreadable. A separate, optional post-stage (like the balcony and build-year stage, but as its own object) keeps old files valid and leaves 14.5's frozen regions alone.

**Primary recommendation:** Build `src/lib/stockholm/` as pure parsers over the embedded JSON (tested on the saved fixtures) plus a thin gated, cached, injected-fetch client; resolve beteckning by (a) broker regex, (a2) a "BRF name looks like kvarter + number" guess that the city list verifies, (b) the city's address fragment, (c) Min Karta last; run the stambyte sweep as about 100 GETs and join sold rows first by free address match, then by rung (b) only for the plausible remainder; and add the stambyte term as an optional post-stage that is kept only if 5-fold CV improves.

## 2. The e-service page shapes (Question 1)

### 2.1 List page (`/byggochplantjansten/arendeochhandlingar`)
- Server-rendered. React islands are `<div data-react data-type='...' data-props='{...}'>`; the visible list is one of them, but **do not parse those**. The authoritative data is the inline script:

```html

    var CaseSearchResultsViewModel = {"BuildCases":{"CaseSearchDetails":[{"RecNo":"1266358","CaseTypeCode":"Byggärende","ObjectType":null,"Description":"…","StartDate":"2023-10-05T00:00:00","RealEstateName":"Droskhästen 8","RealEstateAddress":"Folkungagatan 61","Name":"2023-15008","IsEarchive":false}, …],"Pagination":{"ItemsPerPage":50,"CurrentPage":1},"Header":"Byggärenden","SubHeader":"…","ListId":"buildCases"},"RealEstateCases":{…},"OtherCases":{…},"HasSearched":true};
</script>
```
[VERIFIED: fixtures `list-droskhasten-8`, `ext-*`; keys quoted from the saved page]
- Row keys: `RecNo`, `CaseTypeCode`, `ObjectType`, `Description`, `StartDate`, `RealEstateName`, `RealEstateAddress`, `Name` (= the diarienummer), `IsEarchive`. `BuildCases` holds "Byggärende" rows; `OtherCases` holds "Funktionskontroll, Tillstånd" rows (OVK ventilation inspections, lift orders); `RealEstateCases` holds Lantmäteri cases. Only `BuildCases` matter; OtherCases are kept at most for hiss.
- `RealEstateAddress` can be empty (seen: "Svärdet 9" row) or several addresses joined by `,` (seen: `Brännkyrkagatan 64,Ludvigsbergsgatan 1,Gamla Lundagatan 1`). In the Droskhästen list some rows carry `Folkungagatan 61\, Östgötagatan 33` in the visible React props; split on both `,` and `\,` and trim.
- `RealEstateName` was a single beteckning in all 380 + 53 + 27 rows checked.
- The detail link is built from `RecNo`: `/Byggochplantjansten/arende/arende/<RecNo>?dataSource=Active` when `IsEarchive` is false, `...Archived` when true [VERIFIED: the "Visa" hrefs in the saved list page and the `IsEarchive` flag on the same rows]. ### 5.5 Time alignment (a trap in the fit)
`yearsSinceStambyte` for a sold flat must be counted from the **sale date**, not from today. A case that started after the sale is "future at sale" and must not be coded as a past stambyte. Use start year as the year for list-only cases (archived cases have no usable end date); the proposed bucket edges are wide enough to absorb a 0 to 3 year lag.

Year assignment: per clause, take the year **nearest the stambyte keyword** (up to 25 characters before it or 40 after, ties go to the later one), so "Nytt kök och badrum 2021, stambyte 2018." gives 2018 and "Stambyte genomfört 2018. Nytt kök och badrum 2021." gives 2018 through the clause split; years outside 1950 to 2045 and decades ("på 1980-talet": the year pattern has `(?!\d|-?talet)`) are ignored. A completed stambyte keeps the latest year ≤ run year; a year above the run year, or a clause with a plan word (`planer…|beslutad|kommande|förestående|projekter…|genomförs|påbörjas|startar|beräknas|väntas`), sets `plannedStambyteYear` (earliest future year); an ongoing word (`pågår|pågående|påbörjad|pågick|i full gång|just nu`) sets `stambyteOngoing`; a negation before or after the keyword (`inget|ingen|ej|inte|icke|ännu inte|aldrig`, or "stambyte … ej genomfört/planerat") discards the clause. Relining words (`relining|relinad…|rörrenovering|rörlining`) set `reliningMentioned` only and never a stambyte year.

Keyword: `W(?:va-?)?(?:stambyt(?:e|et|en|ena)?|stambytt\p{L}{0,2}|stambyta|stamrenover\p{L}{1,8})E` | `W(?:stammarna|stammar|avloppsstammar\p{L}{0,3}|vattenstammar\p{L}{0,3})\s{1,3}(?:\p{L}{1,12}\s{1,3}){0,2}?(?:byt(?:ts|tes|s|es)|bytta|utbyt\p{L}{0,4}|renoverad\p{L}{0,3}|renoverades|förnyad\p{L}{0,3}|förnyades)E`.

33 synthetic phrases, all pass (circular, tuned): "Stambyte genomfört 2018. Nytt kök och badrum 2021." → last 2018; "Föreningen har genomfört stambyte 2019." → 2019; "Stambytet utfördes 2015."; "Stambytt 2005."; "2017 genomfördes ett stambyte i huset."; "Stammarna byttes 2016."; "Stambyte är genomfört (2011)."; "Nytt kök och badrum 2021, stambyte 2018." → 2018; "I samband med stambytet 2018 renoverades badrummet." → 2018; "Stambyte och badrumsrenovering gjordes 2019."; "Stambyte genomfört 1991."; "Stambyte planeras 2027." → planned 2027; "Planerat stambyte 2028."; "Föreningen har beslutat om stambyte som startar 2026." → planned 2026; "Stambyte är planerat till 2029."; "Kommande stambyte, år ej fastställt." → nothing; "Stambyte pågår i fastigheten." → ongoing; "Pågående stambyte under 2026." → ongoing; "Inget stambyte är planerat." → nothing; "Stambyte ej genomfört." → nothing; "Stambyte har ännu inte gjorts." → nothing; "Avloppsstammar relinade 2017." → relining only; "Relining genomfört 2015." → relining only; "Stambyte genomfört 2012 samt relining av stammar i källaren 2020." → last 2012 + relining; "Nytt badrum 2021 och nytt kök 2019." → nothing; "VA-stambyte klart 2014."; "Stamrenovering utförd 2010."; "Stambyte på 1980-talet." → nothing; "Föreningen har ett stambyte i sin underhållsplan för 2035." → planned 2035; "Stambyte 2024."; "Stambyte 2031 enligt underhållsplanen." → planned 2031; "Stambytet slutfördes under 2022."; empty → all null. ### 9.3 Pattern: parse the embedded JSON, fail loudly on shape change
```ts
// Source: verified against the saved fixtures (this session); cheerio 1.2.0
import * as cheerio from "cheerio";
const LIST_MARK = "var CaseSearchResultsViewModel =";

export function listViewModel(html: string): unknown | null {
  const $ = cheerio.load(html);
  for (const el of $("script").toArray()) {
    const t = $(el).text();
    const i = t.indexOf(LIST_MARK);
    if (i < 0) continue;
    const rest = t.slice(i + LIST_MARK.length);
    return JSON.parse(rest.slice(0, rest.lastIndexOf(";")));
  }
  return null; // the page changed or is not a result page
}

export function detailViewModel(html: string): unknown | null {
  const $ = cheerio.load(html);
  for (const el of $("script").toArray()) {
    const m = $(el).text().match(/const caseViewModel =\s*JSON\.parse\(("(?:[^"\\]|\\.)*")\)/);
    if (m) return JSON.parse(JSON.parse(m[1])); // a JSON string literal holding JSON
  }
```

### 9.5 Anti-patterns to avoid
- Parsing the visible `data-props` list or the `<table`-less markup: the embedded JSON is the contract and has full rows.
- Sending `SearchParameters.`-prefixed query names (returns the empty form).
- Following hrefs from the page; sending the session cookie back; persisting `Handler`, `Documents`, or free-text `Description`.
- Adding names to `HEDONIC_FEATURES`; changing the model `version`.
- Treating "no city record" as "no stambyte".
- Counting `Description` hits for "balkong" as new balconies without the `tillsyn` and `renovering` filters.

## Common Pitfalls (Question 9)

1. **zod strips unknown keys on load.** `candidateFactsSchema`, `hedonicModelSchema` and every cache schema use plain `z.object`. A field that exists in the file but not in the schema vanishes silently on the next read-and-rewrite. Mitigations: every new facts field `.nullable().default(null)` and a round-trip test per field; every cache file has `schemaVersion` and `rulesVersion`; on a parse failure treat the cache entry as a miss (refetch within the run's request budget), never crash and never re-fetch everything at once (cap misses per run). For the e-service JSON use a schema that lists only the fields read, plus a test that fails when a *required* field disappears, so a shape change is a clean `shape` failure.
2. **One rate gate for all hosts.** A single global spacing would slow Booli's local browser pacing or let city and Min Karta requests bunch. Keep one gate and one `host-gates.json` entry per host. The Booli gate (`booli-gate.mjs` + `booli-traffic-14.5.log`) is a separate, closed-until-2026-10-19T14:57Z mechanism; this phase must not read, write or wait on it, and must make no Booli request.
3. **The e-service can change shape or add a challenge.** It is an ASP.NET site with React islands; the embedded view-model names (`CaseSearchResultsViewModel`, `caseViewModel`) are internal. Handle: marker absent → `shape` failure → stop, record in the run report, and fall back to "unknown", not to a guess. Keep the saved fixtures as the contract test.
4. **PII in case pages.** `Handläggare` appears in the `<dd>` **and** in `CaseDetails.Handler` of the embedded JSON; `Documents[].Title` can name people or the control officer. The parser must never copy them into any object that is cached or logged. A unit test feeds the unredacted shape (synthetic name) and asserts the name appears nowhere in the parser's output or in a serialised cache entry. Free-text ärendemening is not stored (4.3).
5. **Do not touch 14.5.** Plans 06 to 09, 12 and 13 are pending. Not allowed: `layout-*`, stage-2 code in `hedonic-model.ts` (`fitStage2`, `stage2CvRmse`, the stage-2 schema block, the balcony and build-year multipliers), `evidence/`, `truth/`. `fit-score.ts` and `scripts/fit-score.ts` are edited by 14.5 plan 12; 14.6's edits to them go strictly before or after it. Check `git diff --stat <phase-start>..HEAD` on those paths at every wave end and run `frozen-check.mjs` before editing `hedonic-model.ts` and again after. **Do not overwrite the committed `data/hedonic-model.json` during this phase's fits**: 14.5 plan 12 replays snapshots against it and compares the result with a stored record (`replay-14.5-committed.json`), and plan 13 reports on it, so a model file that suddenly carries a kept stambyte term would break their equality checks. Write every 14.6 fit to a scratch file under `.planning/calibration/data/` (`--out`), and swap the committed model only as the very last step, after 14.5 plans 12 and 13 have run (or with Daniel's agreement to re-record their baselines).
6. **Monday window.** The weekly job starts Monday 07:00 and `booli-gate.mjs` treats 06:30 to 09:30 local as occupied. D-01 says the city cache is "never refreshed during" that window. Read literally this also forbids the weekly job's own candidate lookups (which run inside the window). See Open Questions, item 1.
7. **Search is fuzzy; the exact-match filter is mandatory.** Also the address fragment is a prefix match ("Hornsgatan 4" would return 40, 42, 44…): accept only on the equal-address rule of 2.4.
8. **Entrance letters and corner blocks.** Min Karta wants `Torsgatan 48A` closed up; the city fragment returns `…42A` and `…42B` for `…42`. A building can have addresses on two streets (Droskhästen 8: Folkungagatan 61 and Östgötagatan 33), so an address-only join under-counts.
9. **Time alignment and leakage in the fit** (5.5): count years from the sale date; do not code a case that started after the sale as a past stambyte.
10. **Double counting.** A loan-financed stambyte already shows up in `brfDebtPerSqm` and `avgiftPerSqmMonth`; report the correlation (D-06) and keep the term only on CV. Folklore figures are printed beside, never used.
11. **Absence is not "no".** No case record means unknown. The cell says `okänd`, the model gives 0 for it, the reason line stays silent.
12. **Sequencing with the Booli gate.** The area-source live check needs a run that reads broker pages; that is 14.5 plan 13 or the next Monday job, after 2026-10-19T14:57Z. The phase's exit (D-14) therefore waits for that run; plan so that every other deliverable can finish without it.
13. **Mail column order.** `COLUMNS` and `plainCells` are index-coupled; the Booli link must stay last.
14. **Pinned header string.** `FIT_TABLE_HEADER` has a test; changing the columns means changing the string and the test in the same commit.

### Beteckning normalisation and the equal-address rule (design sketch)
```ts
export function normaliseBeteckning(raw: string): string {
  return raw.replace(/^stockholm\s+/i, "").replace(/\s+/g, " ").trim(); // "Stockholm Oljan 29" -> "Oljan 29"
}
const addrKey = (s: string) => s.toLowerCase().replace(/\s+/g, " ").replace(/(\d)\s+([a-zåäö])$/, "$1$2").trim();

/** options: [{text:"Ormen Mindre 2, Hornsgatan 42B", value:"Ormen Mindre 2"}, …] */
export function pickFromAddressFragment(asked: string, options: { text: string; value: string }[]): string | null {
  const key = addrKey(asked);
  const hasLetter = /\d[a-zåäö]$/.test(key);
  const matching = options.filter((o) => {
    const addr = addrKey(o.text.slice(o.text.indexOf(",") + 1));
    return addr === key || (!hasLetter && addr.replace(/(\d)[a-zåäö]$/, "$1") === key);
  });
  const values = new Set(matching.map((o) => o.value));
  return values.size === 1 ? [...values][0] : null; // none or ambiguous -> next rung
}
```
(`Hornsgatan 42` → both options share `Ormen Mindre 2` → resolved; `Hornsgatan 4` → no equal address → null.)

### Weekly-window guard for manual tools
```ts
export function inWeeklyWindow(d: Date): boolean { // Monday 06:30-09:30 local, as booli-gate.mjs
  if (d.getDay() !== 1) return false;
  const m = d.getHours() * 60 + d.getMinutes();
  return m >= 6 * 60 + 30 && m < 9 * 60 + 30;
}
```

## Security Domain

`security_enforcement` is not set to false in `.planning/config.json`, so this section applies.

### Applicable ASVS Categories
| ASVS Category | Applies | Standard Control |
|---------------|---------|------------------|
| V2 Authentication | no | no login is used or attempted; a login wall is a stop condition |
| V3 Session Management | no | the site's session cookie is neither stored nor sent |
| V4 Access Control | no | local scripts |
| V5 Input Validation | yes | zod on the embedded JSON, caches and join file; bounded regex quantifiers; 50 000-character cap on broker text; digits-only `RecNo` in built URLs |
| V6 Cryptography | no | none (a hash may name cache files) |
| V8 Data Protection | yes | drop `Handler`, `Documents`, free-text `Description`; broker text read in memory and dropped; cache holds derived values only |
| V12 Files / SSRF | yes | fixed host list in code, `redirect: "error"`, no URL taken from page content, writes only via `guardedDataPath` under `.planning/calibration/data/` or `.planning/phases/` |
| Secrets | yes | no keys needed; never log cookies, headers or query strings |

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| SSRF via an `href` in a fetched page | Tampering | build detail URLs from the fixed host and a digit-only `RecNo`; reject anything else |
| Path traversal through a beteckning used as a file name | Tampering | file names are a hash or a slug of `[a-z0-9-]`, never the raw string; `guardedDataPath` |
| ReDoS on long broker text | Denial of service | bounded quantifiers, cap, clause split; timing test with pathological input |
| Cache poisoning (hand-edited or stale cache) | Tampering | zod on load, version fields, miss on failure |
| Personal data in case pages | Information disclosure | see V8; a test with a synthetic officer name |
| Hammering a public service | Denial of service (of them) | 3 s spacing per host, one attempt, 24 h stop, request budgets per run, Monday-window guard for manual tools |
| HTML injection into the mail | Tampering | `escapeHtml` is applied per cell in `htmlRow`; new cells go through `plainCells` and get the same treatment; add a test with `<script>` in a case-derived string |
