<domain>
The fit score ranks for-sale flats by expected flip profit: resale from a hedonic kr/m² model
(6 features: neighbourhood level, floor, ground floor, ln area, months ago, centrality km; stage 2
balcony + build-year buckets; a per-district bid premium) minus expected final price minus reno
cost, plus a taste bonus capped at 5 % of resale. Today the credit (resale − expected final) is
capped at 20 % of resale (`MAX_CREDIT_PCT`), which hid the reason a flat is cheap. 14.2 bolted a
"varför här" reason on top (avgift/kvm, BRF debt/kvm, tenure, days on market …). Daniel rejects the
cap: those things belong IN the valuation. Separately, photos today only set reno cost and (via
14.3) the facade; they say nothing about which rooms face the street, whether the flat has windows
on two sides (korsdrag), or where the bedroom is — things Daniel cares about and buyers pay for.
And the expected final price ignores that bidders see the same dated kitchen the model does.

What exists: sold cache `.planning/calibration/data/slutpriser-cache.json` (7 431 rows, 5 746 sold
from 2025-10-01 on; 35 rows already `enriched` with buildYear/balcony/listPrice through
`pull-slutpriser.ts --enrich-sample`, which renders the sold-detail page via the free local rung,
checkpoints after every row and resumes). Sold-detail pages carry the same reshaped listing entity
as for-sale pages (`rent`, `constructionYear`, `tenureForm`, `published`, breadcrumbs → `brfId`).
BRF debt/kvm comes from `fetchBrfFacts(brfId)` (Booli public BRF page; 72 of 77 candidates in 14.2).
Live candidates already carry avgift, build year, tenure, published date, BRF id and (14.2) BRF
debt in `CandidateFacts`, so every new model feature has a prediction-time source.
</domain>

<decisions>

### Part 1 — the valuation covers the gaps (replaces the 20 % cap)
- **D-01 (features, VAL-02):** add to the hedonic model `avgiftPerSqmMonth` (kr/m²/month), `brfDebtPerSqm` (kr/m²) and `tomtratt` (0/1). Same honesty rule as the six existing features: a null is marginalised at the training mean and named in `imputed`; the table shows it. Build year already has its stage-2 buckets; it is enriched because it is free on the same page, not as a new feature. Ridge, CV and the sanity thresholds stay the library's; nothing is tuned to a listing; Folkungagatan 61 stays out of the training set. Bump the model file `version` so a pre-14.4 file is rejected by `parseHedonicModel`, never mis-read.
- **D-02 (listing age, VAL-03):** listing age is NOT a resale feature (a long listing is a consequence of the asking price, not a property of the flat). It enters the expected final price: `bidPremium` gains a days-on-market term (publish date → sold date on the enriched rows; candidate `published` → run date at prediction). Kept only if 5-fold CV error drops (the same rule `fitBidPremium` already uses for flat vs slope); otherwise recorded as "prövad, förkastad" in the model note.
- **D-03 (enrichment, VAL-01):** extend the `enriched` record with `rentSek`, `brfId`, `tenureForm`, `published` (ISO date) — read from the SAME sold-detail render the current `--enrich-sample` does, through the free local rung (`--renderer local`, no `--allow-apify`, 0 USD). Rows already enriched under the old shape are re-read (they lack the new fields). Only sales from 2025-10-01 on (older pages lack the data; say so in the report: tenure/avgift coverage is partial, ≈ 5 700 of 7 400). Second pass: one BRF page per distinct `brfId` (`fetchBrfFacts`), stored in a `brf` map in the cache (`brfId → {loanSek, areaSqm, reportYear, debtPerSqm, readAt}`), resumable the same way.
- **D-04 (how much to read, and when to stop):** this is ≈ 5 700 detail pages + ≈ 1 500 BRF pages at ≈ 5 s each on the local rung — hours, and 70× more traffic than any run so far. So: (1) first a deterministic stratified sample (district × size band, the existing `sampleUnenriched` ordering) of 1 200 sales + their BRFs, run in the background with a log; (2) refit and look at the standard errors of the three new coefficients; (3) extend to the rest only if the sample's failure rate is < 5 % and no challenge page was seen, in batches of ≤ 1 500 with the run log recording failures per batch; stop and report at the first sign of blocking (challenge detected or ≥ 5 % failures in a batch). Politeness: ≤ 2 concurrent (the local rung already enforces this), ≥ 1 s between page starts, no retries beyond the existing one. Daniel's Mac must be awake: run under `caffeinate -i` like the weekly job.
- **D-05 (the cap goes, VAL-04):** `creditSek = gapSek`; delete `MAX_CREDIT_PCT`, the `creditCapped` flag and the `kredit-tak` reason. Add `residualFlag` ("ovanligt långt under modellpris"): asking kr/m² < model kr/m² × exp(−2 × `residualSdLog`), i.e. further below the model than ≈ 97.5 % of training rows. It is a flag with a reason line (the uncapped gap, the residual in %, what the features already explain), never a cap. `notComparable` (ask/pred < 0.5) stays. `watch-reasons.ts` keeps producing the "varför här" line for `residualFlag` and `dold-defekt-risk` rows; the avgift/BRF/tenure reasons now say "redan i värderingen" instead of explaining a cap.
- **D-06 (the report, VAL-05):** offline on the current snapshot (`forsale-snapshot-2026-10-13.json`, replay path): for every row that carried `kredit-tak` — old credit, new credit, kr explained by avgift / BRF debt / tomträtt (feature × beta × area, in kr), residual, new flag; top-15 before/after side by side; Folkungagatan 61 rank + decomposition before/after. Written to the phase `evidence/` directory and summarised in SUMMARY for Daniel in plain words. Measured, not tuned: if the top 15 looks wrong, that is a finding, not a knob.

### Part 2 — layout & livability from the floor plan + photos
- **D-07 (one separate slim call, LAY-01):** a new module `layout-read.ts` with its OWN schema, prompt version, cache file (`.planning/calibration/data/layout-cache.json`, gitignored, keyed by listing key + image-set key + version) and cumulative spend cap, exactly as `sun-floorplan.ts` did — the existing vision schema/prompt/cache are NEVER touched (one field there re-keys 77 cached reads and re-bills ≈ 33 kr). Inputs: the floor plan (same detection as 14.3: white-background plan, typically first or last) plus up to 6 photos. Model: the Sonnet deep-pass tier (reading a plan is the hard part; the roadmap's ≈ 0,5 kr assumes it); cap 0,6 kr per flat estimated before the call, ≤ 40 kr cumulative per run tracked in the cache file, 0 USD Apify.
- **D-08 (schema, strict-output safe):** flat fields, no nullable, no union of objects, no numeric constraints (memory `anthropic-structured-output-limits`): `balconySide` enum street/courtyard/none/unknown; `livingOnBalconySide`, `kitchenOnBalconySide`, `bedroomOnBalconySide` booleans; `windowSides` enum one/twoOpposite/corner/unknown; `bedroomSide` enum street/courtyard/unknown; `streetEvidence` enum cars/oppositeFacade/courtyardGreenery/none (what in the PHOTOS settled street vs courtyard; the plan alone cannot); `confidence` number 0–1. Prompt in Swedish, never asks for a compass or bearing (dead route, 14.3 R-01), never asks about people. Unit tests assert the shape; one live smoke (`RUN_LLM_EVALS=1`) proves the grammar compiles.
- **D-09 (combine with 14.3, LAY-02):** `balconySide = street` + confidence ≥ 0,6 → the sun part uses the STREET facade's hours; `courtyard` → the courtyard facade's; both come from 14.3's `sun-facade`/`sun-hours` for the same flat. Where that holds, `streetOnlyFactor` becomes 1 (we now know which side the living space is on); where the layout is unknown or confidence < 0,6, everything stays as 14.3 left it (0.5). Stated text keeps precedence 1.0. New `sourceLabel` value "planritning+foto" in the Sol column.
- **D-10 (taste terms and flags, LAY-03):** `TASTE_WEIGHTS` gains `korsdragPct: 0.01` (windowSides = twoOpposite) and `quietBedroomPct: 0.01` (bedroomSide = courtyard); the 5 % total cap (`TASTE_CAP_PCT`) is unchanged and binds. Unknown adds 0. Table + mail gain two columns: "Korsdrag" (ja/nej/okänd) and "Sovrum" (gata/gård/okänd), plus the balcony side in the Sol column. The market value of korsdrag/quiet bedroom is NOT modelled (no layout data on sold flats); say so in SUMMARY.
- **D-11 (calibration, LAY-04):** Folkungagatan 61 truth: balcony + living + glass-walled bedroom on the south street side, no courtyard windows → `balconySide = street`, `windowSides = one`, `bedroomSide = street` (sun yes, korsdrag no, bedroom on Folkungagatan). A replay fixture asserts this; one real local run records coverage per field over the current candidates and the agreement rate between `streetEvidence`-settled sides and 14.3's footprint street facade.

### Part 3 — condition-aware bidding
- **D-12 (fit, BID-01):** probe first whether sold-detail pages (2025-10+) still show the broker photos. If yes: a slim Haiku condition read (`sold-condition.ts`, own cache, schema = one enum dated/ok/fresh + one confidence, ≤ 0,1 kr/flat) on a stratified sample of ≈ 300 enriched rows that have an asking price; `fitBidPremium` gains a term `c × conditionIndex` (dated −1, ok/unknown 0, fresh +1); kept only if CV error drops. If the pages carry no photos, or CV rejects it: a documented prior (`source: "prior"`, dated −2 pp, fresh +2 pp — the research must cite where the numbers come from, or lower them) and the model note says which. Spend ≤ 30 kr, 0 USD Apify.
- **D-13 (use, BID-02):** `expectedOverbid` takes the candidate's existing deep-pass verdict (`reno.anyDated` → −1; all three fresh → +1; else 0) — no new call. The table prints the premium used and its source. Before/after on the snapshot goes into the D-06 report.
