## Summary

The phase is mostly wiring, and the wiring is well-trodden: every new feature has a prediction-time source already in `CandidateFacts`, the sold-detail page carries almost everything Part 1 needs, and `sun-floorplan.ts` is a complete template for the layout call. The research found nine places where CONTEXT's premises do not match the code or the data. The planner must plan around these, not around the CONTEXT wording:

1. **There is no `published` field on a sold-detail page.** Days on market is printed directly: info point `daysActive`, text "Bostaden var till salu i **6** dagar", present on 3 of 3 probe pages. Store `daysActive` (integer), not a publish date.
2. **Tomträtt cannot be estimated from sold data.** `tenureForm` is "Bostadsrätt" on every sold page seen, the BRF page has no tomträtt label, and the repo's own `tomtrattFromTenureForm` documents that the field structurally cannot disprove tomträtt. The feature column will have zero spread, so it ends up as an honest `absent` fallback with beta 0. The reasons module must NOT claim tomträtt is "redan i värderingen".
3. **`--enrich-sample` is capped at 300 in the script** (`intArg("--enrich-sample", 0, 0, 300)`), and `enrichSoldRows`/`selectEnrichmentSample` skip any row that already has `enriched`, so old-shape rows would never be re-read. Both need changing.
4. **The cache schema silently drops unknown keys.** `soldRowSchema.enriched` is a plain `z.object`; a new field not in the schema is stripped on load and lost on the next checkpoint. Extend the schema first.
5. **The locked `residualFlag` rule fires on 30 of 77 current rows (39 %)** and is a strict subset of the existing `hiddenDefectRisk` (41 rows). Measured with the committed model: threshold `exp(-2 × 0.115) = 0.794`; median ask/model is 0.82. The "97.5 % of training rows" sentence compares asking price to a model fitted on SOLD prices; a like-for-like test (expected final price vs model) fires on 7 of 77. Implement the locked rule, print both counts, and let Daniel decide.
6. **Candidates carry at most 4 Booli images** (`CAP_IMAGES_PER_LISTING = 4`, plan first for 69 of 77), plus up to 4 broker photos as in-memory bytes. "Plan + up to 6 photos" means 3 Booli photos + 3 broker photos, and the broker bytes exist only during a live run.
7. **`SOLD_DETAIL_PAGE_FUNCTION` has only ever run on Apify (14.1).** The local rung has never rendered a sold-detail page. A 5-row smoke must come before the 1 200-row run.
8. **Removing the cap adds 6.55 M kr of credit across the 77 rows (5.29 M in today's top 15).** Rank order will be dominated by the size of the discount to the model until the new features explain part of it. That is the point of VAL-05, and it should be said to Daniel in those words.
9. **The refit will also switch on stage 2 (balcony from data, build-year buckets)** once ~1 200 rows carry both fields. That moves predictions for reasons unrelated to the three new features. The VAL-05 decomposition must separate "avgift", "BRF-skuld", "tomträtt", and "övrigt (balkong, byggår, ny anpassning)".

**Primary recommendation:** Do Part 1 in this order: freeze the "before" results, extend schema and parser, smoke 5 rows on the local rung, run the 1 200-row stratified sample plus its BRF pages under `caffeinate`, refit, then remove the cap and write the report. Build Part 2 as a copy of the `sun-floorplan.ts` pattern with a deterministic "evidence gate" (street/courtyard only counts when `streetEvidence` is not `none` and confidence >= 0.6). Decide Part 3's branch from `imageIds` recorded for free during Part 1.

### Q3. `hedonic-model.ts` seams

Going from 1 200 to 5 700 rows cuts the SE from 0.0036 to 0.0016 but changes no decision unless the effect is below about 0.007. **Recommendation: the 1 200-row sample suffices to estimate and report the three coefficients; extend to the full set only if a coefficient lands within 2 SE of zero, or if the stage-2 build-year buckets are still thin** (the stage-2 gate `STAGE2_MIN_PER_BUCKET = 20` per bucket; in the 35-row sample 25 of 32 were pre-1931, so 1 200 rows should clear it for the three newer buckets, but check the printed per-bucket counts).

Clustering: flats in one BRF share the debt figure, so the effective n for the debt coefficient is nearer the distinct-BRF count. At 1 200 sales over roughly 900 BRFs the design effect is small (1 + (m−1)ρ with m ≈ 1.3 and ρ unknown, about 1.1 if ρ = 0.3) [ASSUMED]; at 5 700 sales it grows to about 1.3. Report distinct BRFs next to n.

Also report in `fit-hedonic.ts` output: each new coefficient with SE and t, the percent effect per 10 kr/m²/month and per 1 000 kr/m² (decimal comma, as `describeModel` does), `r2` and `cvRmseLog` before and after, the correlation matrix of the three new features and the VIF of each against the others, row counts per feature, and which fallbacks fired.

Power for the condition term (BID-01): residual sd of z (the bid premium in ln) is about 0.074 (CV RMSE of the slope model). With 300 sampled rows, about 220 carrying an ask label and a confident read, and a condition index with sd about 0.6 [ASSUMED], SE ≈ 0.074 / (0.6 × sqrt(220)) = 0.0083, so a ±2 pp effect has t ≈ 2.4 and a ±1 pp effect cannot be detected. A rejection by CV therefore means "effect below about 2 pp or none", not "no effect". Say that in the model note.

### Q10. Prior for BID-01 if the fit fails

Searched Swedish and international sources (2 searches, this session). **No public Swedish study or statistic was found that compares bid premium (slutpris over utgångspris) for dated versus renovated flats.** What exists:
- Descriptive bid-premium figures only: Hemnet Stockholm +4.8 % in March 2026 (highest since 2022); Booli national average 1.9 % for April 2026. Neither controls for condition. [CITED: search results quoting Hemnet/Booli statistics; sources below]
- A Norwegian hedonic preprint on listing text finds a renovation PRICE premium of 5 to 7 % and a discount of 9 to 10 % for neglected dwellings. That is a price level, not a bid premium, and it is not Swedish; it bounds how large a condition effect can plausibly be, nothing more. [CITED: Research Square preprint rs-1401776, via search summary; not peer-reviewed]
- A forum post claiming renovation objects sell 20 to 25 % over asking, unsourced; discard.

Verdict: **the ±2 pp prior in D-12 and BID-01 has no citable source.** It is [ASSUMED]. Two honest options for the planner: (a) keep ±2 pp but label it in the model file and the table as "antagen (ingen källa funnen)", or (b) set the prior to 0 and print "ingen skillnad modellerad". The requirement text asks for a documented prior with source "prior"; pick (a) with the explicit label unless Daniel prefers 0, and surface it as a decision. If the fit branch works, this question disappears.

- **Using the street/courtyard value without the evidence gate:** the model failed the door-arrow trap in 14.3.
- **Describing tomträtt as "redan i värderingen":** it is not, and the reasons text would be false.
- **Recomputing "before" after the change:** impossible without the old code.
- **Running the weekly job and the enrichment at the same time:** same browser, same site, 2-page budget.

## Common Pitfalls

### Pitfall 1: New fields vanish because the schema does not know them
**What goes wrong:** the run enriches 600 rows, the file is reloaded, `rentSek` is gone. **Why:** `z.object` strips unknown keys on parse and `persist` writes the parsed value. **Avoid:** schema first, a test that round-trips a row through `slutprisCacheSchema.parse` + `JSON.stringify` and keeps every new key. **Warning sign:** `rentShare` in the batch log is 100 % and `fit-hedonic` sees 0.

### Pitfall 2: Old-shape rows are never re-read
**What goes wrong:** the 35 rows keep no avgift. **Why:** both the selector and the loop skip any truthy `enriched`. **Avoid:** `needsEnrichment` on `detailVersion`.

### Pitfall 3: `published` does not exist
**What goes wrong:** the parser returns null for every row and the DOM term has no data. **Avoid:** parse the `daysActive` info point (`/\*\*(\d+)\*\*\s*dag/`), tolerate singular "dag", store null when absent. Candidates keep using `facts.daysOnMarket`.

### Pitfall 4: A dead page loops forever
**What goes wrong:** failed rows are re-picked first on every re-run. **Avoid:** failure ledger in the cache; skip rows with 2 attempts; report them.

### Pitfall 5: Tomträtt column has no data and the text claims it does
**What goes wrong:** the model file lists tomträtt with SE 0.115 "osäker uppskattning" and the reasons say "redan i värderingen". **Avoid:** explicit `absent` fallback; `ReasonContext` gets `coveredByModel: {avgift, brfDebt, tomtratt}` taken from the model's feature sources, and the "redan i värderingen" suffix is added only for covered features.

### Pitfall 6: The refit moves predictions for reasons other than the three features
**What goes wrong:** stage 2 flips from "prior" (balcony +1.9 %, no build-year) to a fit once ≥ 20 rows per bucket exist, so every flat with a balcony or an old building moves. **Avoid:** decompose the report into avgift, BRF-skuld, tomträtt and "övrigt"; print the stage-2 outcome and per-bucket counts (`fit-hedonic.ts` already prints them).

### Pitfall 7: The guard zeroes a wrong-signed avgift coefficient
**What goes wrong:** high-avgift buildings can price higher in the raw data, `guardVerdict` replaces the coefficient with 0, and the gaps stay unexplained. **Avoid:** nothing to tune (D-01 forbids it); the report states the outcome in words and the unexplained gap is then carried by `residualFlag`.

### Pitfall 8: `residualFlag` as specified is too common to be a flag
30 of 77 rows (39 %) fire; it is a subset of `hiddenDefectRisk`. **Avoid:** print both the locked rule and the like-for-like variant (expected final / model) with counts in the report; surface to Daniel; do not change the locked rule on the planner's own initiative.

### Pitfall 9: "Before" is gone
See Pattern 3.

### Pitfall 10: Layout cache re-bills every week
**Why:** a key that includes volatile bytes. **Avoid:** key = `visionListingKey` + count-form `imageSetKey` + `LAYOUT_READ_VERSION`; assert in a test that two runs with the same inputs make 0 calls.

### Pitfall 11: Photos that Anthropic cannot download
A sold listing's bcdn URL may 404; the API returns an error, the call counts as failed, and nothing is billed. **Avoid:** `FloorPlanCallError`-style handling that records `failed` with the error name; the Part 3 smoke (<= 1 kr) tests 5 real sold image URLs before the 300-row read; if they fail, switch to the prior.

### Pitfall 12: Agreement metric with tiny n
D-11 asks for agreement between photo-settled sides and the footprint street facade. The layout gives street/courtyard, the footprint gives compass bearings; they only meet where the broker STATED a facade (the snapshot has 0 `sun` records and the 14.3 research found about 2 stated facades in 78). **Avoid:** define the metric precisely (stated facade vs facade implied by layout side + footprint), print n, and add two measures that have real n: (a) internal consistency (balconySide = street implies bedroomOnBalconySide and bedroomSide not contradicting), (b) a by-eye check of 12 flats, as 14.3's research did with 69 plans (the executor can open the images with the Read tool).

### Pitfall 13: Sold-detail page function never ran locally
A 5-row smoke first; check `hasApollo`, the parse of all new fields, seconds per page and `imageIds` share. The local rung navigates with `waitUntil: "domcontentloaded"` and the flight text streams; the rung's 1.5 s re-extract helps if `hasApollo` is false [ASSUMED sufficient].

### Pitfall 14: BRF debt year mismatch
The BRF page prints the latest report (2023 to 2025 in the snapshot), not the figure at the sale date. State it in the model note; do not try to correct.

### Pitfall 15: Candidate DOM is "so far"
See Q5. Document, do not fix.

### Pitfall 16: Daniel's Mac sleeps or Colima is down
Colima is irrelevant here (no Docker), but a sleeping Mac stalls the run and the E2E runner. `caffeinate -i -w $$`.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| SSRF through a listing-supplied image URL | Spoofing/Info disclosure | `isAllowedImageHost` before any URL reaches Anthropic; sold image URLs are built from digit-only ids on the fixed bcdn.se host |
| Prompt injection via text inside a photo or floor plan | Tampering | Output is a strict enum/boolean/number schema; no free text field exists, so nothing the image says can reach a downstream prompt or a table cell |
| Denial of wallet | DoS | Estimate before each call, per-run cap, billed-failure accounting, `RUN_LLM_EVALS=1` gate for smokes, 0 USD Apify (no `--allow-apify`) |
| Secret leakage in logs | Info disclosure | print `satt`/`saknas` only; errors log names, not messages or URLs (as in `sun-floorplan.ts`) |
| Path traversal in `--out`/cache args | Tampering | `guardedDataPath`, existing `resolveOutPath` checks |
| Scraping etiquette and blocking | n/a | ≤ 2 concurrent, ≥ 1 s between starts, stop at first challenge, no Apify fallback |
| Persisting broker photos (GDPR) | Info disclosure | bytes stay in memory; cache holds enums and ids only |
