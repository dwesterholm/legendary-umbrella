# Phase 14.4 Plan 07: Layout read, balcony side picks the sun facade, live grammar smoke Summary

**A separate, cached picture read of the floor plan and photos (balcony side, window sides, bedroom side) behind a plain-code confidence gate, wired so a usable balcony side picks the street or courtyard facade for the sun; the strict-output schema compiled against the live API for 0,11 kr.**

## Accomplishments

- A flat whose layout says "balcony on the street side" now gets the street facade's sun at full weight. 14.3 counted the better of street and courtyard at half weight; with a usable layout the sun part of taste exactly doubles for the Folkungagatan 61 test row, and the Sol cell reads `S gata (planritning+foto, 1,00), balkong gata`. Everything without a usable layout, a stated facade or an unknown sun is exactly as 14.3 left it (the 47-row fixture still prints `S gata/N gård (fastighet/gata, 1,00)`).
- The layout read is its own module with its own schema, prompt, version hash and cache file. The vision schema, prompts and cache (and `sun-fact.ts`, `niche-score.ts`, `report/flags.ts`, `candidate.ts`, `taste.ts`) are untouched, so the 77 cached vision reads and their roughly 33 kr stay valid.
- The live smoke proved the part unit tests cannot: the eight-field strict-output schema is accepted by the API (no HTTP 400). Two reads cost 0,11 kr in total, well under the 1 kr cap.

## Smoke result

**Did the strict schema compile?** Yes. Two live calls, no HTTP 400, `grammar: "ok"`, 0,1114 kr spent (cache ledger total the same, this was the first run). The ungated run prints the skip line and makes no call.

**Folkungagatan 61, live read versus the truth (D-11: balcony street, windows one side, bedroom street):**

| Field | Truth | Live read | Match |
|---|---|---|---|
| balconySide | street | courtyard | no |
| windowSides | one | one | yes |
| bedroomSide | street | courtyard | no |
| streetEvidence | oppositeFacade (hand-written) | courtyardGreenery | n/a |
| confidence | - | 0,55 | - |

This is a finding, not a failure of the plan (as the plan specified). The read got the street/courtyard sides wrong, but it said so at confidence 0,55, below the 0,6 gate, so after the gate the balcony and bedroom side both read as unknown and nothing downstream would have used them. I did not look at the four pictures myself, so I do not know whether they show a view out of a window that the model mistook for a courtyard. The synthetic plan (a drawing without photos) came back all unknown at confidence 0,10, which is the intended behaviour: a plan alone cannot tell street from courtyard.

Plan 08 runs the read over the real candidates and should treat this as the first data point on how much weight the 0,6 gate can bear: the wrong answer here sat only 0,05 under the line.

## Decisions Made

- When the layout picks the facade, the Sol cell prints the sun fact's confidence (what taste multiplied by), not the layout's. The cell and the score then agree, and the taste share is exactly double.
- "No balcony" counts at confidence >= 0,6 alone. It claims nothing about street or courtyard, so it does not need photo evidence. Street, courtyard and bedroom side need both.
- `LayoutCallError` extends `FloorPlanCallError`, so `asBilledFailure` from `sun-floorplan.ts` is reused by import (as the plan said) and passes the new error through unchanged. `sun-floorplan.ts` is not edited.
- The smoke estimates 0,45 kr per call instead of the 0,6 default. With 0,6, two calls cannot both be approved under a 1 kr cap; R-07 puts a full read at about 0,43 kr. The real bill is read from the API and counted as it arrives. The weekly run keeps 0,6.
