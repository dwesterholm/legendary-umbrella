# Phase 14.4: Code Review Report

**Reviewed:** 2026-10-14T06:19:42Z
**Depth:** standard (diff against 0251f64, whole-file reads of the new modules, targeted offline reproductions)
**Files Reviewed:** 22

## Summary

No blocker found. The security-relevant seams hold up: both vision modules put every URL through `isAllowedImageHost` before it can reach Anthropic, the sold side builds URLs only from digit-only ids on the fixed host `bcdn.se` (`bcdnImageUrl`), billed failures (refusal, truncation, empty parse, schema mismatch) are charged to the cap, nothing but enums, ids, counts and confidence is persisted, and the logs print error class names and HTTP status, not messages or URLs. The hedonic seam is sound on the points asked about: training and serving build features through the same `buildFeatureRowFromContext`, an unknown input takes the training mean (contribution exactly 0) and is named in `imputed`, the persisted column mean equals the imputation mean, and clamp bounds are applied identically at fit and at prediction. The decomposition in the valuation report sums exactly: `capRemoved + refit + avgift + debt + tomträtt + övrigt = newGap - oldCredit`, with `övrigt` as the explicit remainder. Residual-flag arithmetic is consistent across both bases (`ln(r) < -2 sd` is the same test as `r < exp(-2 sd)`), and no stale 20 % credit arithmetic is left in the scoring path (`MAX_CREDIT_PCT`, `creditCapped`, `creditCap` are gone from non-test code). Typecheck is clean and the seven relevant test files pass (595 tests).

What does need attention is behaviour the tests cannot see: one cap check that is wired to the wrong quantity (and can silently flip a decision file), a days-on-market term with no bound that moves the expected final price by tens of percentage points between a new and an old listing, a layout gate whose own by-eye check says it lets wrong answers through into profit, and two places in the enrichment stop rule where a single ambiguous or block-induced outcome permanently removes a page from the queue.

## Warnings

### WR-01: Sold-condition smoke cap is compared against the lifetime ledger, so a re-run after the main read is refused and overwrites the evidence

**File:** `scripts/sold-condition-probe.ts:173,211` (cap check in `src/lib/discovery/sold-condition.ts:336`)
**Issue:** `runSoldConditionReads` checks `priorSek + spentSek + estimate > capSek` (a lifetime comparison). The smoke passes `capSek: Math.min(SMOKE_CAP_SEK, remaining)`, a per-run allowance of at most 1 kr. Once the ledger holds more than about 0.9 kr, every smoke call is refused as `cost_cap`. Reproduced offline with the real runner: ledger 26.12 kr, `capSek = min(1, 3.88) = 1` gives `[ 'cost_cap' ]`, no call made. The smoke then writes `evidence/sold-condition-smoke.json` with `read: 0` and `grammar: "other_error"`, and the next `--branch-report` turns the recorded "fit" decision into "prior (smoketestet läste 0 av 5)". The ledger is 26.12 kr today, so any re-run of `--smoke` (for example after a prompt change that bumps `SOLD_CONDITION_VERSION`, which also empties the cache hits) silently destroys the evidence the branch rule reads.
**Fix:**
```ts
const prior = soldConditionSpentSek(cache);
const remaining = Math.max(0, SOLD_CONDITION_CAP_SEK - prior);
// lifetime-style cap: what is already spent plus this run's allowance
const capSek = prior + Math.min(SMOKE_CAP_SEK, remaining);
... { call, cache, capSek, today }
```
Also make the smoke refuse to overwrite an existing evidence file with `attempted > 0 && calls === 0 && cacheHits === 0`.

### WR-02: Days-on-market term is unbounded and very steep for new listings

**File:** `src/lib/discovery/hedonic-model.ts:576-583` (term stored at `:1608`, input from `src/lib/discovery/fit-score.ts:526`)
**Issue:** `ln += dom.beta * (Math.log(1 + days) - dom.mean)` with no clamp on `days`. Continuous features got a 1st-99th percentile clamp; this term did not. Evaluated against the committed model (Södermalm, asking = model price): 0 days gives +23.3 % expected overbid, 7 days +14.6 %, 30 days +9.3 %, 365 days +0.2 %, 730 days -2.2 %, 1500 days -4.6 %. Training days are p50 12, p99 231, max 701; the listing card path converts "N år på Booli" to `365 x N`, so a two-year listing extrapolates past the training range and gets a negative premium (expected final below asking), which inflates profit for exactly the stale listings the "dold-defekt-risk" flag exists for. At the other end, a listing "inkommet idag" is priced as if it were one of the flats that sold within a day (the hot subset), about 10 points above the premium at the training mean, so fresh listings are penalised in the ranking. The model note documents "days so far, not final" as a slight upward bias for long-listed flats; the size of the effect at the fresh end is not "slight" and goes the other way.
**Fix:** persist the training range on the term (for example `lnLo`/`lnHi` = p1/p99 of `ln(1 + daysActive)`) and clamp before applying; consider treating a listing younger than the training median as "days unknown" (adds 0) because its final age is censored:
```ts
const ln1 = Math.log(1 + days);
const used = Math.min(dom.lnHi, Math.max(dom.lnLo, ln1));
ln += dom.beta * (used - dom.mean);
```
Add the two fields to `domTermSchema` (required for version 2) and a test with `daysOnMarket = 5000`.

### WR-03: Layout gate lets wrong answers into profit; its own by-eye check shows it

**File:** `src/lib/discovery/layout-fact.ts:29-30,81-86`, `src/lib/discovery/fit-score.ts:349-363`, `src/lib/discovery/taste.ts:217-218`
**Issue:** The single gate (`confidence >= 0.6`, plus the model's own `streetEvidence !== "none"`) decides both the "korsdrag ja" bonus (+1 % of resale, 40 000 to 60 000 kr on these flats) and the switch of `streetOnlyFactor` from 0.5 to 1 for the sun part. `evidence/layout-eye-check.md` measured: 2 of 3 "korsdrag ja" answers wrong (at 0,60 and 0,70), street versus courtyard confirmed in 1 of 12 flats, refuted in 1 (Folkungagatan 61, kept out only because its confidence was 0,55, five hundredths under the gate), left open in 4. In the live run 12 flats got "korsdrag ja" and 25 of 75 rows had the sun facade chosen from the balcony side. The self-reported evidence word is not a check: the model gave `courtyardGreenery` for artificial grass on a balcony. This is shipped as the weekly ranking input for a purchase decision. The phase summary lists it as an open point; it is still live money-moving behaviour.
**Fix:** the asymmetry matters: only `true` earns taste, so make the positive claim stricter than the negative one, for example require `confidence >= 0.8` for `twoOpposite` and for `usableSide` before it changes the sun factor, keep 0.6 for the "nej"/"okänd" display. Better, require agreement between two reads (plan-only and plan+photos) or between the read and a stated facade before a positive counts. Keep the gate numbers in `layout-fact.ts` as named constants so the tests pin them.

### WR-04: `livingOnBalconySide` is read and paid for but never used; the sun is credited from the balcony side regardless

**File:** `src/lib/discovery/fit-score.ts:349-363` (`inferredSunWithLayout`), `src/lib/discovery/layout-read.ts:76`
**Issue:** The module header of `layout-read.ts` says the point of the read is "whether the living space faces" the street or courtyard. `inferredSunWithLayout` picks the facade from `usableSide(layout, "balcony")` only and sets the source factor to 1 ("we now know which side the living space is on"). A flat with a street balcony and the living room on the courtyard side is still credited with the street facade's sun at full weight. A grep shows `livingOnBalconySide` and `kitchenOnBalconySide` are never read outside the report. (The prompt maps unknown to `false`, so the boolean also cannot tell "no" from "could not see", which is a reason to gate on it rather than treat it as a free signal.)
**Fix:** apply the layout only when `layout.livingOnBalconySide === true`; otherwise fall back to the 14.3 half-weight result (`applied: false`). Add a test: balcony street, living room not on balcony side gives `applied === false`.

### WR-05: One "no_data" sighting permanently removes a sold page

**File:** `src/lib/booli/slutpriser.ts:1113-1116,1140-1152`
**Issue:** `recordNoData` writes `attempts: ENRICH_MAX_ATTEMPTS` straight away, so a page whose render merely came back without a sold payload (slow hydration, partial render, a soft interstitial that is not caught by `isChallenge`) is dead after one attempt, while a thrown failure gets two. `selectEnrichmentSample` and `needsEnrichment` then never pick it again, and the only recovery is hand-editing the cache. R-10 was derived from old expired pages; the code cannot tell those from a transient empty render. It also hides a real block from the stop rule, because no_data never counts as a failure.
**Fix:** count a first no_data as one attempt (`recordedFailure(previous, today, NO_DATA_REASON)`), so a second no_data confirms it; keep not counting it toward the block signal. Optionally add a `--retry-no-data` flag that clears `reason === "no_data"` entries.

### WR-06: Failures caused by a block are charged against the page's retry budget

**File:** `src/lib/booli/slutpriser.ts:1134-1135` (sold), `:1250-1253` (BRF)
**Issue:** A thrown `ChallengeError` is recorded in the ledger like any render failure (`recordFailure(row.booliId, errorClassOf(e))`). Rows are drawn in a fixed hash order, so after a stop the next run starts with the same unfinished rows; two blocked runs on consecutive days kill the same pages for good (`ENRICH_MAX_ATTEMPTS = 2`) although nothing is wrong with them. With 2 pages in flight, up to 2 rows are blamed per block event.
**Fix:** do not increment the page's attempts when `errorClassOf(e) === "ChallengeError"` (or when `stats.challenged` rose during the call); record it in the run log only.

### WR-07: Raw error messages are printed in the enrichment progress and rejection paths, against the stated no-message rule

**File:** `src/lib/booli/slutpriser.ts:1134,1168`; `scripts/pull-slutpriser.ts:578` (`render` throws `Inte en Booli-url: ${url}`)
**Issue:** The ledger and the BRF path deliberately store and print only the error class (T-14.4-08: "a message can carry a URL"), but `onProgress` in `enrichSoldRows` prints `e.message`, and the final `throw new Error(... first.message ...)` repeats it. The local-browser and Apify errors can carry request URLs and proxy details. Everything else in this phase (both probes, both vision calls, the BRF pass) follows the class-name-only rule, so this is the one inconsistent path, and it feeds `enrich-run.log` and the terminal output that gets attached to messages.
**Fix:** print `errorClassOf(e)` (and an HTTP status when present) in both places; keep the message out. Use the same `errorClassOf` in the final aggregate error.

### WR-08: Version-2 model validation does not check the clamp bounds the fit relied on

**File:** `src/lib/discovery/hedonic-model.ts:116-117,148-220`
**Issue:** `lo`/`hi` are both `optional` and nothing ties them to the two continuous features. A file that says `version: 2` but has no `lo`/`hi` on `avgiftPerSqmMonth` or `brfDebtPerSqm` (hand edit, partial refit, a fit that had under 20 known values yet kept the feature) passes `parseHedonicModel`, and `buildFeatureRow` then silently predicts without the clamp that the coefficient was fitted under (train/serve skew on exactly the features most prone to outliers). `lo > hi` is also accepted and makes `Math.min(hi, Math.max(lo, v))` return `hi` for every input.
**Fix:** add a refinement: for each of `CLAMPED_FEATURES`, when `source === "fit"` require both `lo` and `hi` with `lo <= hi`; for every feature, reject `lo`/`hi` present alone. Same message style as the existing refinements.

### IN-08: Strip-mode zod on an expensive, hand-resumable cache
**File:** `src/lib/booli/slutpriser.ts:95,169`
**Issue:** `soldRowSchema`, its `enriched` object and `slutprisCacheSchema` are plain `z.object`, so a field the schema does not know is dropped on the next load-and-persist (the reason the schema had to gain its fields before the run). The 14.4 fields are all declared, so nothing is lost today; the next added field will be lost silently if a run from an older checkout touches the file.
**Fix:** use `z.looseObject` on the cache, row and `enriched` schemas.

### IN-09: Failed reads are never cached; the lifetime ledger resets with a corrupt cache
**File:** `src/lib/discovery/layout-read.ts:372-387,216-240`; `src/lib/discovery/sold-condition.ts:347-358,189-213`
**Issue:** A flat whose read always refuses or truncates is re-billed on every weekly run (bounded by the 40 kr run cap). If the cache file is unreadable it is renamed aside and read as empty, which also resets `spentSekTotal` to 0, so the 30 kr lifetime cap of the sold read no longer holds for that run.
**Fix:** cache a "failed" marker with its cost for the same picture set and version, and carry `spentSekTotal` forward from the `.bak` file when it can still be parsed.

### IN-10: Intermediate-model guard does not match its message; model file written non-atomically
**File:** `scripts/fit-hedonic.ts:536,793`
**Issue:** The error says `--out` must be under `.planning/calibration/data/`, but the check only rejects the exact default path, so `--without-new-features --out data/other.json` is accepted. `writeFileSync(outPath, ...)` writes the committed model in place; a crash mid-write leaves a truncated file that every consumer then refuses.
**Fix:** require the `.planning/calibration/data/` prefix in the intermediate branch; write through `writeTextAtomic`.

### IN-11: A throw in the layout step discards the paid vision pass
**File:** `src/lib/discovery/fit-pipeline.ts:298-299`
**Issue:** `deps.layout` is awaited without a guard. `runLayoutReads` is per-flat safe, but client construction or any unexpected error would abort the run after vision money was spent and before the snapshot is written. Layout is optional enrichment.
**Fix:** wrap in try/catch, log the error class, and continue with `layouts = []` (all rows `layout: null`).

### IN-12: Two different thresholds for "enough condition data"

**Issue:** The R-08 branch rule (at least 200 eligible rows and 4 of 5 smoke reads) is evaluated only to write `bid-branch.md`. The fit does not consult it; it fits the condition term whenever 100 labelled rows exist. The two can disagree (branch says "prior", fit says "fit").
**Fix:** have `fit-hedonic.ts` read the branch result and skip the stage on "prior", or drop the report's claim that the rule decides.

### IN-13: Report bucket edges hard-coded next to a named gate constant
