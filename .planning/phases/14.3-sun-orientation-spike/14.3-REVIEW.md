## Summary

The structure is sound. `tsc --noEmit` is clean and the 761 tests in the touched areas pass. These checks held up:

- Bearing convention: suncalc 2.0 returns degrees, north-zero and clockwise. That matches `bearingOfXY`, `crossings` and the facing test.
- Ray/wall algebra: `t` and `u` checked by hand.
- Overpass client: fixed endpoint list, `redirect: "error"`, size caps (declared and streamed), element-count cap, zod validation, error-name-only logging, mirrors first.
- 31-day rule: no network call below 31 days, and the Overpass client is only dynamically imported in the refresh branch.
- Atomic cache write: temp file then rename.
- Taste: with no sun fact, or an "okänd" one, the old `sunScore` path runs unchanged. The 3 % sun cap and the total cap are intact. `unit()` guards NaN and infinity.
- Sol columns: same index in `COLUMNS` and `plainCells`, and every cell goes through `escapeHtml`.
- Git confirms these were NOT touched in `6305382..HEAD`: `candidate.ts`, `niche-score.ts`, `flags.ts`, `job.ts`, `sun-path.ts`, `vision.ts`, `vision-prompt.ts`, `vision-cache.ts`, `watch-enrich.ts`.

I then ran the engine against the real cache and the 77-flat evidence snapshot. That found one wrong-numbers defect in the delivered evidence, caused by an unchecked OSM height. It also found several smaller correctness and robustness issues, listed below.

## Critical Issues

### CR-01: One bad OSM `height` tag (Ringen centrum, 151,7 m) corrupts the shade figures of nearby flats; nothing sanity-checks tag heights

**File:** `src/lib/discovery/osm-buildings.ts:393-400` (`heightOf`), consumed at `:557` (`wallsNear`)
**Issue:** `heightOf` trusts a `height` tag as it is, with no upper bound and no cross-check against `building:levels`. The cache the evidence runs used contains `way/715073073` ("Ringen centrum", Skanstull, Södermalm) with `height=151.703703` and `building:levels=6`. That is a six-storey mall of about 25 m. Real heights above 60 m in the extract are towers and churches, so 151,7 m is a data error (it looks like an elevation import). The ray check treats it as a 151,7 m wall.

I replayed the evidence snapshot with that one tag set to 25 m. Flats within reach of the mall change:
- Dalslandsgatan 3, June, 06-15: obstructed 0,7 h with the tag, 8,0 h (5,6-8,0) with 25 m.
- Tjurbergsgatan 38, March: 0,8 h with the tag, 2,9 h with 25 m.
- Tjurbergsgatan 34: March 0,0 h versus 1,0 h.
- 4 of 7 flats in reach changed.

March drives the taste bonus (`TASTE_SUN_OBSTRUCTION_DATE`), so rank and profit move for these flats. The output is not marked "höjd uppskattad" either, because the height is a tag. This breaks the "never guess, flag what is estimated" principle of D-02 and R-04. The doc comment in `osm-overpass.ts` says answers are untrusted, but only coordinates are bounded.

A plain ratio rule does not separate the Ringen error from real tall churches (Katarina kyrka: 64,5 m with 1,5 levels), so the fix needs a flag, not only a threshold.

**Fix:** Add a plausibility rule that falls back to the levels formula and marks the result estimated. Keep a small manual override table for known-bad ways so churches and towers stay correct. For example:
```ts
// HEIGHT_PARAMS
maxPlausibleM: 120,           // tallest real innerstan building in the extract is Klara kyrka, 116 m
suspectRatio: 4,              // tag height > 4x the levels formula on an ordinary building type
overrides: { "way/715073073": 25 } as Record<string, number>,

// heightOf (needs the building id passed in)
const fromLevels = levels !== null ? levels * storeyM + baseM : null;
if (tagged !== null && tagged > 0) {
  const ordinary = tags.building === "yes" && tags.man_made === undefined;
  const suspect = tagged > maxPlausibleM || (ordinary && fromLevels !== null && tagged > suspectRatio * fromLevels);
  if (!suspect) return { heightM: tagged, estimated: false };
  if (fromLevels !== null) return { heightM: fromLevels, estimated: true };
}
```
Also print the count of suspect heights in the cache line so a bad import is visible.

## Warnings

### WR-01: The facade (window) point can land inside a building; 9 of 148 derived points do, all on the courtyard side

**File:** `src/lib/discovery/sun-facade.ts:408-409, 443-457`; consumed in `src/lib/discovery/sun-fact.ts:396-403`
**Issue:** The courtyard point is the closest point on any wall with a normal within 45 degrees of the courtyard bearing, pushed 0.3 m along that wall's normal. Nothing checks that the pushed point is outside every building. Two ways it fails:
- The closest point is clamped to a wall endpoint, and the push at a re-entrant corner goes into the solid.
- The chosen wall is a party wall, so "outside" is the neighbour.

On the evidence snapshot, 9 of 148 side points sit inside a footprint. Examples: Klippgatan 14E, Tjurbergsgatan 38 (own building), Folkskolegatan 3, Hallandsgatan 30, Åsögatan 196, Creutzgatan 2. When the ray starts inside a building it exits through that building's own wall at t of a few cm to 10 m. A wall higher than `z + t*tan(alt)` blocks. Results: Klippgatan 14E March obstructed 0,0 h of 2,9 theoretical; Folkskolegatan 3 0,0 of 5,2; Tobaksspinnargatan 10 0,0 of 3,6. Street points were never inside. The first side (the table cell) is the street side, so the table is mostly spared, but taste takes the best of both sides and the sun report counts both.

**Fix:** After computing a candidate point, reject it if any building contains it (`pointInBuilding` over `index.buildings`, or the grid), and try the next-nearest wall. If none works, return `courtyardPoint: null` so the hours degrade to theoretical instead of a false zero.
```ts
// in pushedPoint's caller: sort walls by distance, take the first whose pushed point is outside every building
const ok = (p: {lat:number;lng:number}) => !index.buildings.some((b) => pointInBuilding(b, p.lng, p.lat));
```
This needs `index` passed into the facade point step, or the check done in `computeSunFact` before `wallsNear`.

### WR-02: The metres-per-degree constants are not consistent, so the projection is anisotropic; the doc claim "a few centimetres over 300 m" is false

**File:** `src/lib/discovery/osm-buildings.ts:124-141` (also duplicated at `src/lib/discovery/sun-facade.ts:281-282`)
**Issue:** Latitude uses 110 574 m/deg (the equatorial value). Longitude uses 111 320 x cos(lat) (the spherical value). At Stockholm (59,33 N) the true values are about 111 400 and 56 924 m/deg. I measured `projectFrom` on 300 m true north and 300 m true east: it returns 297,8 m north (error 2,2 m, 0,74 %) and 299,3 m east (0,25 %). That is a 2 m distance error and about 0.1-0.15 degrees of bearing skew. Impact on the results is small, but the doc is wrong and the two axes are scaled differently.

**Fix:** Use latitude-dependent ellipsoid formulas for both axes and share them (no second copy in `sun-facade.ts`):
```ts
const mLat = 111132.92 - 559.82 * Math.cos(2 * phi) + 1.175 * Math.cos(4 * phi);
const mLng = 111412.84 * Math.cos(phi) - 93.5 * Math.cos(3 * phi);
```
Correct the comment to say "within about 0,1 m over 300 m".

### WR-03: A throw inside `sunOf` aborts the whole weekly run after the paid vision calls

**File:** `scripts/fit-score.ts:774-800` (`makeSunStage`); caller `src/lib/discovery/fit-pipeline.ts:294`
**Issue:** `loadSunIndex` is careful never to throw, but the per-row `sunOf` is not. It has only a `try/finally` for timing, so an exception from any row propagates. `withSun` runs after detail fetching and vision, so one bad geometry (a turf `polygon()` validation error, a future bug in `computeSunFact`) loses the whole run, including the spend. The stage is documented as "honest degrade", and a replay would crash the same way.

**Fix:** Catch per row and degrade:
```ts
} catch (e) {
  console.log(`OBS: sol kunde inte beräknas för en annons (${e instanceof Error ? e.name : "fel"})`);
  return unknownSunFact("beräkningsfel");
} finally { ... }
```

### WR-04: The 2 kr probe cap is per invocation and defeated by a non-finite cost

**File:** `src/lib/discovery/sun-floorplan.ts:321-330`; `scripts/sun-floorplan-probe.ts:127-176, 178-212`
**Issue:** There are three gaps.
1. After a successful call `spentSek += costSek` is unguarded. If `costSek` is NaN, `spentSek` becomes NaN, `NaN + estimate > cap` is false forever, and the cap never trips again. A negative cost lowers the total. The failure path already guards with `Number.isFinite(...) && > 0`; the success path does not.
2. The header says the ceiling is "the whole probe, smoke included", but `runFloorPlanProbe` starts at 0 on every call. `--smoke`, the probe and any rerun each get up to `capSek` (the smoke's synthetic call is outside the runner and uncapped), and `--cap-sek` is only validated per run.
3. `client.beta.messages.parse` throws after being billed when the output fails to parse, but `makeCall` can only attribute cost after it returns, so that spend is invisible to the cap.

Actual spend was 0,37 kr, so nothing went wrong, but the guarantee is not enforced.

**Fix:** Clamp: `const paid = Number.isFinite(costSek) && costSek > 0 ? costSek : opts.estSekPerCall ?? FLOORPLAN_EST_SEK_PER_CALL;`. Persist cumulative spend in the cache file (`spentSekTotal`) and cap against it, or state in the docs and USAGE that the cap is per run. Count the estimate for any thrown call that reached the API.

### WR-05: A cache with valid metadata but unusable geometry stays "fresh" for 31 days, and the report blames "OSM-cache saknas"

**File:** `src/lib/discovery/osm-cache.ts:65-74, 178-182`; `scripts/fit-score.ts:777`
**Issue:** The refresh decision reads only the meta (`fetchedAt`, arrays are `z.unknown()`). If `parseOsmExtract` later rejects the file (schema tightened in a later phase, or the two duplicated schemas drift), `loadSunIndex` returns a failure. The weekly run then gives every row "okänd" with reason "OSM-cache saknas", for up to 31 days, because the freshness rule never forces a re-download. The reason shown in the report is also wrong for an invalid file (the console line says "ogiltig (...)", the stored reason says "saknas"). Nothing tells the operator to run `osm-download.ts --force`.

**Fix:** Pass `load.failure` into `unknownSunFact` as the reason (keep the label fixed, e.g. "OSM-cache ogiltig"). In `runLive`, if the cache is fresh by age but `loadSunIndex` fails, print "kör: npx tsx scripts/osm-download.ts --force" (or treat a parse failure as `needsRefresh` once, before the download decision).

## Info

### IN-01: Address and street-name matching gaps

**File:** `src/lib/discovery/sun-facade.ts:119-123`; `src/lib/discovery/osm-buildings.ts:108-115`
**Issue:** `streetNameOf` strips one trailing "number, optional letter, optional -number". I ran it on these:
- "Hornsgatan 12A-14B" and "Götgatan 5 A-B" are not stripped, so the street lookup fails and the flat reads "ingen gata med samma namn inom 35 m".
- "Torsgatan 4 1tr" fails the same way.

`normalizeStreetName` removes diacritics, so å/ä/ö match a/o. That is harmless in practice. It does not map "S:t"/"Sankt", and "Sankt" is a likely mismatch against OSM names (an honest degrade, only 2 of 77 flats degraded in the evidence).
**Fix:** Allow `\d+\s*[A-Za-zÅÄÖåäö]?(?:\s*-\s*\d*\s*[A-Za-zÅÄÖåäö]?)?` and a trailing floor token. Add "S:t" to "Sankt" folding before NFD.

### IN-02: NaN-inverted skip guards in the hours engine

**File:** `src/lib/discovery/sun-hours.ts:234-235`
**Issue:** `if (pos.altitude <= min) continue;` and `if (Math.cos(...) <= facingCosMin) continue;` skip only when the comparison is true. A NaN altitude or azimuth (non-finite input that reached the engine) skips nothing and counts the sample as sunlit, so a bad input reads as a full 16-hour day. Today the callers filter non-finite coordinates, so this is latent.
**Fix:** Use the positive form: `if (!(pos.altitude > P.minAltitudeDeg)) continue;` and `if (!(Math.cos(...) > P.facingCosMin)) continue;`.

### IN-03: A "konflikt" against the footprint can never fire

**File:** `src/lib/discovery/sun-fact.ts:334-340, 219-238`
**Issue:** The footprint is compared through its nearer side, and the two sides are exactly 180 degrees apart. The nearer side is therefore never more than 90 degrees away, and the rule is strictly "> 90". So stated or plan versus footprint never conflicts. Only stated versus plan can, and that route is closed. The report line "konflikt: 0" is always true and carries no information. This follows the written spec, but it is worth knowing before the 14.3 evidence is read as "no sources disagreed".
**Fix:** Either compare against the street bearing only (or both), or drop the claim from the report and note in SUN-02 that conflict detection only exists for the plan route.

### IN-04: Duplicate element schema and a few data-shape edges

**File:** `src/lib/discovery/osm-overpass.ts:98-124` vs `src/lib/discovery/osm-buildings.ts:39-64`; `osm-buildings.ts:148-155, 393-400`
**Issue:** The point/way/relation schemas are copied in two files (WR-05 shows why drift matters). The relations answer has no minimum count, so an empty or partial relations answer is accepted silently, which loses courtyard holes. `building:levels=0` gives a 2 m wall marked as not estimated. The `["building"]` query also matches `building=no`.
**Fix:** Export the element schemas from `osm-buildings.ts` and import them in `osm-overpass.ts`. Add `minRelations` (the research box held 267 in the cache). Treat levels 0 as absent. Skip `building=no`.

### IN-05: Walls are selected by vertex distance; flats near the extract edge see less map without saying so

**File:** `src/lib/discovery/osm-buildings.ts:533-568`; `src/lib/discovery/osm-overpass.ts:332-357`; `src/lib/discovery/sun-facade.ts:311-312`
**Issue:**
- A building is included only if one of its outer vertices is within radius + 50 m. A building longer than about 330 m whose edge passes within 250 m but whose vertices are all farther is missed. (On six test points in the real cache, the selection matched a brute-force segment search exactly, so this is theoretical.)
- The bbox gate only checks the flat is inside the extract, not 250 m inside it. For the research-import fallback (no margin) a flat within 250 m of the edge gets optimistic hours with no flag.

**Fix:** Select by segment distance or a bbox-to-point test. Add `edgeTruncated` when the flat is within `radiusM` of `index.bbox` and mark the hours "begränsad karta".

### IN-06: Failed cache write leaves an orphan temp file

**File:** `src/lib/discovery/json-store.ts:20-23` (used by `osm-cache.ts:120`)
**Issue:** `writeTextAtomic` creates `<path>.tmp-<pid>` and renames. If `writeFileSync` or `renameSync` throws (disk full), a partial 13-20 MB temp file stays under `.planning/calibration/data/osm/`. Each run has a new pid, so they accumulate. The old cache itself stays intact, as designed.
**Fix:** Wrap in try/catch and `rmSync(tmp, { force: true })` before rethrowing.

### IN-07: Re-running the probe overwrites the hand-audited evidence file

**File:** `scripts/sun-floorplan-probe.ts:214-225`
**Issue:** `floorplan-probe.json` now holds `verdict: "dropped"`, `modelVerdict: "go"` and an `audit` block written by hand. The script writes `verdict` straight from `probeVerdict(counts)` ("go" for 54,5 %) and no `audit`. A rerun would silently replace the audited decision with "go" while `FLOORPLAN_ROUTE_ENABLED` stays false, so the evidence file would contradict the code. The console also prints "beslut: go" with no hint of the override.
**Fix:** Write the raw script output to a separate file (`floorplan-probe.raw.json`), or merge and preserve an existing `audit` key. Print "mekaniskt beslut: go (granska bilderna innan FLOORPLAN_ROUTE_ENABLED ändras)".
