### Locked Decisions

- **D-01:** Phase exit = the weekly table carries, for >= 80 % of candidates, (a) an inferred main-window/balcony facade with a confidence label and its SOURCE ("angiven", "planritning", "fastighet/gata", "okänd"), and (b) theoretical sun hours per facade for the three seasons from `sun-path.ts`; PLUS, for the top section ("Förväntat under 4 M") at least, an OBSTRUCTED estimate (neighbouring buildings ray-checked) if the spike finds usable height data - otherwise the obstructed part is reported as "not available: <reason>" with the measured coverage and the phase still closes on (a)+(b). Taste's sun part consumes the inferred facade with the confidence as a multiplier (D-07).
- **D-02:** Never fabricate. Unknown stays "okänd" (score 0). Every inferred facade carries `source` and `confidence` in [0, 1]; the table shows e.g. "S (planritning, 0.8)".
- **D-03 Floor-plan compass via vision.** Among the broker photos, detect floor-plan images (vision already sees the gallery; the floor-plan is usually the last 1-2 images, white background). Ask the EXISTING Anthropic vision pass (new prompt section, same strict-output constraints - memory `anthropic-structured-output-limits`: keep the schema slim; no new nullable-union explosion) for: north-arrow present? bearing of north on the image (0-360) with confidence; which side of the plan has the balcony and the largest windows/room; -> facade = side bearing relative to north. Cost: reuse the already-sent floor-plan image in the same call where possible; else one extra call per flat (about 0.4 kr). Cache with the vision cache.
- **D-04 Building footprint via OpenStreetMap.** Overpass API (public, free, rate-limited; be polite: <= 1 req/s, one bbox query per run for all candidates, cache under `.planning/calibration/data/osm-cache/` gitignored). Snap the flat's lat/lng to the nearest `building` way; compute the bearing of the footprint edge facing the named street (match the street via `addr:street` on the building or the nearest `highway` way with that name); street-facade bearing -> facade. Courtyard side = opposite. Confidence from distance-to-building and edge-length. This gives "street side faces S" without knowing which rooms are where; combined with D-03 (balcony side) it becomes "balcony on the street side, facing S".
- **D-05 Precedence:** stated text > floor-plan compass > footprint/street. If two sources disagree by > 90 degrees, mark `konflikt`, confidence halved, show both.
- **D-06 Data sources to probe, in order:** (1) OSM `building:levels` / `height` coverage within the innerstan bbox (measure the % of buildings with either); (2) Stockholms stad open data (Dataportalen: "3D-byggnader" / "Byggnader LOD") and Lantmäteriet open data ("Byggnad" / "Höjddata" / "Ytmodell") - check licence (CC0/CC-BY), format (CityGML / GeoPackage / GeoJSON / LAZ), download size, and whether a bbox cut is practical; (3) fallback: assume `height = levels x 3 m + 2 m`, and if `levels` is missing assume the innerstan median (5-6 storeys, about 18-20 m) with a flag. Ray-check: for each hour of the 21st of Mar/Jun/Sep/Dec, from the flat's facade centre at `floor x 3 m + 1.5 m`, test whether the sun ray (azimuth/altitude from suncalc) intersects any neighbouring footprint within 150 m whose top is above the ray; count unobstructed hours per facade. +-1 h target; no room-level modelling; no trees.
- **D-07 Taste integration:** sun part = facade weight (east 1.0 / south 0.7 / ...) x confidence x obstruction factor (obstructed hours / theoretical hours for the morning+midday window, if available, else 1). Cap unchanged (3 % of resale). `taste.ts` stays pure; new modules are pure; `niche-score.ts`/`flags.ts` untouched.
- **D-08** Headless only (the weekly script and the HTML mail get "Sol" columns: facade/source/confidence, theoretical hours (Mar/Jun/Dec morning+midday), obstructed hours when available). No UI.
- **D-09** Cost ceiling per weekly run for this feature: <= 30 kr vision extra (cached), 0 USD Apify, Overpass free and cached; one-off data downloads <= 2 GB on disk, gitignored.
- **D-10** Evidence run on the current 77 candidates: coverage per source, agreement rate between D-03 and D-04 where both exist, Folkungagatan 61's inferred facade (truth: south, balcony street side - from the Hemnet text) as the calibration row, a second known flat if any listing states a facade (2 do).

## Summary

Three verdicts, measured on the real snapshot of 78 rows (77 with a picture set) taken on 2026-10-13.

**Orientation from the building footprint: go.** OpenStreetMap has a building polygon under 68 of 76 resolvable flats and a polygon within 15 m for the other 8. Matching the street name from the address to OSM `highway` ways with the same name worked for 76 of 78 rows (the other 2 have no street within 35 m of a building edge). The street-facing edge of Folkungagatan 61 points to 166.2 degrees, which is south, matching the Hemnet text. 67 of the 76 results score confidence >= 0.7. The `addr:street` route in D-04 is dead: only 2.1 % of innerstan buildings carry it. The street name has to come from the road geometry. The weakness is conceptual, not technical: the footprint tells you where the street side is, not which rooms or balcony sit on it. The honest output is two facades per flat (street side and courtyard side, opposite each other) with a street-side probability, not one facade.

**Orientation from the floor-plan compass: no-go as a bearing source.** 69 of 77 flats (90 %) have a floor plan as the first image in the set the vision pass already receives. I looked at all 69 at 480 px width. None has a north arrow or compass rose. Most show a small arrow at the entrance door, which a vision model could mistake for north. The CONTEXT premise that many Swedish plans carry a north arrow does not hold for this sample. Keep one cheap measurement (about 2 kr) so the verdict rests on a model read as well as my eyes, then close the route if prevalence is under 10 %.

**Obstructed sun hours: go, but report a range, not a number.** OpenStreetMap height data is good enough on Södermalm (86 % of buildings within 150 m have `building:levels` or `height`) and poor on Kungsholmen (59 %); whole innerstan is 73.8 %, below the 85 % bar in the brief. The official 3D datasets could not be confirmed (Stockholm "3D-byggnader" showed "Licens behövs" in a 2022 post; Lantmäteriet's open ground model has no buildings), so the fallback in D-06 applies: levels x 3 + 2 m, local median for missing levels (measured error: median 3 m, 88 % within 6 m). The ray-check itself is trivial: 178 ms for 78 flats x 4 dates x 144 time steps against up to 1 400 wall segments each. The accuracy claim is where it gets thin. Raising or lowering every neighbour by 3 m (6 m for estimated ones) gives a spread wider than 2 h, i.e. outside +-1 h, for 7 % of flats in March, 23 % in June, 4 % in September and 13 % in December (flats with at least 1 h of theoretical sun that date). Shifting the flat itself by one storey, which is how unsure the Booli floor numbering is, moves June hours by more than 1 h for 11 of 74 flats. Folkungagatan 61 in December shows the worst case: 0 h, 4.3 h or 5.5 h depending on whether the opposite roofline is 3 m higher, as tagged, or 3 m lower. At a winter sun altitude of 5 degrees, 3 m of height moves the shadow line by about 34 m of street.

**Primary recommendation:** Build `osm cache -> footprint facade -> sun hours engine -> ray-check with a three-scenario height envelope`, all pure and offline against the cached OSM extract, and show obstructed hours as "low-high" with a "usäker" flag when the range exceeds 2 h. Do not extend the existing vision schema; run the floor-plan probe as its own call with its own cache so the 77 cached picture reads (about 33 kr) stay valid.

### Probe 4: suncalc and `sun-path.ts`

- `computeSunExposure(latitude, longitude, floor, orientation: Facade[] | null)` returns `byFacadeAndSeason` (qualitative Swedish labels, never hours), `orientationSource: "description" | "unavailable"`, `orientationConfidence` (fixed 0.5). `floor` is accepted but unused. [VERIFIED: src/lib/discovery/sun-path.ts:198-233]
- Facade type: `export type Facade = "north" | "east" | "south" | "west";` [VERIFIED: sun-path.ts:40]. Season reference dates in UTC: `winter: "2026-12-21T12:00:00Z"`, `springAutumn: "2026-03-20T12:00:00Z"`, `summer: "2026-06-21T12:00:00Z"`; sampling `SAMPLE_HOURS_UTC = [4, 6, 8, 10, 12, 14, 16, 18, 20]` (2-hour steps, UTC). [VERIFIED: sun-path.ts:80-82, 94]
- A facade sees the sun while the angular distance between the sun azimuth and the facade's compass direction is <= 90 degrees (line 124). That is a plane test on the facade centre direction, which is what an outward normal does too.
- It cannot give hours: 2-hour UTC steps with a qualitative label. Obstructed hours need a new function; leave `computeSunExposure` byte-identical (it is registered in the separation test).
- Daylight saving: dates in 2026 are Mar 21 (UTC+1; DST starts Mar 29), Jun 21 and Sep 21 (UTC+2), Dec 21 (UTC+1). Use `Intl.DateTimeFormat("sv-SE", { timeZone: "Europe/Stockholm", hour: "2-digit", minute: "2-digit", hourCycle: "h23" })` to label morning and midday windows; this worked in the prototype.
- Theoretical hours at Folkungagatan 61 for a 166-degree facade (10-minute steps, facade-plane test, altitude > 0.5 degrees): Mar 10.7 h, Jun 9.7 h, Sep 10.8 h, Dec 5.7 h.

### Pattern 1: Street-facade inference from a footprint

**What:** Find the polygon the flat's point lies in (else the nearest edge within 25 m), take its outer-ring edges of length >= 2.5 m, and score each edge as a frontage candidate against the polyline of OSM `highway` ways whose `name` equals the street in the address.

**When to use:** every flat with lat/lng and an address.

**Rules that worked on the snapshot:**
- Street name = address minus trailing house number and letter: `address.replace(/\s+\d+\s*[A-Za-zÅÄÖåäö]?(?:-\d+)?\s*$/, "")`. Exact, case-insensitive match against highway `name`.
- Edge outward normal from the ring orientation (signed area sign).
- An edge qualifies when the nearest named-street point lies in front of it (dot(outward normal, unit vector to street) > 0.5) and within 35 m.
- Group qualifying edges whose normals are within 25 degrees; weight = edge length x exp(-distance/12 m); take the heaviest group; bearing = weight-weighted circular mean.
- Flat position = nearest point on the winning edges to the Booli point, pushed 0.3 m outward (so the ray starts outside the own building).
- Confidence (prototype, a judgement not a measurement): `(inside ? 1 : 0.7) x (0.4 + 0.6 x share of weight in the top group) x (minStreetDistance <= 10 m ? 1 : 0.8) x (frontage length >= 8 m ? 1 : 0.7)`, clamped to [0, 1].
- Flag `ambiguous` when the second group carries more than 60 % of the top group's weight (corner flats): 3 of 76 (Sysslomansgatan 26, Lidnersplan 12, Norra Hammarbyhamnen).
- Courtyard facade = street bearing + 180 degrees. True for slab blocks; wrong for corner blocks, wings and buildings with three exposed sides.

**Results on 78 rows:** 76 resolved, 2 "no-frontage" (Heleneborgsgatan 30A, Reimersholmsgatan 39: nearest same-name road 42 m and 44 m from any edge); 68 inside a polygon, 8 snapped to the nearest edge (all but one within 2 m; the exception is 15 m away); confidence >= 0.7 for 67, >= 0.5 for 75. Street-facade sector among the 74 with a known floor: E 25, N 20, S 17, W 12.

**Self-check available for free:** Booli's floor never exceeds the OSM levels of the polygon the point landed in (58 flats with both: floor minus levels ranges from -17 to 0). A flat whose floor is above the polygon's levels has landed on the wrong building (annex or courtyard building); drop its confidence. [VERIFIED: computed this session]

### Pattern 2: Ray-check against extruded footprints

**What:** From the flat position at height `z`, for each time step with sun altitude > 0.5 degrees and the sun in front of the facade (cos(sun azimuth - facade bearing) > 0.05), cast a horizontal ray along the sun azimuth. Intersect it with every wall segment of every building within the radius (outer and inner rings). The sun is blocked if any crossing at horizontal distance `t` has `H > z + t x tan(altitude)`. Testing every crossing and not only the first one is correct for concave shapes and for courtyard holes: a rising ray that clears the wall height at its lowest crossing clears all later ones.

**Radius:** 250 m. Changing 150 m to 250 m altered the obstructed hours of 3 of 74 flats by more than 0.5 h in March and 3 of 74 in December; 250 m to 400 m altered 0 in March and 1 in December. [VERIFIED: prototype]

**Height of a building:** `height` tag if present, else `levels x 3 + 2` plus `roof:levels x 1.5`, else the local median (tagged non-shed buildings within 150 m) flagged `estimated`; sheds and allotment houses default to 3 m. The `+ roof:levels x 1.5` term is my addition ([ASSUMED]); it moves Folkungagatan 61 from 20 m to 21.5 m.

**Flat height:** `z = floor x 3 + 1.5` (D-06 literal). Booli's `floor` never exceeds the polygon's levels, so it behaves as "floor N of M" with the ground floor counted. Whether the ground floor is 0 or 1 is not proven. The D-06 literal (`floor x 3 + 1.5`, equivalent to the ground floor being 0) matches Daniel's own report from Folkungagatan 65, 5th floor: "daytime sun from the street side even in winter" [memory `daniel-fit-score-decisions`]. With `(floor - 1) x 3 + 1.5` the same flat at Folkungagatan 61 gets 0 h of December sun.

**Scenarios (the envelope):**
- low sun: `z = (floor - 1) x 3 + 1.5`, tagged neighbours +3 m, imputed neighbours +6 m
- nominal: `z = floor x 3 + 1.5`, heights as derived
- high sun: `z = floor x 3 + 1.5`, tagged neighbours -3 m, imputed -6 m

Print "nominal (low-high)" and mark the cell `usäker` when high minus low exceeds 2 h.

### Pattern 4: Combining sources

`SunInference` (recommended shape; discretion area):

```typescript

  source: "angiven" | "planritning" | "fastighet/gata" | "okänd";
  confidence: number;                 // [0,1], D-02
  facades: Array<{ side: "stated" | "street" | "courtyard"; bearing: number | null; facade: Facade; share: number }>;
```

Taste mapping (`taste.ts` stays pure and gets an additive optional input): expected facade weight = confidence x sum over facades of share x `TASTE_WEIGHTS.facade[facade]`. For a footprint-only flat the street side share is 0.5 and the courtyard side 0.5, because the footprint does not say which side the windows or balcony face. A stated facade (text) keeps today's behaviour: share 1.0, confidence 0.5 as in `extractOrientationFromDescription`.

Obstruction factor (D-07): nominal obstructed hours divided by theoretical hours over the morning-plus-midday window (local 06:00 to 15:00) on 21 March for the facade side(s) in play, 1 when unavailable. Use March, not June or December: March is the equinox and was the most stable month in the envelope (93 % within 2 h).

### Anti-Patterns to Avoid

- **One facade per flat from the footprint.** The footprint only fixes the street side. Presenting "S" as the flat's facing direction will mislead for the many flats whose rooms look into the courtyard. Carry both sides.
- **Adding a field to the existing vision schema.** Invalidates the 77 cached reads (about 33 kr) and may never run on flats the Haiku gate skips.
- **A point estimate for December hours.** The envelope for Folkungagatan 61 is 0 to 5.5 h.
- **Using `Date#getHours()` for the morning window.** It depends on the machine's timezone and breaks under a different launchd or CI environment.
- **Treating building tags as certain.** 26 % of the innerstan has no height source; show "estimerad" and widen the envelope.
- **Touching `computeSunExposure`.** It is under the structural-separation test and its output stays qualitative.

## Common Pitfalls

### Pitfall 1: Overpass 504 on the main host
**What goes wrong:** `overpass-api.de` returns HTTP 504 on every request, even a tiny one, for minutes.
**Why:** The main host is overloaded by its own account; the dispatcher times out when slots are not available.
**How to avoid:** An ordered endpoint list (`lz4.overpass-api.de`, `z.overpass-api.de`, `overpass.openstreetmap.fr`, then `overpass-api.de`), up to 3 rounds, 3 s between endpoints and 10-15 s between rounds, a `User-Agent` naming the project, `[timeout:180]`. The weekly run never calls Overpass; it reads the cache and fails closed to "okänd" with a printed reason if the cache file is missing or corrupt.
**Warning signs:** HTTP 504 or 429, a body that starts with `<?xml`, JSON without `elements`.

### Pitfall 2: Relations lose their members
**What goes wrong:** `out geom tags;` returns relations with `bounds` and tags but no `members`, so 243 courtyard buildings vanish or are drawn as nothing.
**How to avoid:** Query relations with `out geom;` (full body). Parse defensively: a relation with no closed outer ring is skipped and counted in the printed coverage line (2 of 243 in the prototype).

### Pitfall 3: Courtyard holes
**What goes wrong:** A flat or a ray inside an inner ring is treated as inside the building; the courtyard is shaded by its own ring.
**How to avoid:** Test inner rings explicitly (point-in-hole means outside the building) and include inner-ring edges in the wall list; the "any crossing" rule handles them.

### Pitfall 4: Street-side is not the window side
**What goes wrong:** The table says "S" for a flat whose living room looks into a north courtyard.
**How to avoid:** Two facades, a street share of 0.5 until another source says otherwise, and show both in the cell. The two stated-orientation flats in the snapshot (Ola Hanssonsgatan 9 and Wennerbergsgatan 6A, both stated "väster" in text) have street facades of 106 and 94 degrees (east), so the stated west is their courtyard side, consistent with the model but not provable because the description text is dropped under the PII rule.

### Pitfall 5: Booli point precision and snapping
**What goes wrong:** The point sits on the street or 2 m outside the polygon; or inside a courtyard annex.
**How to avoid:** Inside the polygon first, else nearest edge within 25 m with lower confidence (8 of 76 needed this); check `floor <= levels`; never move the position more than 25 m; flag the one case at 15 m ("Norra Hammarbyhamnen", confidence 0.35).

### Pitfall 6: Wrong street, or no street
**What goes wrong:** The address street is not an OSM `name` (Heleneborgsgatan 30A and Reimersholmsgatan 39 got no frontage within 35 m), or a corner flat's address street is the short side.
**How to avoid:** Fall back to the nearest highway of any name within 25 m with confidence x 0.5 and `source` text "fastighet/närmaste gata", otherwise "okänd". Do not guess.

### Pitfall 7: `building:levels` is above ground, excludes roofs
**What goes wrong:** Attic storeys (26.5 % of buildings have `roof:levels`) are missed and neighbours are 2-4 m low.
**How to avoid:** Add the `roof:levels` allowance and keep the envelope. The 3 m per storey rule underestimates 1900s buildings with 3.3-3.5 m storeys; the envelope covers about one storey of error.

### Pitfall 8: Floor numbering
**What goes wrong:** Whether "floor 5" is the fifth level (ground = 1) or five flights up changes the flat's height by 3 m; June hours shift by more than 1 h for 11 of 74 flats.
**How to avoid:** Use the D-06 literal for the nominal case and the other convention for the pessimistic scenario; report the sensitivity in the evidence run.

### Pitfall 9: Entrance arrow read as north
**What goes wrong:** The floor-plan model reports a bearing from the door arrow; a wrong "angiven by plan" overrides a correct footprint.
**How to avoid:** The prompt names the lookalike; the decision threshold is confidence >= 0.6 and `northArrowPresent`; and D-05 flags a disagreement above 90 degrees with the footprint as `konflikt`. Plan results never overrule a stated text, but they would overrule the footprint, so the 0 of 69 base rate matters.

### Pitfall 10: Strict output schema limits
**What goes wrong:** Too many nullable fields or numeric constraints cause HTTP 400 at call time; mocked tests do not see it.
**How to avoid:** The proposed schema has four fields, no nullable, no `.min()/.max()`. Run one live smoke.

### Pitfall 11: Winter low sun and the 150 m radius
**What goes wrong:** At 5 degrees altitude a 20 m building 250 m away still blocks a ray at 13 m height.
**How to avoid:** Radius 250 m, ignore time steps with altitude below 0.5 degrees, and ignore the rest of the horizon; 400 m changed 1 of 74 December results.

### Pitfall 12: Committing OSM-derived data
**What goes wrong:** The downloaded cache (17 MB) is committed; ODbL attribution is missing in a fixture.
**How to avoid:** The cache stays under the gitignored `.planning/calibration/data/`; the fixture is trimmed to about 60 KB (keep the street names that matter) and carries the line "(c) OpenStreetMap contributors, ODbL".

### Ray against wall segments

```typescript
// Source: prototype-sun.mjs; blocked if ANY crossing has wall height above the ray at that distance
function blocked(origin: [number, number], z: number, azDeg: number, tanAlt: number,
                 walls: Array<[number, number, number, number, number]>, radius: number): boolean {
  const dx = Math.sin((azDeg * Math.PI) / 180), dy = Math.cos((azDeg * Math.PI) / 180);
  for (const [x1, y1, x2, y2, h] of walls) {
    const ex = x2 - x1, ey = y2 - y1;
    const den = dx * ey - dy * ex;
    if (Math.abs(den) < 1e-9) continue;                  // parallel
    const ox = x1 - origin[0], oy = y1 - origin[1];
    const t = (ox * ey - oy * ex) / den;                 // metres along the ray
    const u = (ox * dy - oy * dx) / den;                 // 0..1 along the wall
    if (t <= 0.05 || t > radius || u < 0 || u > 1) continue;
    if (h > z + t * tanAlt) return true;
  }
  return false;
}
```

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Poisoned or malformed Overpass response (HTML error page, huge body) | Tampering / DoS | Check `content-type` and `elements` array; size cap (about 50 MB); zod parse; keep the previous cache on failure |
| SSRF through an image URL | Spoofing | Only Booli `bcdn.se` URLs from `imageUrls`, re-checked with `isAllowedImageHost` (as `visionResultSchema` does on read) |
| Prompt injection through text in a floor-plan image | Tampering | Strict structured output with booleans and numbers only; no free text returned or stored |
| Personal data | Information disclosure | Floor plans are analysed and not stored; the cache keeps booleans, a bearing and a confidence per image id. Addresses already appear in the snapshot. Never log image URLs with results, as `vision.ts` logs only `{ booliId, code }` |
| Secret exposure | Information disclosure | The API key is read from the environment by the SDK; never printed (global rule) |
