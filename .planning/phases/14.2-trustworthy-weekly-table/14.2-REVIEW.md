# Phase 14.2: Code Review Report

**Reviewed:** 2026-10-13
**Depth:** standard (changed regions via `git diff 2bad358..HEAD`, whole file for new modules)
**Files Reviewed:** 26
**Status:** issues_found

## Summary

The phase is carefully built. Things checked and found sound: no persistent browser profile or storage state (`chromium.launch` + a fresh `newContext`, downloads off); `new Function` only ever compiles the page-function constant, and page text is only read as data; HTML escaping covers every dynamic mail string and only https booli.se links become anchors; the SMTP URL and recipient are never logged (only an error code); atomic writes go temp-file then rename; `--allow-apify` is absent from the wrapper and the plist; the plist holds no secrets; `candidate.ts`, `niche-score.ts`, `report/flags.ts` and `job.ts` have an empty `git diff 2bad358..HEAD` (only `niche-score.test.ts` gained the new forbidden-import specifiers); `nodemailer` 9.0.5 and `playwright` 1.60.0 are exact pins and match `node_modules`.

One finding breaks a stated guarantee (CR-01): on SIGINT/SIGTERM the local renderer is removed, which silently re-routes the still-running pipeline to paid Apify. The warnings are mostly robustness holes in the unattended weekly job: a hung page can stall the run and hold the lock forever, the lock can be wedged by a reused pid, and the "seen" memory can swallow flats that were never mailed.

## Critical Issues

### CR-01: Closing the local renderer on a signal re-enables paid Apify rendering

**File:** `src/lib/booli/local-browser.ts:422-426` (with `src/lib/booli/transport.ts:81-83,113-119` and `closeOnSignals` at `local-browser.ts:209-226`)
**Issue:** `close()` calls `setRenderer(null)` before it awaits `context.close()`. `runPlaywrightRender` falls back to `runApifyRender` whenever `renderer === null`. `closeOnSignals` runs `handle.close()` on SIGINT/SIGTERM and only then calls `process.exit`, so the pipeline keeps running while the browser shuts down. Every in-flight render now fails (browser closed), `walkFallbackTree` moves to its second rung, and that second `runPlaywrightRender` call sees `renderer === null` and starts a paid Apify actor run (about 0.04-0.06 USD each, `APIFY_API_TOKEN` is normally in `~/.zshenv`). The same happens for any new `fetchListing`/`fetchAreaListings`/BRF/broker call the pool starts in that window, in both `fit-score.ts` and `pull-slutpriser.ts`. This defeats the "never falls to Apify without `--allow-apify`" rule (R-03) and the `--apify-max-renders` cap, which only guards the path inside `render`. launchd stopping the job (logout, shutdown) triggers exactly this.
**Fix:** After close, install a refusing renderer instead of restoring the Apify default, so a closed local renderer can never route to Apify:
```ts
async close() {
  if (closed) return;
  closed = true;
  setRenderer(async () => {
    throw new Error("Lokala webblasaren ar stangd");
  });
  // ...close context and browser as before
}
```
If the Apify default must be restored for tests, restore it only when `allowApify` is true. Add a test: signal -> close -> `runPlaywrightRender` rejects and `runApifyRender` is not called.

## Warnings

### WR-01: No watchdog around a page function: one hung page stalls the run and holds the lock indefinitely

**File:** `src/lib/booli/local-browser.ts:346-377` (`attempt`), `scripts/fit-score.ts:915-1003`
**Issue:** `page.goto` has a 45 s timeout, but `run({ page, request })` and `page.evaluate(...)` do not. Playwright's `evaluate` has no default timeout, so a broker page with a busy loop, or a tab that stops responding without crashing, blocks forever. The semaphore slot is never released (two slots in total), the pool stalls, `FIT_ENRICH_DEADLINE_ALL_MS` is only checked when a candidate starts, and there is no run-level timeout. The process stays alive, so `isPidAlive` says the lock is live and every later Monday exits with code 3. `caffeinate -i` also keeps the Mac awake for as long as it hangs. Broker pages are third-party content, so this is a realistic denial of the weekly job.
**Fix:** Wrap the page-function call in a timeout and close the page on expiry:
```ts
const withTimeout = <T,>(p: Promise<T>, ms: number): Promise<T> =>
  Promise.race([p, new Promise<T>((_, rej) => setTimeout(() => rej(new Error("sidan svarade inte")), ms))]);
let out = await withTimeout(run({ page, request: { url } }), PAGE_FUNCTION_TIMEOUT_MS);
```
Also add a whole-run watchdog in `fit-score.ts` (for example 2 h, then close the browser and exit non-zero), and use `unref()` on the timers.

### WR-02: Stale-lock takeover is racy, and a reused pid wedges the lock forever

**File:** `src/lib/discovery/watch-state.ts:332-339,405-422`
**Issue:** Two separate defects in the lock:
1. Race. Runs A and B both see an EEXIST lock with a dead pid. A unlinks and re-creates it; B then unlinks (removing A's fresh lock) and re-creates it. Both believe they hold the lock. The window is small (a manual run racing the Monday run after a crash), but `unlink` followed by `create` is not an atomic takeover.
2. Pid reuse. `isPidAlive` only asks whether some process has that pid. After a crash, reboot or power loss, the pid in the lock file is routinely reused by an unrelated process (after a reboot pids restart low). The lock then reads as live and every weekly run exits with code 3 until someone deletes the file by hand. The failure is silent apart from the log file. `startedAt` is stored but never used.
**Fix:** Treat a lock as stale when it is older than a cap (for example `Date.now() - Date.parse(startedAt) > 6 h`) regardless of pid. For the takeover, rename the stale file to a unique name first (`renameSync(lockPath, `${lockPath}.stale-${pid}`)`, which only one racer can win), then create with `wx`, and re-read the file after creating it to confirm your pid is in it.

### WR-03: A mail that was only written to a file still marks every flat as "seen"

**File:** `scripts/fit-score.ts:611-617`
**Issue:** When `WATCH_SMTP_URL` or `WATCH_EMAIL_TO` is missing, the `no-env` branch writes the HTML and then calls `saveState()`. The launchd job exits 0. If the variables are lost (a typo in `~/.zshenv`, a rotated password rewritten wrongly, a shell that does not read the file), the new flats are recorded as seen and are never emailed; they exist only in an HTML file nobody opens. The `failed` branch correctly keeps the memory. Nothing in the exit code tells launchd or the user anything went wrong.
**Fix:** For an unattended `--email` run, treat `no-env` like `failed` (exit 4, memory untouched), and keep the "write the HTML and save state" behaviour behind an explicit flag such as `--file-only`. At minimum, exit non-zero on `no-env` so the log line `Slut: ..., kod N` shows it.

### WR-04: The local browser retries the same challenged page up to four times, not "one retry"

**File:** `src/lib/booli/local-browser.ts:389-410`, `src/lib/booli/client.ts:592-601,944-955,1227-1236`
**Issue:** `render` makes two attempts for a challenged page (D-04: "one retry"). But `fetchListing`, `fetchAreaPage` and `fetchSoldComps` each wrap `runPlaywrightRender` in two `walkFallbackTree` rungs, designed for Apify's fresh-proxy retry. With the local renderer a challenged page is requested 4 times (two attempts, 5 s wait, then the same again), from one home IP, which is the thing most likely to turn a soft challenge into a block. The spend block also reports `stats.challenged`/`retried` that no longer match the documented policy.
**Fix:** Make the second rung a no-op when a local renderer is installed (for example `isLocalRendererActive()` exported from `transport.ts`), or have `render` throw a `NonRetryable` error after its own second challenge that `walkFallbackTree` does not retry.

### WR-05: Vision cache key ignores model, prompt and schema version

**File:** `src/lib/discovery/vision-cache.ts:74-80,188-199`
**Issue:** An entry is keyed by listing path plus a hash of the picture URLs and the broker photo count. A cache hit is returned as-is and never expires. When the vision prompt, the model or `visionResultSchema` changes, every previously read flat keeps serving the old claims (kitchen/bathroom condition, which feed the renovation tier and profit) until its photos change. A schema-compatible but semantically different prompt change will not even trip the "corrupt cache" path. Separately, the key uses the URL path, so a flat that switches `/annons/` to `/bostad/` is read and paid for again, and a broker photo swap with the same count reuses stale claims.
**Fix:** Add a `VISION_PROMPT_VERSION` (or hash of the prompt + model id) to `imageSetKey`/`entryId`, and key on the booli id digits rather than the full path. Optionally expire entries after N days.

### WR-06: Broker-page render in the local browser has no final-URL or private-address check (known follow-up, with a wider blast radius than the Apify version)

**File:** `src/lib/booli/local-browser.ts:352,383`, `src/lib/broker/fetch-broker-page.ts:164-181`
**Issue:** The only gate is `resolveSafeExternalUrl(url)` on the starting URL (one DNS lookup in Node). The Chromium on Daniel's Mac then does its own DNS lookup (rebinding: public at check time, `127.0.0.1` at navigation time), follows any redirect chain without inspection, and loads sub-resources and iframes from any host. With Apify the render ran in Apify's cloud, so internal addresses were unreachable; here the browser is on the home network and next to local services (local Supabase on 54321, Next dev server, the router admin page). The broker URL comes from a listing, so it is attacker-influenceable. The result is GET requests with side effects against local services and local page text flowing into `parseBrokerPage`. `page.goto` also returns after redirects, so the final URL is available.
**Fix:** After `goto`, parse `page.url()` and refuse (throw a non-retryable error before running the page function) unless the final host is the same registrable host as the start URL or passes `resolveSafeExternalUrl` again. For defence in depth add `context.route("**/*", ...)` that aborts requests to loopback, link-local and RFC1918 addresses and non-http(s) schemes, for broker pages at least.

### WR-07: Memory fingerprint takeover can hide a genuinely new flat

**File:** `src/lib/discovery/watch-state.ts:185-193,26-32`
**Issue:** A row with an unseen key takes over any stored entry with the same "address|district|kvm" fingerprint and an equal asking price. The stored entry has no floor, and entries stay for 90 days after the flat sold. Two units in one building with the same area and the same asking price (identical units are common in uniform associations), listed within three months of each other, make the second one "already seen": it is not new, not in the mail, and its first mail never happens. The module comment argues that a false "new" is visible and a false "already seen" is not; this path produces the invisible kind. The inverse also exists: if the old flat's own row comes later in the same run, the earlier row steals its entry and the old row is reported "new".
**Fix:** Store `floor` (when known) in the entry and require `floorCompatible` on takeover; only take over an entry whose key is not itself present in this run's rows (pre-compute the set of all run keys before the loop, not `seenKeys`, which only holds keys processed so far); optionally require `lastSeen` within the last 14 days.

### WR-08: Per-run vision spend is understated when a billed call failed (known follow-up, confirmed still open)

**File:** `src/lib/discovery/vision-cache.ts:225-241`, header note at lines 27-29
**Issue:** `spentSek` sums `c.vision.costSek` over results that came back. A call that was billed and then refused or truncated counts against the lane cap inside `runVisionPass`, but is invisible here, so the printed `Bildtolkning: ... X kr av tak 60 kr` can read lower than the real Anthropic bill. The 60 SEK ceiling itself still holds (it is enforced inside the pass), but the pinned spend line is not the real spend, which is what the weekly report claims it is.
**Fix:** Have `runVisionPass` return its running spend per lane (or the failed-call cost) and add it to `spentSek`; until then label the line as a lower bound, for example "minst X,XX kr".

### WR-09: `launchd` SIGTERM is not forwarded by the wrapper, so the browser-close and lock-release handlers may never run

**File:** `scripts/launchd/run-weekly.sh:42`
**Issue:** The wrapper runs `caffeinate -i tsx ...` as a child of zsh (no `exec`, because it needs the closing log line). `closeOnSignals` is written so that SIGTERM to the node process closes Chromium and exits 143, and the README says launchd stops jobs with SIGTERM. But launchd signals the job's main process, which is the zsh wrapper. zsh dies on SIGTERM without relaying it to `caffeinate`/`node`, which are then killed hard when launchd cleans the process group (not verified on this machine). Result: no graceful browser close, a leftover Playwright temp profile, a stale lock file.
**Fix:** Run the command in the background and forward signals:
```sh
caffeinate -i ./node_modules/.bin/tsx scripts/fit-score.ts "${ARGS[@]}" &
CHILD=$!
trap 'kill -TERM "$CHILD" 2>/dev/null' TERM INT
wait "$CHILD" || CODE=$?
```
(keep `set -e` interplay in mind: `wait ... || CODE=$?`, and a second `wait` after the trap fires).

### WR-10: `landLeaseFromText` can turn a stated tomträtt into "ruled out"

**File:** `src/lib/discovery/listing-facts.ts:223-232`
**Issue:** Any occurrence of `friköp` or `avlös` anywhere in the text returns `false` ahead of the tomträtt mention. "Föreningen har tomträtt, möjlighet att friköpa finns" or "tomträtten ska avlösas 2028" are read as "not tomträtt", so the "tomträtt" reason is not shown on exactly the flats the column exists to explain. The comment only justifies the case "har friköpt tomträtten". The same ordering applies to `ej|inte|ingen|utan ... tomträtt`, which is fine, but `utan` is also the common conjunction ("lägenhet, utan tomträttsavgäld...").
**Fix:** Only rule out when the verb is past tense or perfect (`friköpt`, `avlöst`, `har friköpt`, `friköpte`) and otherwise keep `true`; drop `utan` from the negation list or require it directly before the noun with no intervening word.

### WR-11: `pull-slutpriser.ts` and `fit-score.ts` duplicate shutdown wiring; `pull-slutpriser` does not guarantee the cache is saved after a signal

**File:** `scripts/pull-slutpriser.ts:117-134,631-656`
**Issue:** `closeOnSignals` exits 130 after `handle.close()`; the code after the `try/finally` (`persist(result.cache)`, summary) never runs. The cache is persisted per page by `persist`, so data loss is limited to the in-flight page, but the last-page state (`status: failed/ok`) of workers still running when the signal arrives is lost and those pages re-render next run. Combined with CR-01, workers still running during the close window also issue Apify renders.
**Fix:** Fixing CR-01 removes the paid-call part. For the rest, have the signal handler call a shared `abort()` that stops new work in `pullSlutpriser` (it already has `renderAllowed`) before closing the browser.

## Info

### IN-01: `new Function` compiles any string a Booli-URL caller passes; the "repo-owned only" claim is not enforced

**File:** `src/lib/booli/local-browser.ts:237-244,383-387`
**Issue:** Only broker URLs are tied to `BROKER_RENDER_PAGE_FUNCTION`. For a Booli URL, `compile(pageFunction)` compiles whatever string arrives. Today every caller passes a repo constant, but the guarantee in the header and in T-14.2-03 is by convention only.
**Fix:** Keep a `Set` of the three allowed sources (`APOLLO_PAGE_FUNCTION`, `BRF_PAGE_FUNCTION`, `BROKER_RENDER_PAGE_FUNCTION`) and throw on anything else before `compile`.

### IN-02: Unit `kr` in the BRF parser has no trailing boundary

**File:** `src/lib/booli/brf-page.ts:105,87`
**Issue:** `valueAfter(t, LOAN_LABEL, /kr/)` accepts "Lån 5 000 kr/kvm" or "kronor" as a loan of 5 000. The 2026-10-13 fixtures (`brf-page-1..3`) are clean, so this is hypothetical until Booli adds such a line, but it would produce a plausible-looking wrong skuld/kvm. Not found: null handling and the blank-line layout (`GAP` allows up to 8 line breaks) are correct, and `debtPerSqm` is null when either number is missing or the area is 0.
**Fix:** `/kr(?![a-zåäö\/])/i`, and for the area `/(?:m²|m2|kvm)(?![a-z0-9])/`.

### IN-03: Skuld per kvm divides total loans by tenant-owner area only

**File:** `src/lib/booli/brf-page.ts:109`
**Issue:** "Lån" is the association's total loan, "Boarea bostadsrätter" excludes commercial and rental floor area. An association with a large commercial or hyresrätt share overstates debt per kvm and can trip "hög föreningsskuld" (10 000 kr/kvm). The fixtures show 0 hyresrätter, so this has not shown up yet.
**Fix:** Print the report year next to the reason ("hög föreningsskuld (12 345 kr/kvm, 2024)") and note the limitation in the module header.

### IN-04: Lock directory is not created before `acquireRunLock`

**File:** `scripts/fit-score.ts:528-541`, `src/lib/discovery/watch-state.ts:392`
**Issue:** `openSync(lockPath, "wx")` fails with ENOENT when `.planning/calibration/data` does not exist (fresh checkout, the folder is gitignored). The error is not `EEXIST`, so it is rethrown, `main().catch` prints it and exits 1 before any work. Every other writer uses `mkdirSync(..., { recursive: true })`.
**Fix:** `mkdirSync(dirname(lockPath), { recursive: true })` at the top of `acquireRunLock`.

### IN-05: Unpinned spend lines print a decimal point; error text for broker pages says "Booli"

**File:** `scripts/fit-score.ts:725,731,793`, `src/lib/booli/local-browser.ts:356`
**Issue:** The pinned lines use a decimal comma (`renderVisionLine`, `formatApifyRunsLine`, `percent`), but `Anthropic (bildtolkning): ${result.visionSek.toFixed(2)} kr`, `Apify: uppskattning 0.12 USD` and `Uppskattad Apify-kostnad: ... USD` print a dot. A broker page returning 404 throws "Booli svarade HTTP 404".
**Fix:** Route those through the same comma formatter; use a neutral message ("Sidan svarade HTTP n").

### IN-06: Vision cache and Playwright temp state are never cleaned

**File:** `src/lib/discovery/vision-cache.ts:243-251`, `src/lib/booli/local-browser.ts:293-299`
**Issue:** Cache entries are replaced per listing but never pruned, so flats that sold stay forever (the watch memory prunes at 90 days; this does not). Chromium started by Playwright uses a temp profile directory that is removed on a clean close; after a hard kill (see WR-09) those directories, which contain Booli and broker-site cookies and cache, stay in the temp folder.
**Fix:** Prune cache entries older than 90 days using `storedAt`; remove stale `playwright_chromiumdev_profile-*` directories at startup or accept and document it.

### IN-07: Small duplication and loose ends

**File:** `scripts/fit-score.ts:182`, `scripts/launchd/run-weekly.sh:14-15`, `scripts/probe-local-booli.ts:177-180`, `scripts/launchd/com.bostadai.weekly-watch.plist`
**Issue:** `DEFAULT_APIFY_MAX_RENDERS = 10` is redeclared in `fit-score.ts` although `local-browser.ts` exports it. The wrapper sources `~/.zshenv`, which zsh already reads for every invocation, so PATH entries can be added twice (harmless). `guardedSavePath` in the probe allows overwriting any file under `data/` or `__fixtures__` (including `watch-state.json`, `vision-cache.json`) and has no extension rule. The log file at `~/Library/Logs/bostadai-weekly-watch.log` is append-only and has no rotation.
**Fix:** Import the constant; drop the explicit sourcing or keep it with a comment; require `.txt`/`.json` and refuse the known state file names in the probe; add a `newsyslog` entry or truncate the log in the wrapper when it passes a size.
