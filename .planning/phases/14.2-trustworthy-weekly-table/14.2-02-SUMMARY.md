# Phase 14.2 Plan 02: Complete District Lists and CandidateFacts Summary

## Accomplishments

- Booli prints how many listings a search has ("totalCount") next to the cards. The page function now keeps that number (and the title that says which list it belongs to) as `SearchMeta` entries. A number with no cards beside it still counts as a dead page, so a change in Booli's card format shows up as a failed source and never as an empty district (W6).
- `fetchAreaListings` with `{ maxPages: 15, minLivingArea: 35 }` pages until the count is reached and returns `totalCount`, `pagesFetched` and `complete`. A call without options is the 14.1 behaviour.
- `listing-facts.ts` is a pure module with a typed facts record. Card facts and detail facts merge, with the detail winning. It is tested on the real captured pages.
- Four real fixtures (about 71 kB) are committed, sanitized: no agent names, no phone numbers, no e-mail addresses, no description text.

In plain terms: before this plan the weekly list stopped after five pages per district and nobody could tell whether anything was missing. Now each district reports "N av M" from Booli's own number, and the run can say honestly when it is short.

## Decisions Made

- `complete` is `areaCompleteness(listings.length + unlistedProjects, totalCount)`. Plain `listings.length >= totalCount` would have said `ofullständig` on three of the four districts every single week, which makes the signal useless. The allowance is bounded: it is at most the number of new-construction items Booli counts and does not draw (0 to 5 here), and the pipeline drops new construction anyway.
- The page count comes from page 2's size. Dividing by page 1's size (the plan's `ceil(totalCount / page-1 size)`) stopped Kungsholmen at 13 pages and left 32 listings unread.
- `listPricePercentageDiff` keeps Booli's sign (negative is lower) because that is what Booli prints next to the price. Only `priceCutSek` is flipped.
- The elevator and balcony stay `null` for a card that does not list them and become `false` only after a detail read (R-04b).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Page count from page 1's size undercounts when page 1 carries extra project cards**
- **Found during:** Task 2 (first real completeness run, Kungsholmen: `455 av 487`)
- **Issue:** The plan's rule `ceil(totalCount / page-1 size)` assumes pages are equal. Kungsholmen page 1 has 38 cards and later pages 35, so 487 / 38 gave 13 pages where 14 were needed.
- **Fix:** After page 1, page 2 is fetched and its size fixes the page count (`1 + ceil((renderable - page1Size) / page2Size)`, capped by `maxPages`); a page 2 under 20 listings is the last page; a failed page 2 falls back to the page-1 lower bound. Pages 3 and up still run in parallel.
- **Files modified:** `src/lib/booli/client.ts`, `src/lib/booli/client.test.ts`
- **Verification:** unit tests for the Kungsholmen shape (14 pages) and for a short page 2; real run `482 av 487 (14 sidor, komplett)`.
- **Committed in:** f0814fa

**2. [Rule 1 - Bug] "complete = collected >= totalCount" reads incomplete on a complete district**
- **Found during:** Task 2 (real runs: `441 av 444`, `507 av 509`)
- **Issue:** Booli's count includes new-construction items it never draws as cards (a search for only those returns fewer cards than its own count). A bare comparison would have flagged three of four districts every week.
- **Fix:** `fetchAreaListings` reports `newConstructionCount` (Booli's Nyproduktion count), `unlistedProjects` (that count minus the project cards actually collected) and `complete`. `areaCompleteness(collected, totalCount)` keeps the exact behaviour the plan specified; the adjustment is applied by the caller. A test pins that missing regular listings still read incomplete.
- **Files modified:** `src/lib/booli/client.ts`, `src/lib/booli/client.test.ts`, `scripts/probe-local-booli.ts`
- **Verification:** unit tests (Södermalm and Kungsholmen shapes, genuine shortfall stays incomplete); real runs complete on all four districts.
- **Committed in:** f0814fa

## Issues Encountered

- A page past the real last page has no Apollo data, so the local renderer reports it as challenged and fails it after a 5 s retry. The page count is therefore computed to land on the last real page; asking for 14 pages on Södermalm would have produced a failed page. The exact formula can overshoot by one page when the hidden projects push the total over a page boundary. A failed page is non-fatal and counted in the line, so the worst case is one noisy page, not a wrong answer.
- Test counts: `npm run test` 1 592 passed / 3 skipped (baseline 1 495 passed). `npx tsc --noEmit` and `npm run lint` clean.
