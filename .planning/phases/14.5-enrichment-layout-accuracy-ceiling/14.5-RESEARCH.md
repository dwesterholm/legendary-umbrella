## Summary

Four findings change the plan compared with what CONTEXT.md assumes. (F1) The stage-2 clamp does not touch cross-validation: `cvRmseLog` is computed from stage 1 only, so D-03's rule "commit ±12 % only if CV does not worsen" would always pass and decide nothing. A stage-2 cross-validation (fit balcony and build-year on four folds, score the fifth) is the honest replacement and is small. (F2) `scripts/valuation-report.ts` cannot take the 14.4 `after/ranking.json` as "before": `buildValuationReport` throws `Före-posten är inte från modell version 1` and the whole report is a 14.1 → 14.4 three-way waterfall. D-04's intent (14.4 → 14.5 movement) needs a small new pure module and script. (F3) The sold-detail payload carries no broker description, so no sold row can ever carry a stated ceiling height; the ≥ 300 threshold of D-06 cannot be met and the hedonic ceiling feature should not be built (taste, column and the for-sale parser are still built). (F4) Layout experiments run on Sonnet 4.6 are billed in the cost ledger at Haiku rates (3 times too low): the "0,11 kr per read" quoted in RESUME.md is really about 0,32 kr, and `runLayoutReads` cannot be pointed at a second prompt or model without deleting the production cache.

On the cap itself, an informal preview on the 1 395 rows enriched so far (read-only, not committed) gives balcony +7,7 % unclamped (95 % interval +6,6 to +8,9 %), so at n ≈ 5 400 the balcony effect probably no longer sits exactly on the ±8 % line; the build-year bucket 1961–1990 comes out at about −10,8 % unclamped (108 rows, so about ±2 points) and is the likely reason a ±12 % step would be triggered. Folkungagatan 61 is built 1912 and has a balcony, so its decomposition depends on the balcony number, not on the 1961–1990 bucket.

Layout accuracy is the hard part and is limited by what a judge can see, not by the model. In the 14.4 eye check, with the same four Booli pictures the model sees, street versus courtyard could be decided for the balcony on 2 of 12 flats and for the bedroom on 1 of 12, while window sides were decidable on 11 of 12. A truth set of 25 random flats would therefore hold about 4 decided balcony sides and 2 decided bedroom sides, far too few to measure 75 %. The set must be chosen from the 74 flats that have stored reads by scanning contact sheets for decisive photos, judged blind (before looking at any model read), and split into a development part (prompt iteration) and a locked holdout (the gate decision). Fields with fewer than 12 decided rows are reported "not measurable" and keep the switch off.

**Primary recommendation:** Build in this order: (1) pure tooling that needs no Booli and no cache (ceiling parser and facts/taste/columns, layout-accuracy module, variant-aware experiment runner with correct cost rates, valuation-compare), (2) the truth set and the paid layout rounds while the enrichment finishes, (3) after the `=== END` line only, the hedonic cap parameter, the refits (±8 % and the single ±12 % variant), the comparison report and the model commit. Do not edit any of the 18 files that `scripts/pull-slutpriser.ts` imports until `=== END` appears (listed under Pitfall 1).

### Pattern 1: Cap as a parameter, travelling with the model
**What:** `clampPct(x, cap)`; `fitHedonicModel(rows, { ..., stage2CapPct? })` defaulting to `STAGE2_CAP_PCT`; the model records `stage2.capPct` (optional zod field, no version bump).
**When to use:** the single ±12 % variant of D-03. Restrict the option to two allowed values so "no second widening" is enforced in code.
**Example:**
```typescript
// hedonic-model.ts today [VERIFIED: hedonic-model.ts:700 and :1812-1814]
//   export const STAGE2_CAP_PCT = 0.08;
//   function clampPct(x: number): number {
//     return Math.min(STAGE2_CAP_PCT, Math.max(-STAGE2_CAP_PCT, x));
//   }
// proposed
export const STAGE2_CAP_WIDENED_PCT = 0.12;
export const STAGE2_ALLOWED_CAPS = [STAGE2_CAP_PCT, STAGE2_CAP_WIDENED_PCT] as const;
function clampPct(x: number, cap: number): number {
  return Math.min(cap, Math.max(-cap, x));
}
// schema: stage2: z.object({ capPct: num.min(0).optional(), balcony: ..., buildYear: ... })
// readers: const capOf = (m: HedonicModel) => m.stage2.capPct ?? STAGE2_CAP_PCT;
```

### Pattern 2: Variant-aware layout reads with their own cache
**What:** a `VariantSpec` (id, model id, system prompt, user instruction, schema, effort, steps) with `version = layoutReadVersion({...})` and one cache file per variant, `.planning/calibration/data/layout-exp-<id>.json`.
**Why:** `runLayoutReads` hard-codes the module constant `LAYOUT_READ_VERSION` in the cache id and in the filter that keeps only current-version entries [VERIFIED: layout-read.ts:392 `if (e.promptVersion === LAYOUT_READ_VERSION) entries[id] = e;`]. Running another prompt through it with the production cache path would drop every other entry (Pitfall 3).

### Pattern 3: Two-step read combined by a pure function
**What:** step A sees the plan only and reports positions relative to the entrance wall and window walls; step B sees only photos and reports per picture what lies outside the window and from which room it was taken. A pure `combineTwoStep(a, b)` produces the existing `LayoutRead` shape so everything downstream (cache entry, `layoutFactFromRead`, gate) is unchanged. Truth table in the code examples.
**When to use:** only round (d), if (a)-(c) stay under 75 % on some field.

### Anti-Patterns to Avoid
- **Editing a file `pull-slutpriser.ts` imports while batches 2, 3 or the BRF pass are about to start.** Each batch is a fresh `npx tsx` process that re-reads the source.
- **Judging with the model's read on screen.** The 14.4 eye check showed the read next to each flat (anchoring). Judge blind.
- **Choosing the gate on the same flats used to tune the prompt.** Keep a locked holdout.
- **Putting the Opus model id into `vision-prompt.ts`.** That file is one of the four locked vision files (D-14); define it in `layout-read.ts`.

## Common Pitfalls

### Pitfall 1: Editing files the running batches import
**What goes wrong:** `enrich-full.sh` starts a new `npx tsx scripts/pull-slutpriser.ts` for batch 2, batch 3 and the BRF pass. A syntax error or schema change in any imported file crashes that start (script writes `STOP: batch N exit` and stops), or changes how the cache is parsed and written mid-run.
**Why it happens:** the closure of imports is wider than it looks. Computed this session by walking the imports of `scripts/pull-slutpriser.ts`:
`src/lib/apify/booli-scraper.ts`, `src/lib/booli/{brf-page,client,fallback-tree,image-host,local-browser,page-functions,slutpriser,transport}.ts`, `src/lib/brf/cost.ts`, `src/lib/broker/{fetch-broker-page,parse-broker-page,url-guard}.ts`, `src/lib/discovery/{area-seed,cost,filter-schema,hedonic-model}.ts`.

### Layout accuracy measurement design (pure module `layout-accuracy.ts`)

- **Per-field correctness** for read `r` against truth `t` (undecidable truth rows are excluded from that field's denominator and counted):
  - balcony side: correct if `r.balconySide === t.balconySide` over `street|courtyard|none`; separately `balconyPresence` (none vs has) because Booli's own balcony flag decides that for free and would inflate a combined number; headline = street/courtyard among truth rows with a balcony.
  - korsdrag: `twoOpposite` is "ja", `one` or `corner` is "nej" (same mapping as `korsdragWhen`); truth the same mapping.
  - bedroom: street/courtyard against truth.
- **Believed vs raw:** compute everything twice, raw (no gate) and believed (the gate's value; null = abstain). Report coverage = believed / decidable and precision = correct / believed.
- **Curve:** for thresholds `t` over the distinct observed confidences, keep reads with confidence ≥ t (per-field confidence when available, else the single one) and the field's evidence rule, and output `{ t, nBelieved, nCorrect, precision, wilsonLow, wilsonHigh }`. The model's confidence will be coarse (14.4 values cluster at 0,40 / 0,55 / 0,60 / 0,70 / 0,9), so the curve has few distinct points; do not interpolate.
- **Gate rule (D-11 made exact):** gate(field) = the lowest observed `t` such that precision ≥ 0,75 at `t` AND at every higher observed threshold (guards against a lucky dip), with `nBelieved(t) ≥ 10`. If none exists the field "fails" and the report names the best precision reached and its n. Choose the gate on the dev rows, then report the same gate on the holdout rows; the switch decision is made on the holdout numbers (precision ≥ 0,75 on each field, n ≥ 10 believed). If holdout cannot supply 10 believed calls for a field, it reports "not enough evidence" and the switch stays off.
- **Intervals:** Wilson 95 %. For orientation, 15 of 20 correct (75 %) has a lower bound of 0,53; 23 of 30 (77 %) has 0,59; 24 of 30 (80 %) has 0,63; 12 of 12 has 0,76 [computed this session]. The decision rule is the point estimate (D-11), but the report prints the interval so Daniel sees how little 20 flats can prove.
- **By evidence type:** also tabulate balcony/bedroom precision by `streetEvidence` (cars, courtyardGreenery, oppositeFacade) to answer D-12.

### Wilson interval
```typescript
export function wilson(k: number, n: number, z = 1.96): { low: number; high: number } {
  if (n === 0) return { low: 0, high: 1 };
  const p = k / n, d = 1 + (z * z) / n, c = p + (z * z) / (2 * n);
  const a = z * Math.sqrt((p * (1 - p)) / n + (z * z) / (4 * n * n));
  return { low: (c - a) / d, high: (c + a) / d };
}
```

### Gate from the curve
```typescript
export function gateFromCurve(curve: { t: number; nBelieved: number; precision: number }[], minN = 10, target = 0.75) {
  const desc = [...curve].sort((a, b) => b.t - a.t);
  let gate: number | null = null;
  for (const pt of desc) {            // walk from the strictest threshold down
    if (pt.nBelieved >= minN && pt.precision >= target) gate = pt.t;
    else if (pt.nBelieved >= minN) break;   // first failing point with enough support ends the walk
  }
  return gate;                          // null = field fails or unmeasurable
}
```

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Prompt injection in broker text or a picture ("ignore instructions") | Tampering | Layout answers are enums validated by schema and a deterministic gate; ceiling parser extracts a number from text and never executes or forwards text; no tool use |
| PII (names, phone numbers) in broker description | Information disclosure | Parser output is a canonical phrase and a number; the description variable is nulled right after, as in `watch-enrich.ts` |
| ReDoS on long descriptions | Denial of service | Bounded quantifiers only (`{0,3}`, `{1,3}`, `{1,2}`); cap input at about 50 000 characters before matching |
| Pictures kept on disk | Information disclosure | Scratchpad directory deleted after judging; grep check above; GDPR rule from the vision phases |
| Cost overrun from a mis-priced ledger | Denial of wallet | Rates per model from a table, cap enforced on real usage, smoke before each round |
