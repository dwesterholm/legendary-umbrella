## Summary

The money-side code is in good shape. I traced the balcony-share centring from the fit (`fitStage2`) through the stage-2 cross-validation to `predictKrPerSqm`: fit, CV and serving all use the same multiplier, and a model file without `share` predicts exactly as before. The kill switch holds: with `LAYOUT_INFLUENCE_ENABLED = false` the only paths into the score (`korsdragOf`, `quietBedroomOf`, `inferredSunWithLayout`) return null or the unchanged sun input, and the coverage line reads the layout through the `*When(..., true)` variants on purpose. Sonnet 4.6 ($3/$15), Opus 5.5 ($4/$20) and Sonnet 5.5 ($2/$10) match the current model table, and the Opus call correctly sends no `temperature`. The TypeSafe call reads the key only as satt/saknas and logs errors by class and HTTP status only.

The one real problem is the one you suspected. The live run has no stop rule at all (CR-01). That is the only item I would hold the Monday job for.

I also ran the ceiling parser on 17 sample sentences. The numeric reading behaves well (2,2–5,0 band, other-space and low-ceiling skips, cm and spelled-out numbers). The negation handling for "högt i tak" is too narrow (WR-06).

## Critical Issues

### CR-01: The live run does not stop at Booli's first 403 or challenge

**File:** `src/lib/discovery/watch-enrich.ts:195-326` (the per-candidate loop and the BRF loop), `scripts/fit-score.ts:1363-1365` (where `enrichAllCandidates` is wired in), `src/lib/booli/local-browser.ts:581-614` (the render that keeps answering "failed" instead of "blocked")

**Issue:** `enrichAllCandidates` checks only a deadline (`now() - startedAt >= opts.deadlineMs`, lines 196 and 307). Nothing in it, in `fit-pipeline.ts`, or in `fit-score.ts` calls `enrichStopReason`. So after Booli's first challenge, every remaining candidate still gets a detail page request, and the local browser then requests it a second time after a 5 s wait (`LOCAL_CHALLENGE_RETRY_MS`). That is exactly the 54 pages / 108 attempts in the 14.5-13 summary. Three more places keep sending traffic after a block:

- The broker leg inside each candidate (line 225) is a different host, but it runs only after a Booli detail page was read, so it does not add Booli traffic. It is not the problem.
- The BRF stage (lines 297-326) requests one Booli page per association after the detail stage, with no stop check.
- The area scrape (`fit-score.ts:1402`) pages all four districts in parallel and treats a failed page as non-fatal (`client.ts` `fetchPages`), so a block in the first district does not stop the others.

The rule already exists and is tested for the enrichment path: `enrichStopReason` in `src/lib/booli/slutpriser.ts:1207` ("a challenge page stops the run at once"), fed by `browser.stats().challenged` through `makeRunGuard` in `scripts/pull-slutpriser.ts:440-458`. The live run never uses it. Consequence: a block that could end after one refused page is extended by roughly a hundred more requests from the same IP, and the Monday job is the one that pays, because the 24 h gate (`booli-gate`) then stays closed.

The error cannot be used as the signal, because the renderer turns a double challenge and any other failure into the same `NonRetryableRenderError` (local-browser.ts:614). The counter in `handle.stats().challenged` is the signal.

**Fix:**

1. `watch-enrich.ts`: add `shouldStop?: () => boolean` to `WatchEnrichOptions` and check it where the deadline is checked, plus once more after `fetchListing` returns and in the BRF pool task:
   ```ts
   const stopped = (): boolean => opts.shouldStop?.() === true;
   // top of readOne, and in the BRF task:
   if (stopped() || now() - startedAt >= opts.deadlineMs) { skipped += 1; return; }
   ```
   Return a `stoppedBy: "utmaning" | null` field in `WatchEnrichment` so the caller can print it.
2. `fit-score.ts` (`enrichOnly`, line 1363): pass `shouldStop: () => (handle?.stats().challenged ?? 0) > 0`. `handle` is a `const` declared later in `runLive`, but the closure runs after it is initialised, so this is safe. Use the same `enrichStopReason` function rather than a second copy of the rule, so the weekly run and the restart cannot drift (add `attempted` and `failed` counters in the wrapper if you want the 5 % failure rate too).
3. `fit-score.ts` scrape: after each district settles, skip the remaining districts when `challenged > 0`, or run the districts one after another in local mode.
4. `local-browser.ts`: add a latch. After a Booli page has been challenged twice, set `blocked = true` and make every later Booli render throw `NonRetryableRenderError` immediately, without `page.goto`. This covers every caller (area pages, detail, BRF, pull-slutpriser) even if a loop forgets to check. Also add an option to skip the 5 s retry for the live run (`retryChallenge: false`), so the first refusal is the last request.
5. After the stage, print the same line as `printStopReason` ("Stopp: utmaning från Booli upptäckt ... Vänta minst ett dygn"), set a non-zero exit code, write the refusal to the traffic log as `booli-gate --refused` does, and have the weekly email say that enrichment was cut short (today `header.incomplete` only reflects the area listing, so a half-enriched run looks complete).

## Warnings

### WR-01: `stats.challenged` counts broker-site challenges too

**File:** `src/lib/booli/local-browser.ts:586-589`
**Issue:** `stats.challenged += 1` runs for every `ChallengeError`, including a third-party broker page (`broker === true`). If the live run adopts the shared rule from CR-01 as written, one Cloudflare page on a broker's site would stop a run that Booli never blocked. In the opposite direction, a Booli block can be hidden among broker numbers in the printed ledger.
**Fix:** Count Booli and broker challenges separately (`challengedBooli`, `challengedBroker`), keep `challenged` as the Booli number for `enrichStopReason`, and print both in the local ledger line.

### WR-02: Experiment runner: a throwing `checkpoint` double-records the item and loses its own result

**File:** `src/lib/discovery/layout-experiment.ts:554-573`
**Issue:** `opts.checkpoint?.(cacheNow())` sits inside the same `try` as the call. In the script the checkpoint is `saveVariantCache`, which throws on a full disk or a path guard failure. When that happens after `reads.push({status:"read"})` and `fresh.set(...)`, the `catch` pushes a second outcome with status `failed` for the same flat. The result then has more entries than `items` (the doc says "same length and order as the items"), `calls` counts a read that is also reported failed, and any code that indexes reads by position is shifted. The same happens on the `BAD_ANSWER` path.
**Fix:** Move the checkpoint calls outside the `try`, or wrap them separately: `try { opts.checkpoint?.(cacheNow()); } catch { checkpointFailed = true; }`, and return `checkpointFailed` so the script exits non-zero after saving once more.

### WR-03: No lifetime ceiling on experiment spend

**File:** `src/lib/discovery/layout-experiment.ts:550` (cap test), `scripts/layout-accuracy.ts:497-546` (`run`)
**Issue:** D-13 says at most 40 kr per round and at most 4 rounds (160 kr). The code enforces 40 kr per invocation only; `spentSekTotal` is documented as "a ledger, never a cap". Six variant ids exist (a, b, c, d-sonnet, d-opus, e), and every re-run after a billed failure gets a fresh 40 kr. Nothing stops a retry loop or a mistaken second `--run c` from spending more than the phase allowance. For the weekly job a per-run cap is right (layout-read.ts says so), but this runner is an experiment tool.
**Fix:** Add `LAYOUT_EXPERIMENT_TOTAL_CAP_SEK = 160` and refuse a round in `run()` when the sum of `spentSekTotal` over the variant caches plus the dry-run estimate exceeds it, with an explicit `--allow-over-total` escape that prints a warning.

### WR-04: The pass rule uses the point estimate, so 5 or 6 calls can "pass"

**File:** `src/lib/discovery/layout-accuracy.ts:414-420` (gate), `:535-554` (`fieldVerdict`), constants at `:240-244`
**Issue:** The bar is `k/n >= 0.75` with `MIN_BELIEVED_HOLDOUT = 5` and `MIN_BELIEVED_TOTAL = 10`. The module computes Wilson intervals but no decision uses them. Balcony side "passes" in c, d and e on holdout 6 of 6; the Wilson 95 % lower bound for 6 of 6 is about 61 %, and for 13 of 13 about 77 %. The gate is also read off the dev curve and then validated on a handful of holdout rows, so a lucky small sample can clear it. The switch is off today, so nothing moves money, but the verdict text says "at least 75 % reliable" and a later person flipping the switch would be relying on this.
**Fix:** Either keep the point-estimate rule and state it in the verdict output ("lower bound X %"), or require the Wilson lower bound on the pooled rows to be at least a stated floor (for example 0,60) in `fieldVerdict`. Print the lower bound next to the pass line in `renderComparisonMd`.

### WR-05: `productionCandidate` can be called "cheapest" when no cost was measured

**File:** `src/lib/discovery/layout-compare.ts:201-206`
**Issue:** A variant without a parsed round log has `sekPerFlat === null` and is priced as `Infinity`. If every passing variant has a null cost, the first column wins and the markdown still says "Billigast per lägenhet av dem, och därmed produktionskandidat enligt R-10". If only one has a cost, it wins by default. This line is what R-10 uses to decide that Jev becomes the production variant.
**Fix:** Skip passing columns with `sekPerFlat === null` when choosing; if none has a cost, return `productionCandidate: null` and render "kostnad ej mätt för de som klarar kraven".

### WR-06: "Högt i tak" flag fires on negations other than a bare "ej/inte/ingen" directly in front

**File:** `src/lib/discovery/ceiling-height.ts:85-86`
**Issue:** The lookbehind only catches `ej|inte|ingen` followed by whitespace and then the phrase. I ran the parser: "Inte särskilt högt i tak men ljust.", "Lägenheten har inte några höga tak." and "Saknar höga tak." all return `tallCeilingPhrase: true`. The flag is display-only today ("högt i tak" in the Takhöjd cell and the coverage count), so no money moves, but the cell then tells Daniel the opposite of the listing. The module comment says a missed phrase is free and a false hit is not.
**Fix:** Drop a clause from the tall check when it contains a negation word anywhere before the phrase: `const NEGATED = /(?<![\p{L}])(?:ej|inte|ingen|inga|saknar|utan|knappast)(?![\p{L}])/iu;` and `if (!tall && !NEGATED.test(clause) && TALL.test(clause)) tall = true;`. Add the three sentences above as test cases.

### WR-07: `fit-hedonic` replaces the model file before it knows the report can be written

**File:** `scripts/fit-hedonic.ts:1005-1033`
**Issue:** `writeTextAtomic(outPath, ...)` runs first (default `data/hedonic-model.json`). Then `--report-json` throws if `measuredStage2 === null` or if `fitReportJsonSchema.parse(payload)` fails. The script exits 1, but the committed model has already been replaced with the new fit. A caller that sees exit 1 and assumes nothing was written is wrong.
**Fix:** Build and validate the report payload (and throw on `measuredStage2 === null`) before writing the model, then write both. Also mention in the header comment that `--out` defaults to the committed model.

### WR-08: Variant version hash misses parts that change what a stored read means

**File:** `src/lib/discovery/layout-experiment.ts:262-298`, `src/lib/discovery/layout-typesafe-call.ts:56-77`, `src/lib/discovery/layout-typesafe.ts:35,207`
**Issue:** The hash covers model, prompts, schema, call shape, image counts and `LAYOUT_LOGIC_REVISION`. For variant e it does not cover how the pictures are prepared (plan as PNG, photos as JPEG q90, 1568 px cap, 280 px padding), the images header, or the mapping rule `noul >= 0.5`. Changing any of these changes the answers but not the version, so a re-run silently reuses old cached reads, and the accuracy report mixes two conditions under one name. Only a manual bump of `LAYOUT_LOGIC_REVISION` (which would re-key variants a to d as well) protects against this.
**Fix:** Add the preparation settings and mapping threshold to `spec.typesafe` (`imagePrep: { planFormat, photoFormat, jpegQuality, ... }, yesThreshold: 0.5`) so they enter the hash for e only.

## Info

### IN-01: `prepareJevImage` upscales a small picture instead of padding it

**File:** `src/lib/discovery/layout-typesafe-call.ts:65`
**Issue:** `resize({ width: w, height: h, fit: "contain" })` scales the image up to fit inside the new box. A 200x200 picture becomes 280x280 enlarged, not padded; only mixed shapes (for example 100x1000) get white bars. The doc says "padded with white". Harmless for the layout read, but the comment is wrong.
**Fix:** Use `extend` with the missing pixels (`sharp(bytes).extend({ top, bottom, left, right, background })`) or fix the comment.

### IN-02: Model schema accepts any `stage2.capPct` and does not check the values against it

**File:** `src/lib/discovery/hedonic-model.ts:227`
**Issue:** `capPct: num.min(0).optional()` lets a file say `capPct: 5` with a balcony of 0,3. `valuation-compare` and `valuation-report` then flag "on the cap" against that number. `fitHedonicModel` itself only allows 0,08 or 0,12.
**Fix:** In the `superRefine`, require `capPct` (when present) to be one of `STAGE2_ALLOWED_CAPS` and `|balcony.pct|`, and each bucket pct, to be at most `capPct`.

### IN-03: `capDecision` widens on a tie

**File:** `src/lib/discovery/valuation-compare.ts:238-239`
**Issue:** `cv12 <= cv8` picks ±12 % when the two errors are equal, which is what happens when no value sits on the 8 % cap. The sentence printed says "alltså inte sämre", true but the widening was not needed. `capStepNeeded` covers this elsewhere, but `capDecision` alone can be read as a recommendation to widen.
**Fix:** Use a small tolerance and a strict improvement: `cv12 < cv8 - 1e-9`, or return `chosen: 0.08` when `capStepNeeded` is false.

### IN-04: Days-term cross-validation scores the unclamped term, serving uses the clamped one

**File:** `src/lib/discovery/hedonic-model.ts:1744-1749` (CV) against `:730` (prediction)
**Issue:** At prediction `ln(1+days)` is clamped to `[lnLo, lnHi]`. The CV that decides whether the term is kept applies it unclamped to held-out rows, so the kept/rejected verdict is measured on a slightly different formula from the one that prices flats.
**Fix:** Clamp `dl` with the fold's own 1st and 99th percentile inside the CV loop.

### IN-05: The live run uses no start gap between page starts

**File:** `scripts/fit-score.ts:1337-1365` (compare `scripts/pull-slutpriser.ts:588-601`)
**Issue:** `--start-gap-secs` (R-07) exists for the enrichment restart only. The weekly run relies on the local browser's own 1-2 s pacing with two pages in flight. Given three blocks after 35 to 64 pages, a floor like the restart's 2 s may be worth applying here too.
**Fix:** Thread an optional `startGate` into the `fetchListing` and `fetchBrfFacts` deps in `watch-enrich.ts`, with the same `makeStartGate` helper.

### IN-06: Ceiling parser takes the first plausible height in text order

**File:** `src/lib/discovery/ceiling-height.ts:165-176`
**Issue:** "Takhöjd 2,4 m i sovrum, 3,4 m i vardagsrum" gives 2,4; "Takhöjd 3,4 m i vardagsrum men 2,4 m i sovrum" gives 3,4 and 2 % of resale in taste. Both are by design (first wins), but the second turns one tall room into a flat-wide bonus. It stays inside the 5 % cap and is labelled "angiven", so this is a note rather than a defect.
**Fix:** Optional: when a clause names a room word (vardagsrum, sovrum, kök, hall) that is not the living room, skip it, or take the lowest of several stated heights.
