### Part 2 — ceiling height (CEIL-01, CEIL-02), Claude's judgement as Daniel asked
- **D-05 (source):** stated text only. Parser `ceilingHeightFromText(text): { metres, phrase } | null` over the broker description: patterns like "takhöjd 3,2 m", "takhöjd på/om ca 3 meter", "3,5 meters takhöjd", "högt i tak (3,4 m)", comma or dot decimals, "m"/"meter"; plausibility 2,2–5,0 m, else null; "högt i tak" without a number → `tallCeilingPhrase: true` as a flag only, never a number. Attach `ceilingHeightM` + `ceilingSource: "angiven"` to `CandidateFacts` (for-sale detail text, already read for sun phrases) and to the sold row's `enriched` record IF the probe shows sold-detail payloads carry the description (one offline probe over the three saved dumps + the fixtures first; if absent, say so and skip the sold side).
- **D-06 (model):** fit `ceilingHeightM` as a hedonic feature only if ≥ 300 sold rows carry it (honesty rule: null → mean, `imputed`); report SE. Below 300: not fitted, reported as "för få angivna" — never imputed from build year into the valuation.
- **D-07 (taste + table):** `TASTE_WEIGHTS` gains `ceilingPct`: +0,01 at ≥ 3,0 m, +0,02 at ≥ 3,5 m (fraction of resale), unknown adds 0, inside the unchanged 5 % cap (`TASTE_CAP_PCT`); "Takhöjd" column in table and mail ("3,2 m" / "högt i tak" / "okänd"). The sold-side enrichment for height, if possible, runs AFTER the running enrichment finishes (D-01) and only over rows it would re-read anyway — or as a text-only pass that renders no page if the description is already in the cache. Never a second concurrent local browser.

### Part 3 — layout read accuracy (LAYACC-01..03)
- **D-09 (truth set):** ≥ 25 flats from the current snapshot + the 14.4 live run (plans + photos available via cached image URLs), judged by the executor by eye from the floor plan and photos with a written procedure (what counts as street evidence; corner/two-side windows; bedroom side relative to the balcony side; "undecidable" allowed and counted). Stored as `truth/layout-truth.json` under the phase directory: Booli id, fields, confidence of the judge, one-line justification. Folkungagatan 61 is row 1 with the known truth (balcony street, windows one side, bedroom street). No photos persisted.
- **D-10 (experiments):** against the truth set, in this order, each ≤ 40 kr and cached: (a) the current prompt + Sonnet as baseline accuracy per field; (b) a reworked prompt with explicit evidence rules (cars/street lamps/shopfronts/tram wires = street; bicycle racks/lawns/sandpits/the building's own rear facade = courtyard; artificial grass or decking on a balcony is NOT greenery; the plan's entrance arrow is NOT a side; "undecidable" is a valid answer) on Sonnet; (c) the same prompt on the Opus tier; (d) if still < 75 %: two-step reading (plan first → which side has the balcony relative to the entrance; then photos → which side is the street), combined in code. Stop at the first variant that reaches ≥ 75 % on all three fields; record every variant's per-field accuracy and a confidence-vs-accuracy curve.
- **D-11 (gate and switch):** the gate is set per field from the measured curve (the lowest confidence at which precision ≥ 75 % on the truth set), not 0,6 by assumption. `LAYOUT_INFLUENCE_ENABLED` flips to true ONLY when balcony side, korsdrag and bedroom side each reach ≥ 75 % accuracy on the truth set at that gate; the flip is its own commit quoting the numbers. Otherwise it stays false and the SUMMARY says which field failed and what was tried. The weekly job keeps running the read either way (it is the measurement).
- **D-12 (sun-side evidence, UAT item 5):** when the switch is on, the balcony side steers the sun facade only for `streetEvidence` in {cars, courtyardGreenery} (not oppositeFacade, which fits both sides) — unless the truth set shows oppositeFacade is reliable (≥ 75 %), in which case keep it and record that.
